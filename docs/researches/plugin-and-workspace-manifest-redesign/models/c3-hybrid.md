# Модель C3 — Hybrid in-tree/out-of-tree

## Описание

Построена на модели B, но добавляет явный маркер типа плагина
в `plugin.yml`:

```yaml
# .agloom/plugins/team-rules/plugin.yml
kind: in-tree
name: team-rules
description: "Shared rules for internal reuse"
```

```yaml
# external repo — cusxy/skill-cycling/plugin.yml
kind: out-of-tree
name: skill-cycling
version: 2.0.1
description: "Cycling agents for Agloom"
author:
  name: "cusxy"
  email: "..."
```

Для `kind: in-tree` поля `version` и `author` становятся
опциональными — признание «эти поля не поддерживаются в живом
репо». Для `kind: out-of-tree` валидация строгая, как сейчас.

## Плюсы

- **C3+1**. Все плюсы модели B сохраняются.
- **C3+2**. Эстетический выигрыш по K4: явный маркер kind
  делает документально очевидным, для чего плагин предназначен.
- **C3+3**. Пользователь, глядя на `plugin.yml`, сразу понимает
  режим валидации.
- **C3+4**. Позволяет ослабить требования identity для
  in-tree без ослабления для out-of-tree (что важно для
  `cusxy/skill-cycling` и будущих реестров).

## Минусы

- **C3-1**. Дополнительное поле, дополнительный enum,
  дополнительная валидация — стоимость реализации выше,
  чем у B.
- **C3-2**. Избыточность: тип плагина уже выводится из того,
  КАК он подключён в `config.yml`. Если `path:` указывает
  внутрь текущего репо — in-tree, если на git — out-of-tree.
  Явное поле `kind:` дублирует эту информацию и требует
  её согласованности (что если `kind: in-tree`,
  но подключён через git?).
- **C3-3**. K9 страдает: ещё одно понятие для объяснения
  в guide («kind у плагина»).
- **C3-4**. Ослабление identity-полей для in-tree создаёт
  второй tier валидации. Если автор затем захочет опубликовать
  in-tree плагин out-of-tree, нужна миграция `kind` + добавление
  обязательных полей.

## Контекст применимости

- **Оправдано, если**: опыт показывает, что B оставляет слишком
  много свободы интерпретации у пользователя. C3 добавляет
  явный контракт.
- **Не оправдано, если**: тип плагина прозрачно выводится
  из места подключения (что фактически верно для v1).

## Оценка по критериям

| K   | Значение | Обоснование                                       |
| --- | -------- | ------------------------------------------------- |
| K1  | high     | как B                                             |
| K2  | high     | как B                                             |
| K3  | yes      | ослабление identity для in-tree                   |
| K4  | high     | явный маркер kind                                 |
| K5  | yes      | как B                                             |
| K6  | small    | чуть больше, чем B (парсинг kind)                 |
| K7  | medium   | +новая секция «Kind плагина» в plugin-manifest.md |
| K8  | high     | как B                                             |
| K9  | medium   | дополнительное понятие для объяснения             |
| K10 | easy     | как B                                             |

## Вердикт

**Резервный вариант.** Близок к B по всем сильным сторонам,
но добавляет избыточное поле и сложность валидации. Рекомендуется
как fallback, если в ходе реализации B проявятся проблемы
интерпретации in-tree vs out-of-tree со стороны пользователей.
Не рекомендуется сразу, потому что тип плагина выводим
из места подключения — явное поле `kind:` избыточно на v1.
