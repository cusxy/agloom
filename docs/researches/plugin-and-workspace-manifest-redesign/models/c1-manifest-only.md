# Модель C1 — Manifest-only

## Описание

Статус-кво: дихотомия `config.yml` / `plugin.yml` сохраняется
в неизменном виде. Плагины живут ТОЛЬКО в отдельных репозиториях
и подключаются через git-ref. Запрет `config.yml` в директории
плагина сохраняется. Для shareable rules у автора нет
альтернативы — обязательный вынос в отдельный репозиторий.

Изменения от текущего состояния: никаких структурных —
только возможное добавление `targets:` и `plugins:`
в `plugin.yml` для независимых улучшений (транзитивные deps,
декларация поддерживаемых адаптеров).

## Плюсы

- **C1+1**. Минимум изменений — ментальная модель уже знакома
  пользователям, читавшим текущие спеки.
- **C1+2**. Чёткая семантическая граница: «плагин = отдельный
  репо». Нет двусмысленности.
- **C1+3**. identity-поля `plugin.yml` работают как задумано —
  каждый плагин имеет релизный цикл.
- **C1+4**. Secondary use case (distribution) обслуживается
  идеально.

## Минусы

- **C1-1 (fatal для primary)**. Автор вынужден создавать
  отдельный репозиторий для каждого shareable-набора правил,
  даже если правила используются только между его двумя
  внутренними проектами. Релизный цикл навязан.
- **C1-2**. Dogfooding формально запрещён: автор не может
  держать `.agloom/config.yml` в директории плагина для
  собственной разработки. Нужно либо нарушать спеку, либо
  держать дев-setup вне `.agloom/`.
- **C1-3**. Несколько наборов shareable rules = несколько
  репозиториев. Административный overhead.
- **C1-4**. Невозможно атомарно менять правила и их
  потребителя — нужно коммитить в два репо.

## Контекст применимости

- **Оправдано, если**: приоритет — distribution через публичный
  реестр, а не внутренняя переиспользуемость.
- **Оправдано, если**: автор готов платить административную
  стоимость отдельного репо за каждый набор правил.
- **Не оправдано, если**: primary use case — переиспользование
  между проектами одного автора без релизного цикла (это
  исходный запрос пользователя, см. RESEARCH.md § 1.2).

## Оценка по критериям

| K   | Значение | Обоснование                                       |
| --- | -------- | ------------------------------------------------- |
| K1  | **low**  | принуждает к отдельному репо для каждой share     |
| K2  | high     | distribution работает идеально                    |
| K3  | yes      | identity-поля на своём месте                      |
| K4  | medium   | семантика чистая, но use case не покрыт           |
| K5  | **no**   | запрет config.yml в плагине не снят               |
| K6  | small    | никаких изменений                                 |
| K7  | small    | минимальные (только targets/plugins опционально)  |
| K8  | high     | без изменений                                     |
| K9  | high     | простая ментальная модель                         |
| K10 | medium   | требует отдельного protocol'а для transitive deps |

## Вердикт

**Отвергнута.** Проваливает K1 и K5. Модель адекватна только
для чисто distribution-сценария, но primary use case agloom
согласно context — внутренняя переиспользуемость без релизного
цикла. Упоминается в исследовании как baseline «что будет,
если ничего не менять».
