# Исследование: стек лендинга agloom.sh

Дата: 2026-04-07

## Контекст исследования

### Проблема

Agloom — CLI-инструмент на TypeScript/Node.js, транспилирующий канонические
файлы `AGLOOM.md` в форматы конкретных AI-агентов (`CLAUDE.md`, `AGENTS.md`
и др.). Документация уже реализована на Docusaurus и хостится отдельно
на `docs.agloom.sh`. Маркетинговый лендинг `agloom.sh` отсутствует.

### Мотивация

Лендинг — основная точка входа для нового пользователя: формирует первое
впечатление, доносит ценностное предложение и направляет на установку.
Docusaurus-сайт оптимизирован под навигацию по документации, а не под
маркетинговый storytelling, и переиспользовать его как landing невозможно
без компромиссов в обоих направлениях.

### Цель

Выбрать стек и организацию репозитория для одностраничного лендинга
с возможностью плавного роста (добавление showcase-страницы) и сохранением
свободы кастомизации визуала.

### Границы

Исследуется только стек **отдельного лендинга**, который собирается и
деплоится независимо от docs-сайта. За границами:

- Реализация лендинга (содержимое hero, копирайтинг, дизайн).
- Выбор хостинга — заранее зафиксирован Cloudflare Pages для обоих сайтов.
- Архитектура docs-сайта — рассмотрена в [docs-site-generators](docs-site-generators/RESEARCH.md).
- Аналитика, A/B-тесты, формы — не в scope MVP.

### Ограничения от пользователя (Q1–Q4)

- **Q1.** На старте — строго одна страница (hero, install, features, CTA,
  links). В обозримой перспективе — добавление showcase. Блог и changelog
  не планируются.
- **Q2.** Структура репозитория обсуждается отдельно (см. соответствующую
  секцию ниже).
- **Q3.** Визуальная амбиция — минимализм в духе Bun, Hono, Drizzle.
  Без тяжёлых иллюстраций и scroll-анимаций.
- **Q4.** Критическое ограничение — необходима глубокая кастомизация
  визуала. Это исключает движки с навязанной темой, где приходится бороться
  со слоем темизации (Docusaurus, VitePress, Starlight в режиме landing).

## Критерии оценки

Критерии определены до анализа кандидатов (защита от anchoring bias).

## Эмпирические данные: стеки лендингов известных dev-tool проектов

Для калибровки рекомендации проведена проверка стеков публичных лендингов
популярных dev-tool проектов в нише CLI и библиотек. Стек определялся по
артефактам HTML (asset paths, generator-теги, специфичные window-объекты)
и кросс-проверкой с публичными репозиториями.

### Наблюдения

- **Доминирующий стек минималистичных dev-tool лендингов — Astro** (Biome,
  Tauri, Drizzle, и сам Astro). VitePress занимает второе место, но он
  тяготеет к docs-первым сайтам, где landing — это просто `index.md` с
  `layout: home` (Vite, Vitest, Hono).
- **Next.js** встречается у проектов с большой маркетинговой амбицией
  и корпоративной поддержкой (Turborepo / Vercel) — это переусложнение
  для одностраничного OSS-лендинга.
- **Docusaurus** в нише лендингов занимает миноритарную позицию: единственный
  пример из выборки (tRPC) использует его как docs-first инструмент,
  а не как landing-движок.
- **Чистый custom HTML/CSS** в публичной выборке встречается у Bun. Это
  проект с собственной командой и in-house web-инфраструктурой; для
  одного мейнтейнера такой подход редко окупается.
- **Совмещение лендинга и docs в одном инструменте** — норма (8 из 10 в
  выборке). Раздельная архитектура (Agloom) — меньшинство, и это требует
  отдельного решения по стеку лендинга.
- **Bias-предупреждение (B7, survivorship).** Выборка содержит только
  успешные проекты — провалы и забытые лендинги в неё не попали. Поэтому
  «доминирование Astro» — это сигнал, а не доказательство.

## Кандидаты

Описаны шесть обязательных и два опциональных кандидата. Версии указаны
по состоянию на апрель 2026.

### 1. Чистый HTML/CSS (+ ванильный JS)

Один `index.html`, один `styles.css`, опционально `script.js` для copy
button. Без сборщика, без зависимостей. Деплой как статическая директория.

**Когда оправдан.** Одностраничный лендинг без планов роста, мейнтейнер
комфортно пишет CSS вручную, нет необходимости в шаблонизации.

**Плюсы.**

- Нулевые зависимости и нулевой maintenance overhead — нет breaking changes,
  нет миграций мажорных версий.
- Минимальный размер бандла: HTML + 1 CSS-файл, JS только при необходимости.
  Lighthouse 100/100/100/100 достижим без оптимизации.
- Полная свобода разметки и стилей — ничего не навязывает структуру.
- Cloudflare Pages: build command пустой, output directory — корень.

**Минусы.**

- Нет компонентов: дублирование разметки между лендингом и потенциальным
  showcase. При росте до 2–3 страниц возникает копипаста header/footer.
- Подсветка install snippet — вручную (Shiki в браузере или заранее
  сгенерированный HTML), copy button — ручной JS.
- Нет dev-сервера с HMR из коробки (хотя `python -m http.server` работает).
- Нет готовых стартеров под dev-tool лендинг — всё пишется с нуля.
- Сборка assets (favicon-варианты, OG-image, SVG-оптимизация) — ручная.

### 2. Astro

Content-focused SSG с островной архитектурой. Zero JS by default,
интерактивные островки гидрируются по требованию. Поддержка `.astro`
компонентов, MDX, React/Vue/Svelte как opt-in. Версия 5.x.

**Когда оправдан.** Лендинг + рост до showcase / blog / changelog,
важна производительность и кастомизация без навязанной темы, мейнтейнер
готов к лёгкой компонентной модели.

**Плюсы.**

- Zero JS by default: для типового лендинга финальный JS-bundle ~0 KB,
  если не использовать islands. Lighthouse «из коробки» близок к 100.
- `.astro`-компоненты — простой шаблонный синтаксис без необходимости
  выбирать UI-фреймворк. Можно подключить React только для одного
  интерактивного блока.
- Полная свобода разметки и стилей — нет навязанной темы (в отличие
  от Starlight). Scoped CSS из коробки.
- Встроенный Shiki для подсветки кода (`<Code />` компонент), что
  напрямую закрывает требование install snippet.
- Официальный гид Cloudflare Pages: build `npm run build`, output `dist`.
- Эмпирически доминирующий выбор минималистичных dev-tool лендингов
  (Biome, Drizzle, Tauri, astro.build).
- Лёгко добавляются страницы: `src/pages/showcase.astro` — и страница есть.
  Content collections готовы к будущему showcase с typed frontmatter.

**Минусы.**

- Зависимости и build-tooling: ~200 MB `node_modules`, под капотом vite,
  esbuild и sharp. Требует регулярных bump до новых major (Astro выпускает
  major 1–2 раза в год — 2.0 → 5.x за ~3 года).
- Кривая обучения `.astro`-синтаксиса (frontmatter скрипт + JSX-подобная
  разметка) — небольшая, но ненулевая.
- Image optimization (sharp) тяжеловесна для одного хеадер-логотипа,
  её можно отключить.

### 3. Vite + React (SPA)

Минимальный SPA-сетап: `npm create vite@latest -- --template react-ts`.
Один компонент `App.tsx`, ручной CSS или Tailwind. Билд через `vite build`,
output `dist`.

**Когда оправдан.** Команда уже использует React, нужна богатая
интерактивность (формы, dynamic content), нет претензий к JS-bundle.

**Плюсы.**

- Знакомая React-модель компонентов; для разработчика, уже работающего
  с React, нулевая кривая обучения.
- Vite-DX отличный: HMR <50 ms, мгновенный cold start.
- Полная свобода разметки.
- Cloudflare Pages: build `npm run build`, output `dist`.

**Минусы.**

- SPA-модель: HTML почти пустой, контент рендерится JS. Lighthouse
  «из коробки» хуже, чем у SSG; требуется SSR/prerender для нормального
  SEO и социальных preview-карточек, что сводит на нет «минимализм»
  сетапа.
- Bundle включает react + react-dom (~45 KB gzipped) для лендинга,
  где React почти не нужен.
- Подсветка кода — отдельная зависимость (`shiki`, `prism-react-renderer`).
- Нет готовых стартеров под dev-tool лендинг с фокусом на минимализм.
- Рост до showcase требует ручного роутера (react-router), что превращает
  «минимальный SPA» в полноценное SPA-приложение.
- Не используется Ink-стек проекта (Ink — это TUI, не web; React-компетенция
  команды переоценена как аргумент).

### 4. 11ty (Eleventy)

Лёгкий шаблонный SSG на Node.js без обязательного сборщика для CSS/JS.
Поддержка Nunjucks, Liquid, Markdown, JS-шаблонов. Версия 3.x.

**Когда оправдан.** Контент-сайт с упором на Markdown, минимум JS,
мейнтейнер любит шаблонизаторы вроде Nunjucks.

**Плюсы.**

- Очень лёгкий: ~10 MB зависимостей, без vite/esbuild по умолчанию.
- Полная свобода разметки и стилей; никакой темы не навязано.
- Один из самых маленьких bundle: HTML генерируется напрямую из шаблонов,
  JS добавляется только тем, что вы написали руками.
- Cloudflare Pages: официальная конфигурация — build `npx @11ty/eleventy`,
  output `_site`.
- Просто масштабируется на showcase: добавить `.md`-файлы с frontmatter
  и template — и страницы появляются.

**Минусы.**

- Подсветка кода — через плагин (`@11ty/eleventy-plugin-syntaxhighlight`),
  copy button — руками.
- Меньше готовых стартеров для dev-tool лендингов, чем у Astro
  (есть starter packs, но в нише ориентированы на блоги).
- Шаблонный синтаксис (Nunjucks/Liquid) — отдельный язык; для команды,
  привыкшей к JSX/Astro, это шаг назад в DX.
- Нет встроенной обработки CSS/JS — Tailwind и автопрефиксер требуют
  отдельной настройки PostCSS или подключения внешнего pipeline.
- Меньше momentum в нише dev-tool лендингов: ни один проект из выборки
  не использует 11ty.

### 5. Next.js (static export)

`next build` с `output: 'export'` в `next.config.js`. Получается статическая
директория `out`. Версия 15.x.

**Когда оправдан.** Команда стандартизирована на Next.js, лендинг — часть
большой Next-инфраструктуры, нужны Vercel-маркетинговые примитивы.

**Плюсы.**

- Богатая экосистема UI-китов и маркетинговых компонентов.
- File-based routing, готовый image optimization (с ограничениями
  в static export).
- Cloudflare Pages поддерживает static-Next через отдельный гид.
- Используется Turborepo и другими крупными проектами с маркетинговой
  амбицией.

**Минусы.**

- Тяжеловесный фреймворк: даже в static export bundle включает React,
  next runtime, ~80–120 KB gzipped минимум. Для одностраничного лендинга
  это переусложнение.
- Static export ограничивает функциональность: нет middleware, нет
  ISR, нет image optimization в полной мере. Это «деградировавший» Next,
  где половина возможностей выключена.
- Высокая частота breaking changes: 13 → 14 → 15 за два года, App Router
  vs Pages Router раскол, нестабильные RSC API — большой maintenance
  overhead для одного мейнтейнера.
- Эмпирически в нише минималистичных лендингов почти не встречается
  (Turborepo — исключение, не правило).

### 6. Docusaurus (для baseline)

React-based SSG, оптимизированный под документацию. Версия 3.x. Уже
используется в `website/` для docs-сайта Agloom.

**Когда оправдан.** Лендинг и docs живут в одном инструменте, кастомизация
ограничена темизацией Docusaurus, не требуется индивидуальный визуал.

**Плюсы.**

- Уже знаком команде — мейнтейнер настраивал `website/` ранее.
- Готовый landing-template (`@theme/Layout` + кастомные React-компоненты).
- Версионирование, i18n, sidebar — пригодны для будущего расширения.

**Минусы.**

- **Несоответствие Q4 (критическое).** Docusaurus навязывает Infima
  CSS-фреймворк и набор `@theme/*` компонентов. Глубокая кастомизация
  требует swizzling, который ломается при minor-апдейтах темы. Это
  именно та «борьба с темой», которую пользователь хочет избежать.
- Bundle тяжёлый: React + Docusaurus runtime + Infima ≈ 200+ KB JS
  даже для пустой страницы.
- Webpack-based: cold build медленнее Vite/Astro.
- Двойной Docusaurus (docs + лендинг как два инстанса) — дублирование
  зависимостей и удвоение maintenance burden.
- Эмпирически почти не используется как landing-движок: tRPC — единственный
  пример из выборки, и он совмещает docs+landing в одном инстансе.

### 7. Опциональные: Starlight, VitePress, SvelteKit

- **Starlight.** Astro-based docs-фреймворк. **Отклоняется по Q4**:
  это тема поверх Astro с собственной структурой, навигацией и
  CSS-токенами. Хороший выбор для docs (что подтверждают Biome, Tauri),
  но для лендинга со свободой кастомизации он избыточен — мейнтейнер
  всё равно будет писать `src/pages/index.astro` руками. В этом случае
  чистый Astro предпочтительнее.
- **VitePress.** Vue-based docs-first инструмент. **Отклоняется по Q4**:
  его landing работает через `layout: home` в `index.md` с фиксированной
  структурой hero/features. Кастомизация требует Vue-компонентов поверх
  default theme — это та же «борьба с темой».
- **SvelteKit (adapter-static).** Хороший SSG, но не доминирует в нише
  dev-tool лендингов и добавляет ещё один UI-фреймворк к стеку проекта,
  который уже использует React (Ink). Не включён в детальный анализ,
  потому что не даёт уникальных преимуществ перед Astro.

**Обозначения**: оценки бандла — порядок величины для типового лендинга
без тяжёлых зависимостей.

## Структура репозитория: монорепо vs отдельный репо

Q2 пользователя — выбор между подпапкой в текущем монорепо Agloom
(рядом с `website/`) и отдельным репозиторием `agloom-landing`.

### Вариант A: монорепо-подпапка (`landing/` рядом с `website/`)

**Плюсы.**

- Один источник правды: лендинг, docs, исходники CLI и release-tagging
  живут вместе; не нужно держать несколько checkouts.
- Общий CI: один GitHub Actions workflow с матрицей build для
  `website/`, `landing/` и пакета.
- Атомарные коммиты при изменении бренда (например, новый install snippet
  одновременно в README, docs и landing).
- Версия CLI и контент лендинга синхронизируются автоматически — релизный
  тег охватывает всё.
- Pnpm workspace уже настроен, добавление `landing/` тривиально.

**Минусы.**

- Захламление основного репо: больше watchers в IDE, больше файлов
  в `git status`, дополнительный `node_modules/`.
- Риск pipeline-перехлёста: lint/test pipeline монорепо может триггериться
  на изменения в лендинге, если не настроены paths-фильтры в Actions.
  Митигируется через `paths:` / `paths-ignore:` в workflow.
- Контрибьюторам с доступом только к лендингу всё равно виден весь
  исходник CLI.

### Вариант B: отдельный репозиторий (`agloom-landing`)

**Плюсы.**

- Полная изоляция истории: коммиты лендинга не смешиваются с коммитами
  CLI; clean `git log`.
- Можно дать write-доступ дизайнеру или контрибьютору без раскрытия
  основного кода.
- Независимые CI-минуты, независимый release cycle.
- Меньше шум в основном репо.

**Минусы.**

- Двойная синхронизация при изменении бренда: install snippet, версия,
  ссылки — обновлять в двух репозиториях вручную.
- Два места для issue tracking: пользователь не знает, куда нести фидбек
  по лендингу — в основной репо или в `agloom-landing`.
- Удвоение boilerplate: два `.github/`, два набора workflows, два
  `pnpm-lock.yaml`, две настройки Cloudflare Pages.
- Лендинг небольшой по объёму (одна страница) — собственный репо
  выглядит overkill.

### Сравнение

| Критерий                         | Монорепо `landing/` | Отдельный `agloom-landing` |
| -------------------------------- | ------------------- | -------------------------- |
| Boilerplate / setup              | Минимальный         | Удвоенный                  |
| Sync контента (версии, snippets) | Атомарный           | Ручной                     |
| Загрязнение основного репо       | Среднее             | Нулевое                    |
| Изоляция доступа                 | Нет                 | Да                         |
| Шум в `git status`/IDE           | Есть                | Нет                        |
| Release coupling с CLI           | Естественный        | Нужно настраивать          |

### Рекомендация по структуре

**Монорепо-подпапка** для Agloom оправдана. Решающие аргументы:

- Один мейнтейнер — изоляция доступа не нужна.
- Релиз CLI и обновление лендинга часто будут идти вместе (новые фичи —
  новые блоки в features-секции, новые install snippets).
- Boilerplate отдельного репо не окупается для одностраничного сайта.
- Cloudflare Pages умеет деплоить из подпапки монорепо: настраивается
  «Root directory» в проекте и отдельный «Build output directory»
  (`landing/dist`).

Риск pipeline-перехлёста снимается стандартными `paths:`-фильтрами в
GitHub Actions: workflow для лендинга триггерится только на
`landing/**`, workflow для CLI — на `src/**`, `packages/**`, `tests/**`.

## Анализ trade-offs

### HTML/CSS vs Astro

Чистый HTML лучше Astro по K1 (поддержка) и K2 (размер бандла), но
проигрывает по K8 (рост) и K3 (DX маркет-блоков). Astro даёт zero-JS
output, сравнимый по весу с HTML/CSS, но добавляет компонентную модель,
встроенный Shiki и легко масштабируется на showcase. Критическая разница
— K8: пользователь явно сказал, что showcase будет следующим шагом.
Поэтому ради экономии 5–10 KB и пары мегабайт зависимостей не стоит
жертвовать тем, что станет нужно через 2–3 месяца.

### Astro vs Next.js

Next.js даёт богатую экосистему компонентов, но платит за это размером
бандла (×6–10 раз больше Astro по K2), частотой breaking changes
(K1) и переусложнением для одностраничного сайта. Эмпирически Next.js
доминирует у проектов с маркетинговой амбицией и командой ≥3 человек
(Turborepo); для одного мейнтейнера и минималистичного визуала это
неоправданное усложнение.

### Astro vs Vite+React

Vite+React даёт знакомый компонентный синтаксис, но в форме SPA: пустой
HTML, контент рендерится JS, плохой SEO без prerender. Astro решает
ту же задачу через `.astro`-компоненты с zero-JS output. React можно
подключить как island, если понадобится — гибридность сохраняется.

### Astro vs 11ty

11ty легче по зависимостям и проще в pipeline, но проигрывает по K3
(нет встроенного Shiki), K7 (меньше dev-tool стартеров) и DX (Nunjucks/
Liquid вместо JSX-подобного синтаксиса). 11ty — рациональный выбор для
блог-ориентированных сайтов; для лендинга dev-tool с install snippet
и feature grid Astro даёт больше из коробки.

### Astro vs Docusaurus

Docusaurus отсекается по Q4 — навязанная тема Infima и swizzling-механика
противоречат требованию свободной кастомизации. Также Docusaurus
дублирует уже существующий инстанс (`website/`), что удваивает maintenance
burden без выигрыша.

## Заключение

### Решение: Astro в подпапке `landing/` монорепо

По совокупности критериев и эмпирических данных рекомендуется **Astro**
как стек лендинга и **монорепо-подпапка `landing/`** как структура.

**Обоснование стека (Astro).**

1. **K4 — кастомизируемость (high).** Astro не навязывает темы. Лендинг
   пишется как `src/pages/index.astro` со свободной разметкой и стилями.
   Это снимает критическое ограничение Q4.
2. **K2 — размер бандла (high).** Zero JS by default обеспечивает
   Lighthouse-метрики, сопоставимые с чистым HTML/CSS.
3. **K8 — возможность роста (medium).** Добавление showcase сводится
   к созданию `src/pages/showcase.astro` или content collection. Q1
   явно фиксирует showcase как следующий шаг.
4. **K3 — DX маркет-блоков (medium).** Встроенный Shiki через `<Code />`
   закрывает install snippet; copy button — однострочный island.
5. **Эмпирическое доминирование.** В выборке минималистичных dev-tool
   лендингов (Biome, Tauri, Drizzle, astro.build) Astro — самый частый
   выбор. Это сигнал, что инструмент проверен в нише.
6. **K5 — Cloudflare Pages.** Официальная поддержка, build `npm run build`,
   output `dist`. Нулевое трение настройки.

**Компромиссы.** Astro добавляет ~200 MB зависимостей и требует регулярных
bump major-версий (1–2 раза в год). Для одного мейнтейнера это допустимо:
breaking changes Astro исторически касаются конфига, не контента, и
миграции занимают <1 часа.

**Обоснование структуры (монорепо).** Один мейнтейнер, тесная связь
лендинга с релизами CLI, отсутствие потребности в изоляции доступа,
неоправданность boilerplate отдельного репо. Изоляция CI достигается
через `paths:`-фильтры в GitHub Actions.

### Альтернативы и когда они оправданы

- **Чистый HTML/CSS** — если мейнтейнер уверен, что лендинг останется
  одностраничным навсегда и комфортно пишет CSS вручную. Пересмотреть
  выбор при появлении второй страницы.
- **11ty** — если предпочтение шаблонизаторам перед JSX-подобному
  синтаксису сильнее, чем выгода от встроенного Shiki.
- **Vite+React** — если планируется существенная клиентская интерактивность
  (формы, dashboards) и SEO не критичен.

### Отклонённые варианты

- **Next.js (static export)** — переусложнение для одностраничного
  лендинга, частые breaking changes, бандл в 6–10 раз тяжелее Astro.
- **Docusaurus** — нарушает Q4 (навязанная тема, swizzling), дублирует
  существующий инстанс `website/`.
- **Starlight, VitePress** — навязанные docs-темы, нарушают Q4.
- **SvelteKit** — не даёт уникальных преимуществ перед Astro в нише
  лендингов, добавляет ещё один UI-фреймворк к стеку.

### Next-step план

1. Создать подпапку `landing/` в корне монорепо рядом с `website/`.
2. Инициализировать через `pnpm create astro@latest landing -- --template minimal --typescript strict`.
3. Структура: `src/pages/index.astro` (hero, install, features, CTA, links),
   `src/components/` (Hero, Features, InstallSnippet, CTA), `src/styles/global.css`.
4. Использовать встроенный `<Code />` для install snippet (npm/pnpm/bun
   tabs — три блока + минимальный JS island для переключения).
5. Настроить GitHub Actions workflow `landing.yml` с `paths: ['landing/**']`.
6. Создать второй проект Cloudflare Pages для `agloom.sh` с root
   directory `landing/`, build command `pnpm --filter agloom-landing build`,
   output `landing/dist`.
7. Showcase отложить до фактической потребности; зарезервировать
   `src/pages/showcase/` и `src/content/showcase/` под content collection.

## Choices

- **C1 — Стек: Astro 5.x.** Контекст: 6 кандидатов сравнены по 8 критериям,
  доступны эмпирические данные о доминирующих стеках dev-tool лендингов.
  Анализ: Astro выигрывает по K2/K4/K8 одновременно, что для одностраничного
  лендинга с планами роста и требованием кастомизации — решающее сочетание.
  Confidence: **high**.
- **C2 — Структура: монорепо `landing/`.** Контекст: один мейнтейнер,
  существующий pnpm workspace, тесная связь с релизами CLI. Анализ: boilerplate
  отдельного репо не окупается; изоляция доступа не нужна; pipeline-перехлёст
  митигируется paths-фильтрами. Confidence: **high**.
- **C3 — Опциональные кандидаты исключены.** Контекст: Starlight, VitePress,
  SvelteKit рассмотрены кратко. Анализ: первые два нарушают Q4 (навязанная
  тема), третий не даёт уникальных преимуществ перед Astro. Confidence: **high**.
- **C4 — Showcase реализуется на том же стеке (Astro), отложен до явной
  потребности.** Контекст: Q1 фиксирует showcase как «следующий шаг»,
  но без сроков. Анализ: преждевременная имплементация добавит maintenance
  без пользователей. Astro готов к расширению через content collections
  без рефакторинга. Confidence: **medium**.
- **C5 — Cloudflare Pages настраивается как отдельный проект для `agloom.sh`,
  не как ветка существующего docs-проекта.** Контекст: лендинг и docs
  деплоятся независимо. Анализ: отдельные проекты Pages дают независимые
  build-логи, custom domains и preview URLs; объединение в один проект
  усложнило бы конфигурацию без выгоды. Confidence: **high**.
