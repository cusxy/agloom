# Загрузка плагинов

Ключевые слова «ТРЕБУЕТСЯ», «ЗАПРЕЩАЕТСЯ», «ДОЛЖЕН», «НЕ ДОЛЖЕН», «СЛЕДУЕТ»,
«НЕ СЛЕДУЕТ», «МОЖЕТ» и «НЕОБЯЗАТЕЛЬНО» в этом документе толкуются
в соответствии с [RFC 2119](https://tools.ietf.org/html/rfc2119).

Данная спецификация описывает механизм загрузки плагинов — объявление
в конфигурационном файле, обнаружение из файловой системы и интеграцию
в пайплайн транспиляции. Спецификация является связующим звеном между
манифестом плагина (см. `docs/specs/plugin-manifest.md` — что плагин
собой представляет) и моделью слоёв (см. `docs/specs/layer-model.md` —
как слои объединяются).

## Терминология

- **Плагин (plugin)** — внешний проект, структурированный как Agloom-проект,
  содержащий `plugin.yml` (манифест). Плагин предоставляет инструкции,
  навыки, агенты и overlay-файлы, которые применяются как слой
  при транспиляции.
- **Локальный проект** — текущий проект, в котором выполняется
  команда `transpile`. Всегда применяется последним слоем
  с наивысшим приоритетом.

## Расширение формата конфигурационного файла

Формат файла `.agloom/config.yml`
(см. `docs/specs/config.md` § Формат файла) расширяется
опциональным полем верхнего уровня:

- `plugins` (array\<string>, опционально) — список путей
  к директориям плагинов. Каждый элемент ДОЛЖЕН быть строкой,
  содержащей путь к директории плагина. Пути МОГУТ быть
  относительными (разрешаются относительно корня проекта)
  или абсолютными. Массив МОЖЕТ быть пустым
  (эквивалентно отсутствию поля). Порядок элементов определяет
  порядок применения плагинов при транспиляции.

Пример содержимого:

```yaml
adapters:
  - claude
  - opencode
plugins:
  - ../shared-config
  - ../team-standards
```

При отсутствии поля `plugins` поведение ДОЛЖНО быть идентично
текущему (без плагинов). Это обеспечивает обратную совместимость.

## Расширение процедуры Load Config

Процедура Load Config (см. `docs/specs/config.md`
§ Процедура Load Config) расширяется обработкой поля `plugins`.

**Новые шаги:**

После шага 4 (валидация адаптеров):

5\. Проверить, содержит ли результат парсинга поле `plugins`.
6\. Если `plugins` присутствует — проверить, что значение является
массивом строк.

**Новые расширения:**

5a. Поле `plugins` отсутствует → значение `pluginPaths` равно `null`
(плагины не объявлены).

6a. Значение `plugins` не является массивом или содержит
нестроковые элементы →
`Error("Invalid config: 'plugins' must be an array of strings.")`.

**Изменения в результате:**

К существующему результату добавляется:

- `pluginPaths` (array\<string> | null) — список путей к плагинам
  из конфига, или `null` если поле `plugins` отсутствует.

## Тип ResolvedPlugin

- `name` (string) — имя плагина из манифеста
  (см. `docs/specs/plugin-manifest.md`).
- `path` (string) — абсолютный путь к директории плагина.
- `manifest` (PluginManifest) — распарсированный манифест плагина
  (см. `docs/specs/plugin-manifest.md`).

## Процедура Resolve Plugins (cli:procedure)

Разрешение и валидация списка плагинов из конфигурации. Вызывается
командой `transpile` после загрузки конфига.

**Вход:**

- `pluginPaths` (array\<string>, обязательно) — список путей
  к директориям плагинов из конфигурационного файла.
- `projectRoot` (string, обязательно) — абсолютный путь к корню проекта.

**Поведение:**

1. Инициализировать пустой массив `resolved` для результатов
   и пустую карту `nameToPath: Record<string, string>`
   для обнаружения дубликатов.
2. Для каждого `pluginPath` из `pluginPaths` в порядке объявления:
   2.1. Разрешить путь: если `pluginPath` является относительным —
   вычислить абсолютный путь относительно `projectRoot`.
   Если абсолютный — использовать как есть.
   2.2. Проверить, что разрешённый путь указывает на существующую
   директорию.
   2.3. Прочитать файл `plugin.yml` из корня разрешённого пути.
   2.4. Распарсить содержимое файла как YAML.
   2.5. Валидировать манифест
   (см. `docs/specs/plugin-manifest.md`).
   2.6. Извлечь значение поля `name` из манифеста.
   2.7. Проверить, что `name` отсутствует в `nameToPath`.
   2.8. Добавить `name` → `абсолютный путь` в `nameToPath`.
   2.9. Добавить `ResolvedPlugin` с `name`, `path` (абсолютный)
   и `manifest` в массив `resolved`.
3. Вернуть `resolved`.

**Расширения:**

2.2a. Разрешённый путь не существует →
`Error("Plugin path not found: '{абсолютный путь}'.")`.

2.2b. Разрешённый путь существует, но не является директорией →
`Error("Plugin path is not a directory: '{абсолютный путь}'.")`.

2.3a. Файл `plugin.yml` не существует в директории плагина →
`Error("Plugin manifest not found: '{абсолютный путь}/plugin.yml'.")`.

2.4a. Содержимое файла не является валидным YAML →
`Error("Invalid plugin manifest at '{абсолютный путь}/plugin.yml': {parseErrorMessage}.")`.

2.5a. Манифест не прошёл валидацию →
`Error("Invalid plugin manifest at '{абсолютный путь}/plugin.yml': {validationErrorMessage}.")`.

2.7a. `name` уже присутствует в `nameToPath` →
`Error("Duplicate plugin name '{name}': declared at '{nameToPath[name]}' and '{абсолютный путь}'.")`.

**Результат:**

- `plugins` (array\<ResolvedPlugin>) — упорядоченный список
  разрешённых плагинов в порядке объявления.

## Расширение процедуры «Шаг транспиляции» (cli:procedure)

Процедура «Шаг транспиляции» (см. `docs/specs/cli.md`
§ Шаг транспиляции) расширяется опциональным параметром
для разделения discover/transform и write.

**Новые параметры:**

К существующим параметрам ТРЕБУЕТСЯ добавить:

- `sourceRoot` (string, опционально, default: значение `projectRoot`) —
  абсолютный путь к корню источника для discover и transform.
  Если передан, транспилер создаётся с `sourceRoot` вместо
  `projectRoot`:
  `transpilerFactory({ projectRoot: sourceRoot, adapters: [adapter], agloomDir: "." })`.
  Запись результатов (`writeResults`) ДОЛЖНА выполняться
  в `projectRoot` (не в `sourceRoot`). Для этого `writeResults`
  вызывается с `projectRoot` в качестве целевого корня:
  `transpiler.writeResults(transpileResults, { targetRoot: projectRoot })`.
- `agloomDir` (string, опционально, default: `".agloom"`) —
  относительный путь к директории agloom внутри корня проекта.
  Транспилер использует `agloomDir` для построения путей discover
  (например, `path.join(projectRoot, agloomDir, "skills")`).
  При наличии `sourceRoot` значение ДОЛЖНО быть `"."`,
  потому что плагины хранят `skills/`, `agents/` на верхнем уровне
  (без `.agloom/` prefix). При отсутствии `sourceRoot`
  параметр не передаётся, и транспилер использует значение
  по умолчанию `".agloom"`.

**Изменения в поведении:**

Шаг 1 изменяется:

1. Создать экземпляр транспилера вызовом
   `transpilerFactory({ projectRoot: sourceRoot ?? projectRoot, adapters: [adapter], agloomDir })`.
   Если `sourceRoot` передан, `agloomDir` ДОЛЖЕН быть `"."`.
   Если `sourceRoot` не передан, `agloomDir` не передаётся
   (транспилер использует значение по умолчанию `".agloom"`).

Шаг 3 изменяется:

3. Вызвать `transpiler.writeResults(transpileResults, { targetRoot: projectRoot })`,
   получив `writeResult`. Если `sourceRoot` не передан,
   `targetRoot` совпадает с `projectRoot` транспилера
   и поведение идентично текущему.

## Расширение команды transpile (cli:command-ext)

Команда `transpile` (см. `docs/specs/cli.md` § Команда transpile)
расширяется обработкой плагинов.

**Новые шаги:**

После шага 3 (Resolve Adapters from CLI Args) и перед шагом 4
(цикл по записям):

3.1. Извлечь `pluginPaths` из результата Load Config
(выполненного внутри Resolve Adapters from CLI Args).
3.2. Если `pluginPaths` не равен `null` и не является пустым массивом —
выполнить процедуру Resolve Plugins
(см. § Процедура Resolve Plugins)
с `pluginPaths` и `projectRoot`.
3.3. Если `pluginPaths` равен `null` или является пустым массивом —
установить `plugins` в пустой массив.

**Изменения в шаге 4 (цикл по записям):**

Шаг 4 оригинальной спецификации (цикл для каждой записи
из полученного списка адаптеров) расширяется. Для каждой записи
адаптера ТРЕБУЕТСЯ выполнить транспиляцию всех источников
и одну операцию overlay в следующем порядке:

4.1. Отобразить заголовок с spinner.
4.2. Для каждого плагина из `plugins` в порядке объявления:
4.2.1. Выполнить шаг транспиляции "Instructions"
с адаптером `entry.instructions`, `projectRoot`
и `sourceRoot` = `plugin.path`.
4.2.2. Выполнить шаг транспиляции "Skills"
с адаптером `entry.skills`, `projectRoot`
и `sourceRoot` = `plugin.path`.
4.2.3. Выполнить шаг транспиляции "Agents"
с адаптером `entry.agents`, `projectRoot`
и `sourceRoot` = `plugin.path`.
4.3. Выполнить шаг транспиляции "Instructions"
с адаптером `entry.instructions` и локальным `projectRoot`
(без `sourceRoot`).
4.4. Выполнить шаг транспиляции "Skills"
с адаптером `entry.skills` и локальным `projectRoot`
(без `sourceRoot`).
4.5. Выполнить шаг транспиляции "Agents"
с адаптером `entry.agents` и локальным `projectRoot`
(без `sourceRoot`).
4.6. Сформировать массив `layers` (см. § Формирование массива layers).
4.7. Выполнить операцию overlay
(см. `docs/specs/layer-model.md` § Рефакторинг операции overlay)
с `entry`, `projectRoot`, `variables` и `layers`.
4.8. Отобразить результаты шагов в TUI.

Результаты шагов транспиляции плагинов (4.2.1–4.2.3)
и локального проекта (4.3–4.5) ТРЕБУЕТСЯ агрегировать
в единый набор `TranspilerStepOutcome` для отображения.
Для каждого типа шага (Instructions, Skills, Agents)
значение `writtenCount` ДОЛЖНО быть суммой `writtenCount`
по всем источникам (плагины + локальный проект). Значение `errors`
ДОЛЖНО быть конкатенацией массивов `errors` по всем источникам.
Результат шага Overlay (4.7) отображается как единый
`TranspilerStepOutcome`.

**Новые расширения:**

3.2a. Resolve Plugins вернул ошибку → отобразить сообщение ошибки;
процесс завершается с exit code 1.

**Изменения в exit codes:**

Exit code учитывает ошибки процедуры Resolve Plugins
наравне с ошибками Resolve Adapters from CLI Args.

## Формирование массива layers

Каждый разрешённый плагин и локальный проект формируют записи
`LayerSource` (см. `docs/specs/layer-model.md` § Тип LayerSource)
для единственного вызова операции overlay per-adapter.

Формирование массива `layers`:

1. Для каждого плагина из `plugins` в порядке объявления создать
   `LayerSource` с `id` = `plugin.name` и `overlayDir` =
   `<plugin.path>/overlays/<entry.id>/`.
2. Создать `LayerSource` для локального проекта с `id` = `"local"`
   и `overlayDir` = `<projectRoot>/.agloom/overlays/<entry.id>/`.

Массив `layers` передаётся в операцию overlay
(см. `docs/specs/layer-model.md`
§ Рефакторинг операции overlay), которая обрабатывает все слои
за один проход с deep merge / override стратегиями.

## Интеграция с транспилерами

Транспилеры (Instructions, Skills, Agents) при обработке плагина
вызываются с параметрами `sourceRoot` = `plugin.path`
и `agloomDir` = `"."`. Транспилер обнаруживает и обрабатывает
файлы относительно `sourceRoot`, а записывает результаты
в `projectRoot` (локальный проект).

Параметр `agloomDir` определяет относительный путь от корня
проекта к директории agloom. Транспилеры Skills и Agents
используют `agloomDir` для построения пути discover
(например, `path.join(projectRoot, agloomDir, "skills")`).
При значении `"."` транспилер обнаруживает файлы непосредственно
в `<sourceRoot>/skills/` и `<sourceRoot>/agents/`, что
соответствует структуре плагина
(см. `docs/specs/plugin-manifest.md`).

При обработке плагина:

- Instructions-транспилер обнаруживает `AGLOOM.md`
  в `<plugin.path>/AGLOOM.md`.
- Skills-транспилер обнаруживает навыки
  в `<plugin.path>/skills/` (через `agloomDir: "."`).
- Agents-транспилер обнаруживает агентов
  в `<plugin.path>/agents/` (через `agloomDir: "."`).

Записанные файлы размещаются в целевой директории локального
проекта (`projectRoot`). Разделение discover/transform
и write обеспечивается параметрами `sourceRoot` и `agloomDir`
расширенной процедуры «Шаг транспиляции»
(см. § Расширение процедуры «Шаг транспиляции»).

При обработке локального проекта `sourceRoot` не передаётся,
`agloomDir` не передаётся (default `".agloom"`). Транспилер
использует `projectRoot` для discover, transform и write —
поведение идентично текущему.

Данная спецификация описывает только контракт передачи параметра
`agloomDir` из процедуры «Шаг транспиляции» в фабрику транспилера.
Внутренняя реализация discover-функций транспилеров Skills и Agents
(использование `agloomDir` для построения путей) является scope
спецификаций соответствующих транспилеров.

## Стратегия обработки ошибок

Обработка ошибок плагинов ДОЛЖНА следовать двухуровневой
стратегии. Уровни различаются по этапу жизненного цикла
плагина и по последствиям ошибки.

### Уровень 1 — загрузка и валидация (fail-fast)

Ошибки на этапе загрузки и валидации плагинов (процедура
Resolve Plugins, см. § Процедура Resolve Plugins) ДОЛЖНЫ
останавливать всю транспиляцию. Процедура Resolve Plugins
ДОЛЖНА выбрасывать `Error` при первой обнаруженной ошибке,
без попытки продолжить обработку оставшихся плагинов.

К ошибкам уровня 1 относятся:

- Путь плагина не существует (расширение 2.2a).
- Путь не является директорией (расширение 2.2b).
- Файл `plugin.yml` отсутствует (расширение 2.3a).
- Манифест не является валидным YAML (расширение 2.4a).
- Манифест не прошёл валидацию (расширение 2.5a).
- Дублирование имён плагинов (расширение 2.7a).

Обоснование: пользователь явно объявил плагин в `config.yml`.
Если плагин невалиден, это конфигурационная ошибка. Результат
транспиляции без объявленного плагина будет неполным,
поэтому продолжение транспиляции ЗАПРЕЩАЕТСЯ.

Команда `transpile` обрабатывает ошибку уровня 1
в расширении 3.2a (см. § Расширение команды transpile):
отобразить сообщение ошибки, завершить процесс с exit code 1.

### Уровень 2 — применение (tolerant)

Ошибки на этапе применения валидного плагина (транспиляция
файлов и overlay) НЕ ДОЛЖНЫ останавливать процесс.
Каждая ошибка отдельного файла ДОЛЖНА быть добавлена
в массив `errors` соответствующего `TranspilerStepOutcome`,
после чего обработка оставшихся файлов ДОЛЖНА продолжиться.

К ошибкам уровня 2 относятся:

- Ошибка парсинга файла при merge
  (см. `docs/specs/layer-model.md` § Новые расширения, 2.7a).
- Ошибка интерполяции файла
  (см. `docs/specs/layer-model.md` § Новые расширения, 2.6a).
- Ошибка сериализации или записи файла
  (см. `docs/specs/layer-model.md` § Новые расширения, 3.3a).
- Исключение в `transpile()` транспилера
  (см. `docs/specs/cli.md` § Шаг транспиляции, расширение 2a).
- Ошибки записи в `writeResults`
  (см. `docs/specs/cli.md` § Шаг транспиляции, шаг 5).

Данная стратегия соответствует модели частичного успеха
(partial success), принятой в операции overlay
(см. `docs/specs/provider-overlay.md` § Операция overlay)
и в процедуре «Шаг транспиляции»
(см. `docs/specs/cli.md` § Шаг транспиляции).

Итоговый exit code определяется наличием ошибок уровня 2:
если массив `errors` хотя бы одного `TranspilerStepOutcome`
непуст — exit code 1 (см. `docs/specs/cli.md` § Exit codes).

## Обратная совместимость

При отсутствии поля `plugins` в `.agloom/config.yml`:

- Процедура Load Config возвращает `pluginPaths: null`.
- Шаги 3.1–3.3 расширения команды `transpile` устанавливают
  `plugins` в пустой массив.
- Цикл в шаге 4.2 не выполняется (пустой массив).
- Шаги 4.3–4.5 выполняются для локального проекта.
- Массив `layers` (шаг 4.6) содержит единственный `LayerSource`
  с `id` = `"local"`.
- Операция overlay (шаг 4.7) обрабатывает один слой.

Поведение ДОЛЖНО быть идентично текущей реализации
(см. `docs/specs/cli.md` § Команда transpile).

## Вне scope

Следующие аспекты НЕ ВХОДЯТ в scope данной спецификации:

- Формат манифеста плагина (`plugin.yml`) — см. `docs/specs/plugin-manifest.md`.
- Стратегии слияния файлов (deep merge, override) — см. `docs/specs/layer-model.md`.
- Загрузка плагинов из Git-репозиториев — итерация 2.
- Кэширование плагинов — итерация 2.
