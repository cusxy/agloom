# Patch-механизм

Ключевые слова "ТРЕБУЕТСЯ", "ЗАПРЕЩАЕТСЯ", "ДОЛЖЕН", "НЕ ДОЛЖЕН", "СЛЕДУЕТ",
"НЕ СЛЕДУЕТ", "МОЖЕТ" и "НЕОБЯЗАТЕЛЬНО" в этом документе толкуются
в соответствии с [RFC 2119](https://tools.ietf.org/html/rfc2119).

Данная спецификация расширяет модель слоёв
(см. `docs/specs/layer-model.md`) третьей стратегией применения файлов --
patch. Patch предназначен для точечной модификации structured-файлов
(массивов, отдельных ключей) без полной замены (override) и без
ограничений deep merge (массивы заменяются целиком, нет способа
добавить элемент).

## Терминология

- **Patch** -- стратегия применения файла: выполнение набора
  декларативных операций над текущим состоянием целевого файла.
  Patch-файл содержит структуру, повторяющую иерархию целевого
  файла, с маркерами операций в узлах, требующих модификации.
- **Маркер операции** -- ключ объекта с префиксом `$`, обозначающий
  конкретную операцию (`$append`, `$prepend`, `$remove`, `$set`,
  `$unset`, `$merge`, `$mergeBy`, `$insertAt`). Маркеры ЗАПРЕЩАЕТСЯ
  интерпретировать как обычные ключи данных.
- **Целевой файл** -- файл, к которому применяется patch.
  Определяется по имени patch-файла после удаления суффикса
  `.patch` (аналогично `.override`).

## Конвенция `.patch`

### Формат имени

Patch-файл ДОЛЖЕН иметь формат имени
`<basename>.patch.<ext>`, где `<ext>` -- расширение merge-eligible
формата (`.json`, `.jsonc`, `.yaml`, `.yml`, `.toml`).

Примеры:

- `settings.patch.yaml` -- patch для целевого файла `settings.yaml`
  (или `settings.json`, см. ниже).
- `tsconfig.patch.json` -- patch для целевого файла `tsconfig.json`.

### Обнаружение суффикса

Суффикс `.patch` ДОЛЖЕН располагаться непосредственно перед
финальным расширением файла. Обнаружение выполняется
по паттерну `<basename>.patch.<ext>`.

### Удаление суффикса при записи

При определении целевого пути суффикс `.patch` ТРЕБУЕТСЯ удалить
из имени файла. Файл `settings.patch.yaml` в слое ДОЛЖЕН
применяться к целевому файлу `settings.yaml`.

### Область применения суффикса

Суффикс `.patch` имеет практическое значение только для файлов
merge-eligible форматов (`.json`, `.jsonc`, `.yaml`, `.yml`,
`.toml`). Если расширение patch-файла НЕ входит в список
merge-eligible -- файл ТРЕБУЕТСЯ обработать как обычный override
(суффикс `.patch` удаляется при записи, содержимое копируется
без интерпретации маркеров).

### Взаимоисключаемость с `.override`

Файл НЕ ДОЛЖЕН одновременно содержать суффиксы `.patch`
и `.override`. При обнаружении файла с обоими суффиксами
(например, `settings.patch.override.json`
или `settings.override.patch.json`) система ДОЛЖНА добавить
сообщение об ошибке в `errors` и пропустить файл.

## Определение стратегии для конкретного файла

Определение стратегии (см. `docs/specs/layer-model.md`
§ Определение стратегии для конкретного файла) расширяется
третьим вариантом. Полный алгоритм:

1. Если имя файла содержит суффикс `.override` перед расширением --
   стратегия override.
2. Если имя файла содержит суффикс `.patch` перед расширением
   И расширение входит в список merge-eligible -- стратегия patch.
3. Если расширение файла входит в список merge-eligible
   и суффиксы `.override` / `.patch` отсутствуют -- стратегия
   overlay (merge).
4. Иначе -- стратегия override.

## Маркеры операций

Маркер операции -- ключ объекта с префиксом `$`. Система
ДОЛЖНА поддерживать следующие маркеры:

### `$append`

Добавляет элементы в конец массива.

**Тип значения:** array (обязательно).

**Целевое поле:** ДОЛЖНО быть массивом.

**Поведение:** каждый элемент из значения `$append` ТРЕБУЕТСЯ
добавить в конец целевого массива в порядке их следования.

**Пример:**

Текущее состояние:

```json
{ "editor": { "rulers": [80, 120] } }
```

Patch:

```yaml
editor:
  rulers:
    $append: [140]
```

Результат:

```json
{ "editor": { "rulers": [80, 120, 140] } }
```

### `$prepend`

Добавляет элементы в начало массива.

**Тип значения:** array (обязательно).

**Целевое поле:** ДОЛЖНО быть массивом.

**Поведение:** каждый элемент из значения `$prepend` ТРЕБУЕТСЯ
вставить в начало целевого массива. Порядок элементов из значения
`$prepend` ДОЛЖЕН сохраняться: первый элемент `$prepend`
становится первым элементом результата.

**Пример:**

Текущее состояние:

```json
{ "plugins": ["existing-plugin"] }
```

Patch:

```yaml
plugins:
  $prepend: [first-plugin, second-plugin]
```

Результат:

```json
{ "plugins": ["first-plugin", "second-plugin", "existing-plugin"] }
```

### `$remove`

Удаляет элементы из массива по значению.

**Тип значения:** array (обязательно).

**Целевое поле:** ДОЛЖНО быть массивом.

**Поведение:** для каждого элемента из значения `$remove`
система ДОЛЖНА удалить все вхождения этого элемента
из целевого массива. Сравнение ДОЛЖНО выполняться
по строгому равенству (===) для скалярных значений (строки,
числа, булевы). Для объектов и массивов внутри целевого массива
сравнение ДОЛЖНО выполняться по глубокому равенству (deep equal).

Если элемент из `$remove` не найден в целевом массиве --
элемент пропускается без ошибки (silent no-op).

**Пример:**

Текущее состояние:

```json
{ "files": { "exclude": ["node_modules", "dist", ".cache"] } }
```

Patch:

```yaml
files:
  exclude:
    $remove: [node_modules, .cache]
```

Результат:

```json
{ "files": { "exclude": ["dist"] } }
```

### `$set`

Устанавливает значение ключа.

**Тип значения:** любой (обязательно).

**Целевое поле:** любой тип или отсутствует.

**Поведение:** значение `$set` ТРЕБУЕТСЯ установить как значение
родительского ключа, заменяя текущее значение целиком. Если ключ
не существует -- он создаётся.

Маркер `$set` эквивалентен обычному присвоению в merge,
но используется в контексте patch-файла, где обычные ключи
интерпретируются как навигация по структуре (см. § Алгоритм
применения patch).

**Пример:**

Текущее состояние:

```json
{ "editor": { "fontSize": 14, "tabSize": 2 } }
```

Patch:

```yaml
editor:
  fontSize:
    $set: 16
```

Результат:

```json
{ "editor": { "fontSize": 16, "tabSize": 2 } }
```

### `$unset`

Удаляет ключи из объекта.

**Тип значения:** array\<string> (обязательно). Каждый элемент --
имя ключа для удаления.

**Целевое поле:** ДОЛЖНО быть объектом (родительский узел).

**Поведение:** для каждого имени ключа из значения `$unset`
система ДОЛЖНА удалить соответствующий ключ из родительского
объекта. Если ключ не существует -- элемент пропускается без
ошибки (silent no-op).

`$unset` предоставляет механизм удаления ключей, работающий
во всех форматах, включая TOML (где `null` не поддерживается).

**Пример:**

Текущее состояние:

```json
{ "editor": { "fontSize": 14, "wordWrap": "on", "minimap": true } }
```

Patch:

```yaml
editor:
  $unset: [wordWrap, minimap]
```

Результат:

```json
{ "editor": { "fontSize": 14 } }
```

### `$merge`

Выполняет deep merge вложенного объекта.

**Тип значения:** object (обязательно).

**Целевое поле:** ДОЛЖНО быть объектом или отсутствовать.
Если целевое поле отсутствует -- оно создаётся как пустой
объект перед merge.

**Поведение:** значение `$merge` ТРЕБУЕТСЯ объединить
с текущим значением родительского ключа по правилам deep merge
(см. `docs/specs/layer-model.md` § Алгоритм deep merge).
`$merge` позволяет комбинировать обычный deep merge
с другими patch-операциями в одном файле.

**Пример:**

Текущее состояние:

```json
{ "editor": { "fontSize": 14, "tabSize": 2, "rulers": [80] } }
```

Patch:

```yaml
editor:
  $merge:
    fontSize: 16
    tabSize: 4
```

Результат:

```json
{ "editor": { "fontSize": 16, "tabSize": 4, "rulers": [80] } }
```

### `$mergeBy`

Merge массива объектов по ключевому полю (аналог Kustomize
strategic merge patch и Ansible `lists_mergeby`).

**Тип значения:** object (обязательно) с полями:

- `key` (string, обязательно) -- имя поля, по которому
  выполняется сопоставление.
- `items` (array\<object>, обязательно) -- массив объектов
  для merge.

**Целевое поле:** ДОЛЖНО быть массивом объектов.

**Поведение:**

1. Для каждого объекта из `items` найти в целевом массиве
   элемент, у которого значение поля `key` совпадает
   со значением поля `key` incoming-объекта.
2. Если элемент найден -- выполнить deep merge целевого
   элемента с incoming-объектом по правилам deep merge
   (см. `docs/specs/layer-model.md` § Алгоритм deep merge).
3. Если элемент НЕ найден -- добавить incoming-объект в конец
   целевого массива (append).
4. Порядок существующих элементов ДОЛЖЕН сохраняться.
5. Новые элементы (не нашедшие пару) добавляются в конец
   в порядке их следования в `items`.

**Расширения:**

1a. Элемент целевого массива не является объектом -- пропустить
элемент при сопоставлении (не рассматривать как кандидата
для merge).

Ошибки валидации значений и целевого типа -- см. § Валидация
значений маркеров.

**Пример:**

Текущее состояние:

```json
{
  "tasks": [
    { "name": "build", "command": "tsc", "args": ["--strict"] },
    { "name": "test", "command": "vitest" }
  ]
}
```

Patch:

```yaml
tasks:
  $mergeBy:
    key: name
    items:
      - name: build
        args: ["--strict", "--noEmit"]
      - name: lint
        command: eslint
```

Результат:

```json
{
  "tasks": [
    { "name": "build", "command": "tsc", "args": ["--strict", "--noEmit"] },
    { "name": "test", "command": "vitest" },
    { "name": "lint", "command": "eslint" }
  ]
}
```

### `$insertAt`

Вставка элементов в массив по индексу.

**Тип значения:** object (обязательно) с полями:

- `index` (integer, обязательно) -- позиция вставки (0-based).
  Отрицательные значения считаются от конца
  (`-1` = перед последним элементом).
- `items` (array, обязательно) -- элементы для вставки.

**Целевое поле:** ДОЛЖНО быть массивом.

**Поведение:**

1. Нормализовать `index`: если отрицательный --
   `max(0, length + index)`.
2. Если `index` > `length` -- clamp до `length`
   (вставка в конец).
3. Вставить все элементы `items` начиная с позиции `index`,
   сдвигая существующие элементы вправо.
4. Порядок элементов `items` ДОЛЖЕН сохраняться.

**Расширения:**

Нет расширений.

**Пример:**

Текущее состояние:

```json
{ "plugins": ["a", "b", "c"] }
```

Patch:

```yaml
plugins:
  $insertAt:
    index: 1
    items: [x, y]
```

Результат:

```json
{ "plugins": ["a", "x", "y", "b", "c"] }
```

## Комбинация маркеров в одном узле

Один узел (объект) в patch-файле МОЖЕТ содержать несколько
маркеров одновременно. При наличии нескольких маркеров в одном
узле они ДОЛЖНЫ применяться в следующем фиксированном порядке:

1. `$unset` -- сначала удалить ключи.
2. `$merge` -- затем выполнить deep merge.
3. `$mergeBy` -- затем merge массива по ключу.
4. `$set` -- затем установить значение (перезаписывает результат
   предыдущих операций для данного ключа).
5. `$remove` -- затем удалить элементы из массива.
6. `$insertAt` -- затем вставить по позиции.
7. `$prepend` -- затем добавить в начало массива.
8. `$append` -- затем добавить в конец массива.

### Ограничения комбинаций

Маркеры `$set` и `$merge` в одном узле ЗАПРЕЩАЮТСЯ -- `$set`
заменяет значение целиком, а `$merge` выполняет слияние. При
обнаружении обоих маркеров в одном узле система ДОЛЖНА добавить
сообщение об ошибке в `errors` и пропустить файл.

Маркеры `$set` и `$mergeBy` в одном узле ЗАПРЕЩАЮТСЯ -- `$set`
заменяет значение целиком, что делает `$mergeBy` бессмысленным.
При обнаружении обоих маркеров в одном узле система ДОЛЖНА
добавить сообщение об ошибке в `errors` и пропустить файл.

Маркеры `$mergeBy` и `$merge` в одном узле ДОПУСКАЮТСЯ --
`$merge` применяется к объекту-родителю, `$mergeBy` к массиву-значению.
Маркеры применяются в порядке, определённом выше.

Маркеры `$insertAt` с `$append` и/или `$prepend` в одном узле
ДОПУСКАЮТСЯ. Маркеры применяются в порядке, определённом выше:
`$insertAt` -> `$prepend` -> `$append`.

Маркеры `$append`, `$prepend` и `$remove` МОГУТ присутствовать
в одном узле одновременно и применяются в порядке, определённом
выше.

## Алгоритм применения patch (cli:procedure)

### Процедура Apply Patch

Процедура применения patch-операций к текущему состоянию файла.

**Вход:**

- `base` (object | undefined, обязательно) -- текущее состояние
  целевого файла (распарсенное). Если файл не существует --
  `undefined`.
- `patch` (object, обязательно) -- распарсенное содержимое
  patch-файла.

**Поведение:**

1. Если `base` имеет значение `undefined` -- инициализировать
   `base` как пустой объект `{}`.
2. Для каждого ключа `key` в `patch`:
3. Если `key` является маркером операции (начинается с `$`) --
   выполнить операцию маркера над `base`
   (см. § Применение маркера к узлу).
4. Если `key` НЕ является маркером операции -- проверить,
   содержит ли значение `patch[key]` вложенные маркеры.
5. Если `patch[key]` является объектом и содержит хотя бы один
   ключ с префиксом `$` -- рекурсивно применить процедуру
   Apply Patch к `base[key]` (как `base`) и `patch[key]`
   (как `patch`).
6. Если `patch[key]` является объектом и НЕ содержит ключей
   с префиксом `$` -- рекурсивно применить процедуру Apply Patch
   к `base[key]` (как `base`) и `patch[key]` (как `patch`)
   для обработки глубоко вложенных маркеров.
7. Если `patch[key]` НЕ является объектом -- пропустить ключ
   (в patch-файле не-объектные значения без маркеров не имеют
   эффекта; для присвоения значения ТРЕБУЕТСЯ использовать
   `$set`).

**Расширения:**

3a. Неизвестный маркер (ключ начинается с `$`, но не входит
в список поддерживаемых маркеров) -- добавить сообщение
`"Unknown patch marker '{key}' in {path}"` в `errors`,
пропустить файл.

**Результат:**

- `result` (object) -- модифицированный объект `base`.

### Применение маркера к узлу

Процедура применения одного маркера к текущему узлу `base`.

**Вход:**

- `base` (any, обязательно) -- текущее значение узла.
- `marker` (string, обязательно) -- имя маркера (`$append`,
  `$prepend`, `$remove`, `$set`, `$unset`, `$merge`, `$mergeBy`,
  `$insertAt`).
- `value` (any, обязательно) -- значение маркера из patch-файла.
- `parentKey` (string, обязательно) -- ключ родительского объекта,
  в котором находится `base`.
- `parent` (object, обязательно) -- родительский объект.

**Поведение:**

Перед выполнением каждого шага система ДОЛЖНА выполнить валидацию
типа значения маркера и целевого типа (см. § Валидация значений
маркеров). При ошибке валидации -- добавить сообщение в `errors`,
пропустить файл.

1. Если `marker` равен `$set` -- установить `parent[parentKey]`
   равным `value`.
2. Если `marker` равен `$unset` -- для каждого имени ключа
   из `value` удалить `base[name]`.
3. Если `marker` равен `$merge` -- выполнить deep merge
   `base` и `value` (по правилам
   `docs/specs/layer-model.md` § Алгоритм deep merge).
   Установить `parent[parentKey]` равным результату. Если
   `base` не является объектом и не является `undefined` --
   установить `parent[parentKey]` равным `value`.
4. Если `marker` равен `$mergeBy` -- для каждого объекта
   из `value.items` найти в `base` элемент с совпадающим
   значением поля `value.key`. Если найден -- выполнить deep merge
   целевого элемента с incoming-объектом. Если не найден --
   добавить incoming-объект в конец `base`.
5. Если `marker` равен `$remove` -- для каждого элемента
   из `value` удалить все вхождения из `base`.
6. Если `marker` равен `$insertAt` -- нормализовать `value.index`,
   вставить элементы `value.items` начиная с нормализованной
   позиции (см. § `$insertAt` Поведение).
7. Если `marker` равен `$prepend` -- вставить элементы `value`
   в начало `base`.
8. Если `marker` равен `$append` -- добавить элементы `value`
   в конец `base`.

**Расширения:**

4d. Элемент целевого массива не является объектом -- пропустить
элемент при сопоставлении (не рассматривать как кандидата
для merge).

Ошибки валидации значений маркеров и целевых типов --
см. § Валидация значений маркеров.

**Результат:**

- Модифицированный `parent` с обновлённым `parent[parentKey]`.

## Обработка несуществующего целевого поля

При навигации по структуре (шаги 4--6 процедуры Apply Patch),
если `base[key]` не существует (`undefined`):

- Для маркера `$set` -- ключ создаётся с указанным значением.
- Для маркера `$merge` -- ключ создаётся как пустой объект `{}`,
  затем выполняется deep merge.
- Для маркера `$mergeBy` -- ключ создаётся как пустой массив `[]`,
  затем все элементы `items` добавляются как новые (append).
- Для маркеров `$append` и `$prepend` -- добавить сообщение-предупреждение
  `"Patch target field '{path}' does not exist, skipping"` в `errors`,
  пропустить операцию. Массив НЕ ДОЛЖЕН создаваться неявно.
- Для маркера `$insertAt` -- добавить сообщение-предупреждение
  `"Patch target field '{path}' does not exist, skipping"` в `errors`,
  пропустить операцию. Массив НЕ ДОЛЖЕН создаваться неявно.
- Для маркера `$remove` -- silent no-op (нечего удалять).
- Для маркера `$unset` -- silent no-op (нечего удалять).

## Валидация значений маркеров

Данная секция является каноническим источником всех ошибок
валидации для patch-маркеров. Описания маркеров (§ Маркеры
операций) и процедура «Применение маркера к узлу» ссылаются
на эту секцию.

### Валидация типа значения маркера

Перед выполнением операции система ДОЛЖНА проверить тип значения
маркера:

- `$append` -- значение ДОЛЖНО быть массивом. Если не массив --
  добавить сообщение `"$append value must be array at '{path}'"` в `errors`,
  пропустить файл.
- `$prepend` -- значение ДОЛЖНО быть массивом. Если не массив --
  добавить сообщение `"$prepend value must be array at '{path}'"` в `errors`,
  пропустить файл.
- `$remove` -- значение ДОЛЖНО быть массивом. Если не массив --
  добавить сообщение `"$remove value must be array at '{path}'"` в `errors`,
  пропустить файл.
- `$unset` -- значение ДОЛЖНО быть массивом строк. Если не массив
  или содержит не-строки -- добавить сообщение
  `"$unset value must be array of strings at '{path}'"` в `errors`,
  пропустить файл.
- `$merge` -- значение ДОЛЖНО быть объектом. Если не объект --
  добавить сообщение `"$merge value must be object at '{path}'"` в `errors`,
  пропустить файл.
- `$mergeBy` -- значение ДОЛЖНО быть объектом с полями `key` (string)
  и `items` (array). Если значение не является объектом -- добавить
  сообщение `"$mergeBy value must be object at '{path}'"` в `errors`,
  пропустить файл. Если `key` не является строкой -- добавить сообщение
  `"$mergeBy key must be string at '{path}'"` в `errors`, пропустить файл.
  Если `items` не является массивом -- добавить сообщение
  `"$mergeBy items must be array at '{path}'"` в `errors`, пропустить файл.
- `$insertAt` -- значение ДОЛЖНО быть объектом с полями `index` (integer)
  и `items` (array). Если значение не является объектом -- добавить
  сообщение `"$insertAt value must be object at '{path}'"` в `errors`,
  пропустить файл. Если `index` не является integer -- добавить сообщение
  `"$insertAt index must be integer at '{path}'"` в `errors`, пропустить файл.
  Если `items` не является массивом -- добавить сообщение
  `"$insertAt items must be array at '{path}'"` в `errors`, пропустить файл.
- `$set` -- допускается любой тип значения.

### Валидация целевого типа

При выполнении операции система ДОЛЖНА проверить тип целевого
узла (`base`):

- `$append` на не-массиве -- добавить сообщение
  `"$append requires array target at '{path}'"` в `errors`,
  пропустить файл.
- `$prepend` на не-массиве -- добавить сообщение
  `"$prepend requires array target at '{path}'"` в `errors`,
  пропустить файл.
- `$remove` на не-массиве -- добавить сообщение
  `"$remove requires array target at '{path}'"` в `errors`,
  пропустить файл.
- `$insertAt` на не-массиве -- добавить сообщение
  `"$insertAt requires array target at '{path}'"` в `errors`,
  пропустить файл.
- `$unset` на не-объекте -- добавить сообщение
  `"$unset requires object target at '{path}'"` в `errors`,
  пропустить файл.
- `$mergeBy` на не-массиве -- добавить сообщение
  `"$mergeBy requires array target at '{path}'"` в `errors`,
  пропустить файл.

### Валидация элементов `$mergeBy`

При обработке каждого элемента из `$mergeBy.items` система
ДОЛЖНА выполнить дополнительную валидацию:

- Элемент `items` не является объектом -- добавить сообщение
  `"$mergeBy items must contain objects at '{path}'"` в `errors`,
  пропустить файл.
- Элемент `items` не содержит поля, указанного в `key` --
  добавить сообщение
  `"$mergeBy item missing key field '{key}' at '{path}'"` в `errors`,
  пропустить файл.

**Новый шаг 2.9 (после шага 2.8):**

2.9. Если стратегия patch -- распарсить содержимое

2.9b. Парсинг существующего целевого файла завершился ошибкой --

## Взаимодействие со слоями

### Порядок применения

Patch-файл участвует в том же порядке слоёв, что и файлы
с merge/override стратегиями (см. `docs/specs/layer-model.md`
§ Порядок применения слоёв). Более поздний слой имеет более
высокий приоритет.

### Комбинация стратегий между слоями

Один слой МОЖЕТ содержать файл `settings.json` (стратегия merge),
а другой слой -- файл `settings.patch.yaml` (стратегия patch)
для того же целевого файла `settings.json`. Стратегии
применяются последовательно в порядке слоёв:

- Слой A содержит `settings.json` -- выполняется deep merge
  с текущим состоянием.
- Слой B содержит `settings.patch.yaml` -- выполняется patch
  над результатом слоя A.

### Формат patch-файла и целевого файла

Формат (расширение) patch-файла МОЖЕТ отличаться от формата
целевого файла. Например, patch-файл `tsconfig.patch.yaml`
МОЖЕТ применяться к целевому файлу `tsconfig.json`. Целевой файл
определяется по `targetRelativePath` (имя после удаления суффикса
`.patch`), а не по расширению patch-файла.

При несовпадении расширений patch-файла и целевого файла:

- Patch-файл парсится в соответствии со своим расширением
  (`.yaml` в данном примере).
- Целевой файл парсится в соответствии со своим расширением
  (`.json` в данном примере).
- Результат сериализуется в формат целевого файла.

### Взаимодействие с интерполяцией

Интерполяция переменных (см. `docs/specs/interpolation.md`)
ДОЛЖНА выполняться ПЕРЕД парсингом patch-файла, аналогично
поведению для merge/override
(см. `docs/specs/layer-model.md` § Взаимодействие
с интерполяцией).

## Обработка ошибок

Patch-механизм использует tolerant-стратегию (уровень 2):
при ошибке в отдельном файле или операции система продолжает
обработку оставшихся файлов, накапливая ошибки в массиве
`errors`.

Сводка поведения при ошибках:

| Ситуация                                                 | Поведение                                     |
| -------------------------------------------------------- | --------------------------------------------- |
| Невалидный patch-файл (ошибка парсинга)                  | Сообщение в `errors`, пропуск файла           |
| `$append`/`$prepend`/`$remove`/`$insertAt` на не-массиве | Сообщение в `errors`, пропуск файла           |
| `$unset`/`$merge` на не-объекте                          | Сообщение в `errors`, пропуск файла           |
| `$mergeBy` на не-массиве                                 | Сообщение в `errors`, пропуск файла           |
| `$mergeBy` item не содержит поля `key`                   | Сообщение в `errors`, пропуск файла           |
| `$mergeBy` item не является объектом                     | Сообщение в `errors`, пропуск файла           |
| `$mergeBy.key` не является строкой                       | Сообщение в `errors`, пропуск файла           |
| `$mergeBy.items` не является массивом                    | Сообщение в `errors`, пропуск файла           |
| `$insertAt.index` не является integer                    | Сообщение в `errors`, пропуск файла           |
| `$insertAt.items` не является массивом                   | Сообщение в `errors`, пропуск файла           |
| Невалидный тип значения маркера                          | Сообщение в `errors`, пропуск файла           |
| `$unset` несуществующего ключа                           | Silent no-op                                  |
| `$remove` несуществующего элемента                       | Silent no-op                                  |
| `$append`/`$prepend`/`$insertAt` на несуществующем поле  | Предупреждение в `errors`, пропуск операции   |
| `$mergeBy` на несуществующем поле                        | Создать `[]`, все items добавляются как новые |
| Неизвестный маркер (ключ с `$`, не в списке)             | Сообщение в `errors`, пропуск файла           |
| Одновременно `$set` и `$merge` в одном узле              | Сообщение в `errors`, пропуск файла           |
| Одновременно `$set` и `$mergeBy` в одном узле            | Сообщение в `errors`, пропуск файла           |
| Одновременно `.patch` и `.override` в имени файла        | Сообщение в `errors`, пропуск файла           |

## Вне scope

Следующие аспекты НЕ ВХОДЯТ в scope данной спецификации:

- Условные операции (применение маркера только при выполнении
  условия).
- Patch для не-merge-eligible форматов (`.md`, `.xml` и т.д.).
- RFC 6902 (JSON Patch) совместимость -- формат намеренно
  отличается для удобства ручного написания.
- Wildcard-паттерны в путях маркеров (применение операции
  ко всем элементам массива объектов).
