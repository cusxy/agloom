# Модель слоёв

Ключевые слова «ТРЕБУЕТСЯ», «ЗАПРЕЩАЕТСЯ», «ДОЛЖЕН», «НЕ ДОЛЖЕН», «СЛЕДУЕТ»,
«НЕ СЛЕДУЕТ», «МОЖЕТ» и «НЕОБЯЗАТЕЛЬНО» в этом документе толкуются
в соответствии с [RFC 2119](https://tools.ietf.org/html/rfc2119).

Данная спецификация формализует модель слоёв (layer model) — механизм
слияния конфигурационных файлов из нескольких источников (плагины
и локальный проект) при транспиляции. Модель заменяет текущую
файловую перезапись (см. `docs/specs/provider-overlay.md`) гибридной
стратегией: deep merge для структурированных данных и полная замена
для остальных форматов.

## Терминология

- **Слой (layer)** — единица конфигурации из одного источника
  (плагин или локальный проект). Каждый слой содержит набор файлов,
  которые применяются к целевой файловой структуре проекта.
- **Overlay (слияние)** — стратегия применения файла: deep merge
  структурированных данных с предыдущим значением по тому же пути.
  Применяется к файлам merge-eligible форматов
  (см. § Классификация файлов по стратегии слияния), если файл
  НЕ имеет суффикса `.override`.
- **Override (замена)** — стратегия применения файла: полная замена
  предыдущего значения по тому же пути. Применяется к текстовым,
  бинарным файлам и к файлам merge-eligible форматов с суффиксом
  `.override`.

## Классификация файлов по стратегии слияния

### Merge-eligible форматы (структурированные данные)

Файлы со следующими расширениями ТРЕБУЕТСЯ считать merge-eligible.
Сравнение расширения ДОЛЖНО быть case-insensitive:

- `.json`
- `.jsonc`
- `.yaml`
- `.yml`
- `.toml`

### Override-only форматы

Все файлы, расширение которых НЕ входит в список merge-eligible,
ТРЕБУЕТСЯ обрабатывать стратегией override (полная замена). Это
включает, но не ограничивается:

- `.md`, `.txt`, `.html`, `.svg` — текстовые файлы.
- `.xml` — структурированный формат, но объектная модель
  неоднозначна для deep merge.
- `.jsonl` — line-delimited JSON, НЕ является единой структурой.
- Бинарные файлы (изображения, архивы и т.д.).

### Определение стратегии для конкретного файла

Стратегия слияния для файла определяется следующим образом:

1. Если имя файла содержит суффикс `.override` перед расширением
   (например, `settings.override.json`) — стратегия override,
   независимо от расширения.
2. Если расширение файла входит в список merge-eligible
   и суффикс `.override` отсутствует — стратегия overlay (merge).
3. Иначе — стратегия override.

## Конвенция `.override`

Суффикс `.override` в имени файла ТРЕБУЕТСЯ интерпретировать
как явное указание стратегии полной замены для файлов merge-eligible
форматов.

### Обнаружение суффикса

Суффикс `.override` ДОЛЖЕН располагаться непосредственно перед
финальным расширением файла. Обнаружение выполняется
по паттерну `<basename>.override.<ext>`.

Примеры:

- `settings.override.json` — суффикс обнаружен, стратегия override.
- `settings.json` — суффикс не обнаружен, стратегия overlay (merge).
- `readme.override.md` — суффикс обнаружен, но `.md` не является
  merge-eligible, поэтому стратегия override (как и без суффикса).

### Удаление суффикса при записи

При копировании файла с суффиксом `.override` в целевой путь
суффикс ТРЕБУЕТСЯ удалить из имени файла. Файл
`settings.override.json` в слое ДОЛЖЕН быть записан как
`settings.json` в целевой директории.

### Область применения суффикса

Суффикс `.override` имеет практическое значение только для файлов
merge-eligible форматов (`.json`, `.jsonc`, `.yaml`, `.yml`,
`.toml`). Для override-only форматов (`.md`, `.txt`, `.xml`,
бинарные) суффикс допускается, но не изменяет поведения —
стратегия для таких файлов всегда override. Суффикс всё равно
ТРЕБУЕТСЯ удалить при записи.

## Алгоритм deep merge

Deep merge применяется при стратегии overlay для merge-eligible
файлов. Алгоритм объединяет два значения: `base` (результат
предыдущих слоёв) и `incoming` (значение из текущего слоя).

### Правила слияния

Слияние выполняется рекурсивно по следующим правилам:

1. Если `incoming` является объектом (ассоциативный массив ключ-значение)
   и `base` является объектом — для каждого ключа из `incoming`
   рекурсивно применить правила слияния к значениям `base[key]`
   и `incoming[key]`. Ключи, присутствующие только в `base`,
   ДОЛЖНЫ сохраняться без изменений.
2. Если `incoming` является массивом — значение `incoming` ДОЛЖНО
   полностью заменить значение `base`, независимо от типа `base`.
   Элементы массивов НЕ ДОЛЖНЫ объединяться (append).
3. Если `incoming` имеет значение `null` — ключ ДОЛЖЕН быть удалён
   из результата. Значение `null` в `incoming` означает
   «удалить ключ из base».
4. Для всех остальных скалярных значений `incoming` (строки, числа,
   булевы значения) — значение `incoming` ДОЛЖНО заменить
   значение `base` (last-writer-wins).
5. Если `incoming` является объектом, а `base` НЕ является объектом
   (или `base` отсутствует) — значение `incoming` ДОЛЖНО заменить
   значение `base`.

### Пример deep merge

Base (`settings.json` после предыдущего слоя):

```json
{
  "editor": {
    "fontSize": 14,
    "tabSize": 2,
    "rulers": [80, 120]
  },
  "files": {
    "exclude": ["node_modules"]
  }
}
```

Incoming (`settings.json` из текущего слоя):

```json
{
  "editor": {
    "fontSize": 16,
    "rulers": [100],
    "wordWrap": "on"
  },
  "files": null
}
```

Результат:

```json
{
  "editor": {
    "fontSize": 16,
    "tabSize": 2,
    "rulers": [100],
    "wordWrap": "on"
  }
}
```

Обоснование:

- `editor.fontSize`: `16` заменил `14` (правило 4, last-writer-wins).
- `editor.tabSize`: `2` сохранён (ключ отсутствует в `incoming`).
- `editor.rulers`: `[100]` заменил `[80, 120]` (правило 2, массивы заменяются целиком).
- `editor.wordWrap`: `"on"` добавлен (новый ключ из `incoming`).
- `files`: удалён (правило 3, `null` удаляет ключ).

### Парсинг файлов для merge

Перед выполнением deep merge содержимое файлов ТРЕБУЕТСЯ
распарсить в соответствии с форматом:

| Расширение      | Парсер                     |
| --------------- | -------------------------- |
| `.json`         | `JSON.parse`               |
| `.jsonc`        | JSONC strip → `JSON.parse` |
| `.yaml`, `.yml` | YAML-парсер                |
| `.toml`         | TOML-парсер (`smol-toml`)  |

Для `.jsonc` ТРЕБУЕТСЯ использовать следующую процедуру парсинга
безо всяких fallback-ветвей:

1. Удалить из исходного содержимого все `//`-комментарии
   (line comments), `/* */`-комментарии (block comments) и trailing
   commas перед закрывающими `}` и `]`. Шаг удаления ТРЕБУЕТСЯ
   выполнять существующей JSONC-strip-утилитой; выбор конкретной
   библиотеки (например, `jsonc-parser` или эквивалентной) остаётся
   за фазой реализации.
2. Результат шага 1 пропустить через стандартный `JSON.parse`.
3. Если `JSON.parse` после strip-этапа выбрасывает ошибку — применяется
   общее правило fail-fast для невалидного base (см. ниже).

Замечание: Agloom эмитирует `.jsonc`-файлы как чистый JSON без
комментариев. Пользовательские комментарии допустимы в overlay-слоях,
но после deep merge итоговый output-файл всё равно не содержит
комментариев (comment-preserving round-trip НЕ входит в scope данной
спецификации).

TOML не поддерживает значение `null`, поэтому правило 3
(null = удалить ключ) неприменимо к TOML-файлам. Удаление
ключей через TOML-слои невозможно. Для удаления ключа
из результата merge ТРЕБУЕТСЯ использовать слой в формате,
поддерживающем `null` (JSON, JSONC, YAML), или стратегию
override (суффикс `.override`).

Парсинг и сериализация TOML ТРЕБУЕТСЯ выполнять библиотекой
`smol-toml`. Сериализация ДОЛЖНА сохранять стабильный порядок
ключей (порядок вставки в объект-результат merge), чтобы вывод
был детерминированным.

Если существующий целевой файл (base), подлежащий deep merge,
не может быть распарсен соответствующим парсером (синтаксическая
ошибка JSON, невалидный JSONC после strip-этапа, невалидный YAML,
невалидный TOML и т.п.), обработка оставшихся записей слоя
ТРЕБУЕТСЯ прервать с ошибкой `LayerMergeError`. Объект ошибки
ДОЛЖЕН содержать:

- абсолютный путь к невалидному файлу;
- формат файла (по расширению);
- сообщение исходного парсера, включая позицию ошибки (offset,
  line/column), если парсер её предоставляет.

`LayerMergeError` ДОЛЖЕН быть перехвачен вызывающим кодом
`runOverlayStep` и конвертирован в `TranspilerStepOutcome.errors`
согласно § Расширение «Операция overlay», расширение 2.7a.
Необработанное распространение `LayerMergeError` наружу
`runOverlayStep` ЗАПРЕЩЕНО (см. `docs/specs/cli.md`
§ Обработка ошибок транспиляции § Общий контракт шагов).

Silent overwrite невалидного base ЗАПРЕЩЁН: пользователь ДОЛЖЕН
разрешить конфликт самостоятельно (удалить или починить
невалидный файл) перед повторным запуском транспиляции. Это
поведение симметрично для всех merge-eligible форматов (`.json`,
`.jsonc`, `.yaml`, `.yml`, `.toml`).

После deep merge результат ТРЕБУЕТСЯ сериализовать обратно
в формат `incoming` файла и записать в целевой путь.

## Порядок применения слоёв

### Общий порядок per-adapter pipeline

Для каждого адаптера слои применяются в следующем порядке:

```text
Для каждого адаптера:
  Плагин A: instructions → skills → agents → overlay
  Плагин B: instructions → skills → agents → overlay
  Локальный проект: instructions → skills → agents → overlay
```

Плагины применяются в порядке, объявленном в конфигурационном
файле `config.yml` (см. `docs/specs/config.md`). Локальный проект
всегда применяется последним и имеет наивысший приоритет.

### Приоритет слоёв

Более поздний слой имеет более высокий приоритет:

1. Первый плагин — наименьший приоритет.
2. Последующие плагины — в порядке объявления.
3. Локальный проект — наивысший приоритет.

При конфликте по одному пути файла (один и тот же относительный путь
в нескольких слоях):

- Для merge-eligible файлов без суффикса `.override` — выполняется
  deep merge всех версий в порядке приоритета.
- Для override-only файлов и файлов с суффиксом `.override` —
  последний слой полностью заменяет предыдущие.

### Отношение к шагам транспиляции

Overlay-шаг ДОЛЖЕН выполняться ПОСЛЕ всех транспилерных шагов
(Instructions, Skills, Agents) каждого источника (плагина
или локального проекта), как определено
в `docs/specs/provider-overlay.md` § Приоритет. Файлы,
сгенерированные транспилерными шагами, рассматриваются как base
для overlay-шага первого слоя.

## Взаимодействие с интерполяцией

Интерполяция переменных (см. `docs/specs/interpolation.md`)
ДОЛЖНА выполняться ПЕРЕД операцией merge. Каждый слой
интерполируется независимо с использованием карты переменных
текущего адаптера.

Порядок обработки файла из слоя:

1. Определить стратегию слияния (overlay или override).
2. Если файл подлежит интерполяции (расширение входит
   в `INTERPOLATABLE_EXTENSIONS`, см. `docs/specs/provider-overlay.md`
   § Whitelist расширений для интерполяции) — выполнить
   интерполяцию содержимого.
3. Если стратегия overlay — распарсить интерполированное содержимое
   и выполнить deep merge с текущим base-значением по данному пути.
4. Если стратегия override — записать интерполированное содержимое
   (или побайтовую копию для файлов вне whitelist интерполяции)
   в целевой путь, заменяя предыдущее значение.

## Рефакторинг операции overlay (cli:procedure)

Операция overlay (см. `docs/specs/provider-overlay.md`
§ Операция overlay) ТРЕБУЕТСЯ расширить для поддержки модели слоёв.

### Новые параметры

К существующим параметрам операции overlay ТРЕБУЕТСЯ добавить:

- `layers` (array\<LayerSource>, обязательно) — упорядоченный список
  источников слоёв. Последний элемент имеет наивысший приоритет.

### Тип LayerSource

- `id` (string, обязательно) — идентификатор источника
  (имя плагина или `"local"`).
- `overlayDir` (string, обязательно) — абсолютный путь
  к директории overlay данного источника.

### Изменения в поведении

Текущее поведение (обработка одной директории-источника) ТРЕБУЕТСЯ
заменить на последовательную обработку нескольких слоёв:

1. Инициализировать пустую карту `mergeState: Record<string, unknown>`
   для отслеживания текущего состояния merge-eligible файлов
   по относительным путям.
2. Для каждого `layer` из `layers` в порядке объявления:
   2.1. Определить директорию-источник как `layer.overlayDir`.
   2.2. Рекурсивно обнаружить все файлы в директории-источнике.
   2.3. Для каждого обнаруженного файла определить относительный
   путь внутри директории-источника.
   2.4. Для каждого обнаруженного файла определить целевой
   относительный путь (с удалением суффикса `.override`
   при наличии).
   2.5. Для каждого обнаруженного файла определить стратегию
   слияния (см. § Определение стратегии для конкретного файла).
   2.6. Если `variables` передан И расширение файла входит
   в `INTERPOLATABLE_EXTENSIONS` — прочитать содержимое
   файла-источника с кодировкой UTF-8, вызвать
   `interpolate(content, variables, env)`.
   2.7. Если стратегия overlay — распарсить содержимое
   (интерполированное или исходное), выполнить deep merge
   с `mergeState[targetRelativePath]` (или с содержимым
   существующего целевого файла, если `mergeState`
   не содержит записи), обновить `mergeState[targetRelativePath]`.
   2.8. Если стратегия override — сохранить содержимое
   (или путь к файлу для побайтового копирования)
   в `mergeState[targetRelativePath]`, заменяя предыдущее
   значение.
3. Для каждой записи в `mergeState`:
   3.1. Определить целевой путь как `<projectRoot>/<относительный путь>`.
   3.2. Создать промежуточные каталоги при необходимости.
   3.3. Сериализовать и записать результат в целевой путь.
4. Сформировать `TranspilerStepOutcome` с `name: "Overlay"`,
   `writtenCount` и `errors`.

### Новые расширения

2.2a. Директория-источник слоя не существует → пропустить слой,
продолжить со следующим.

2.6a. `interpolate` выбрасывает `InterpolationError` →
добавить сообщение
`"Interpolation failed for {layer.id}:{relativePath}: {причина}"`
в `errors`, пропустить файл, продолжить с оставшимися.

2.7a. Парсинг существующего целевого файла (base) или файла текущего
слоя завершился ошибкой (невалидный JSON, JSONC после strip, YAML,
TOML) → прервать обработку оставшихся записей слоя с ошибкой
`LayerMergeError` (см. § Парсинг файлов для merge, правило fail-fast).
`runOverlayStep` ДОЛЖЕН перехватить `LayerMergeError` и вернуть
`TranspilerStepOutcome` с `name: "Overlay"`, `writtenCount`, равным
количеству файлов, успешно записанных до момента ошибки, и массивом
`errors`, содержащим построчное представление `LayerMergeError`:

1. первая строка — `"Failed to parse {format} file at {absolutePath}:"`;
2. вторая строка — сообщение исходного парсера, включая позицию
   ошибки (offset, line/column), если парсер её предоставляет;
3. третья строка —
   `"Please fix or remove the file and retry transpilation."`.

Каждая логическая строка ДОЛЖНА быть отдельным элементом массива
`errors` (см. `docs/specs/cli.md`
§ Обработка ошибок транспиляции § Формат отображения ошибки в TUI).
`runOverlayStep` ЗАПРЕЩЕНО распространять `LayerMergeError` как
необработанное исключение за пределы процедуры (см.
`docs/specs/cli.md` § Обработка ошибок транспиляции
§ Общий контракт шагов).

3.2a. Ошибка создания промежуточного каталога → добавить сообщение
в `errors`, продолжить с оставшимися записями.

3.3a. Ошибка сериализации или записи файла → добавить сообщение
в `errors`, продолжить с оставшимися записями.

## Отношение к существующим спецификациям

Данная спецификация расширяет `docs/specs/provider-overlay.md`.
После реализации модели слоёв:

- Операция overlay (см. `docs/specs/provider-overlay.md`
  § Операция overlay) ДОЛЖНА поддерживать параметр `layers`
  для обработки нескольких источников.
- Обратная совместимость: при вызове операции overlay без параметра
  `layers` (единственный источник — локальный проект) поведение
  ДОЛЖНО соответствовать текущей спецификации
  `docs/specs/provider-overlay.md`, за исключением добавления
  поддержки merge-стратегии для merge-eligible файлов.
- Whitelist расширений для интерполяции
  (`INTERPOLATABLE_EXTENSIONS`) остаётся без изменений
  (см. `docs/specs/provider-overlay.md`
  § Whitelist расширений для интерполяции).

## Вне scope

Следующие аспекты НЕ ВХОДЯТ в scope данной спецификации:

- Формат манифеста плагина (plugin manifest) — отдельная спецификация.
- Механизм загрузки и обнаружения плагинов — отдельная спецификация.
- Patch-операции (JSON Patch, JSON Merge Patch) — итерация 2.
- Загрузка плагинов из Git-репозиториев — итерация 2.
- Стратегии слияния для Markdown-файлов.
- Конкретные библиотеки для парсинга TOML, JSONC
  (определяются на этапе реализации).
