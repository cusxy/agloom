## S-тир — Критически важные техники

### 1. Явная рубрика с критериями оценки

Самая мощная техника для ревью. Без неё модель даёт размытый, непоследовательный фидбэк.
Исследование ResearchRubrics (2025, arXiv) показало, что даже лучшие AI-агенты достигают
лишь ~67% compliance с экспертными рубриками — а без рубрик результат ещё хуже.
Rubric-based evaluation — подтверждённый тренд 2025 года (Snorkel AI, Labelbox).

**Плохо:**

```text
Проверь этот markdown документ и дай обратную связь.
```

**Хорошо:**

```text
Оцени документ по следующим критериям (1-5 для каждого):
1. Структура: логичность иерархии заголовков, навигация
2. Полнота: все ли ключевые аспекты темы раскрыты
3. Ясность: понятность для целевой аудитории (junior-разработчики)
4. Техническая корректность: точность утверждений и примеров кода
5. Оформление: правильность markdown-синтаксиса, консистентность стиля

Для каждого критерия: приведи цитату из документа, оценку, и конкретное предложение по улучшению.
```

**Почему S:** задаёт рамки, в которых модель работает стабильно и повторяемо.
Превращает хаотичный фидбэк в системное ревью.

---

### 2. Few-shot примеры хорошего ревью

Исследования подтверждают: few-shot остаётся техникой с наивысшим ROI.
Anthropic рекомендует 3–5 примеров, обёрнутых в теги. Исследование 2024 года показало,
что GPT-4 с markdown-структурированными промптами достигает 81.2% точности
против 73.9% без них.

**Подход:**

```xml
<examples>

<example>
<input>## Установка\nЗапустите команду для установки</input>
<review>
- [Полнота: 2/5] Секция "Установка" не содержит саму команду установки.
  Цитата: "Запустите команду для установки" — какую именно команду?
  Предложение: Добавить `npm install package-name` или эквивалент.
- [Ясность: 3/5] Нет указания на prerequisites (Node.js версия, ОС).
  Предложение: Добавить секцию "Требования" перед установкой.
</review>
</example>

<example>
<input>## API\n### getUser(id)\nВозвращает пользователя.</input>
<review>
- [Полнота: 2/5] Отсутствует описание параметра `id` (тип, обязательность).
  Предложение: Добавить таблицу параметров с колонками: имя, тип, обязательность, описание.
- [Полнота: 1/5] Не описан формат возвращаемого значения.
  Предложение: Добавить пример ответа в формате JSON.
- [Техническая корректность: 3/5] Не указаны возможные ошибки (404, 403).
  Предложение: Добавить секцию "Ошибки" с кодами и описаниями.
</review>
</example>

</examples>
```

**Почему S:** примеры калибруют глубину, формат и тон ревью эффективнее,
чем любые словесные инструкции.

## A-тир — Сильно улучшают результат

### 3. Декомпозиция на отдельные проходы (Prompt Chaining)

Не пытайтесь проверить всё за один промпт — это подтверждённая ошибка
(overloading a single prompt). Когда модель должна одновременно проверять грамматику,
логику, техническую корректность и markdown-синтаксис, качество каждого аспекта
деградирует.

**Рекомендуемые проходы:**

| Проход | Фокус                     | Что проверяем                                                                 |
| ------ | ------------------------- | ----------------------------------------------------------------------------- |
| 1      | Структура и навигация     | Иерархия заголовков, оглавление, внутренние ссылки, логический порядок секций |
| 2      | Содержание и корректность | Фактическая точность, полнота, актуальность примеров кода                     |
| 3      | Стиль и язык              | Грамматика, консистентность терминологии, тон, читабельность                  |
| 4      | Markdown-синтаксис        | Валидность разметки, рендеринг таблиц, блоков кода, ссылок                    |

**Почему A:** требует чуть больше инфраструктуры (несколько вызовов API или ручная
последовательность), но существенно повышает качество каждого аспекта ревью.
Особенно эффективно для документов длиннее 500 строк.

---

### 4. Разделение документа и инструкций XML-тегами

Ключевая рекомендация Anthropic. Без явного разделения модель путает контент
ревьюируемого документа с инструкциями промпта. Это особенно критично,
когда документ сам содержит инструкции, примеры промптов или код.

**Подход:**

```xml
<instructions>
Ты — старший технический писатель. Проведи ревью документа ниже.
Фокус: точность API-примеров и полнота описания параметров.
</instructions>

<document>
{содержимое markdown-файла}
</document>

<output_format>
Для каждой найденной проблемы укажи:
- Строка/секция
- Серьёзность: critical / major / minor / suggestion
- Описание проблемы
- Предложение по исправлению
</output_format>
```

**Почему A:** устраняет целый класс ошибок интерпретации. XML-теги помогают LLM
однозначно разбирать сложные промпты, где смешаны инструкции, контекст, примеры
и переменные входные данные.

---

### 5. Явный формат вывода с уровнями серьёзности

Claude 4.x буквально выполняет то, что просят — не больше. DreamHost (2025)
подтвердил: ранние версии сами расширяли ответ, а новые модели требуют явных
инструкций о формате. Если не задать формат, получите эссе вместо
структурированного ревью.

**Подход:**

```text
Классифицируй каждое замечание по серьёзности:

- critical: фактические ошибки, сломанные ссылки, некорректный код
- major: пропущенные важные секции, непонятные объяснения
- minor: стилистические замечания, опечатки
- suggestion: необязательные улучшения

Начни ответ с краткого summary (3-5 предложений), затем перечисли
все замечания, сгруппированные по серьёзности от critical к suggestion.
Заверши общей оценкой готовности документа к публикации (готов / нужны правки / требует переработки).
```

**Почему A:** делает результат actionable — легко приоритизировать исправления.
Группировка по severity позволяет автору сначала исправить критичное,
а мелочи — по ситуации.

## B-тир — Заметно помогают

### 6. Контекст: цель документа и целевая аудитория

Без контекста модель не может оценить уместность уровня детализации.
Документ для senior-архитектора и для junior-разработчика требует разного подхода.

**Подход:**

```text
Контекст документа:
- Тип: README для open-source библиотеки
- Целевая аудитория: разработчики с 1-3 годами опыта
- Цель: пользователь должен за 5 минут понять, что делает библиотека,
  и за 15 минут запустить первый пример
- Язык: русский (технические термины допускаются на английском)
```

**Почему B:** полезно, но работает как множитель для других техник,
а не самостоятельно. Без рубрики (S-тир) контекст сам по себе
не обеспечит качественного ревью.

---

### 7. Конкретная роль вместо общей

Anthropic (5-Level Prompt Hierarchy) отмечает, что роль работает только после того,
как базовые техники (ясность, примеры, структура) уже на месте.
Большинство людей начинают с роли и удивляются, почему не работает.

**Плохо:**

```text
Ты — эксперт. Проверь документ.
```

**Хорошо:**

```text
Ты — senior technical writer в команде документации Stripe.
Ты ревьюируешь API-документацию перед публикацией.
Твои приоритеты: точность примеров кода, полнота описания ошибок,
простота onboarding-пути.
```

**Почему B:** улучшает релевантность замечаний и прайминг модели на нужную
экспертизу, но менее критично, чем рубрика и примеры.

---

### 8. Цитирование перед вердиктом (Chain-of-Thought)

Заставьте модель сначала процитировать проблемный фрагмент, потом давать оценку.
Это снижает галлюцинации — модель не может "придумать" проблему, если обязана
показать цитату. Anthropic рекомендует использовать XML-теги `<thinking>` и `<answer>`
для разделения рассуждений и вывода.

**Подход:**

```text
Для каждого замечания:
1. Процитируй точный фрагмент документа в блоке `>`
2. Объясни, почему это проблема
3. Предложи исправленный вариант в блоке кода
```

**Пример вывода:**

````markdown
> Функция принимает объект конфигурации и возвращает результат.

Проблема: не указаны обязательные поля объекта конфигурации,
тип возвращаемого значения не определён.

Предложение:
​```
Функция принимает объект конфигурации со следующими полями:

- `url` (string, обязательно) — адрес API-эндпоинта
- `timeout` (number, опционально, по умолчанию 5000) — таймаут в мс

Возвращает `Promise<Response>`.
​```
````

**Почему B:** эффективная защита от галлюцинаций в ревью,
но добавляет объём к выводу.

## C-тир — Ситуационно полезны

### 9. Негативные инструкции (что НЕ делать)

Полезны после нескольких итераций, когда вы уже знаете, какой нерелевантный
фидбэк модель генерирует для ваших типов документов.

**Подход:**

```text
НЕ комментируй:
- Субъективные стилистические предпочтения (oxford comma, порядок секций, если он логичен)
- Необязательные секции, которые не релевантны для данного типа документа
- Намеренно упрощённые примеры кода (они упрощены для ясности)
- Отсутствие changelog или contributing guide в README библиотеки на ранней стадии
```

**Почему C:** помогает отфильтровать шум, но работает только после итерации.
Невозможно предсказать все ненужные замечания заранее.

---

### 10. Версионирование и итерация промптов

Prompt drift — реальная проблема: вы вносите изменение в промпт, забываете
что изменили, и потом отлаживаете ухудшившийся вывод. Если промпт используется
повторно, он должен быть в version control.

**Практики:**

- Храните промпты в git-репозитории
- Ведите changelog изменений промпта
- Создайте golden test set из 5-10 документов с ожидаемыми замечаниями
- Прогоняйте тест при каждом изменении промпта (regression testing)
- Пинните версию модели в production (например, `claude-sonnet-4-6`)

**Почему C:** это не техника промпта, а инженерная практика. Критически важна
для production-систем, но не влияет на качество отдельного ревью.

## D-тир — Переоценённые техники

### 11. Общие инструкции без конкретики

```text
Будь внимательным и тщательным. Проверь всё. Убедись, что документ хорошего качества.
```

**Почему D:** не несёт информации. Модель и так старается "быть внимательной".
Это занимает токены и не меняет поведение. Замените на конкретные критерии
из рубрики (см. пункт 1).

---

### 12. Чрезмерно длинные системные промпты

Попытка специфицировать все возможные случаи, крайние ситуации
и исключения в одном монолитном промпте.

Исследование arXiv (2505.13360) показало, что чрезмерная спецификация
**ухудшает** результат из-за ограниченной способности LLM следовать длинным
сложным инструкциям. Очевидное решение "укажи все требования в одном промпте"
на практике контрпродуктивно.

**Почему D:** лучше разбить на чейн из нескольких проходов (см. пункт 3)
или использовать Anthropic prompt caching — статический контент первым,
переменный последним — для оптимизации.

## Готовый шаблон промпта

Ниже — шаблон, объединяющий техники тиров S, A и B. Адаптируйте под ваш тип документов.

```xml
<instructions>
Ты — senior technical writer, специализирующийся на документации для разработчиков.
Проведи ревью markdown-документа ниже.

Контекст:
- Тип документа: [README / API docs / tutorial / guide]
- Целевая аудитория: [junior/middle/senior разработчики]
- Цель документа: [что пользователь должен понять/сделать после прочтения]

Оцени документ по следующим критериям (1-5 для каждого):
1. Структура — логичность иерархии заголовков, навигация, порядок секций
2. Полнота — все ли ключевые аспекты раскрыты для целевой аудитории
3. Ясность — понятность формулировок, качество примеров
4. Техническая корректность — точность утверждений, работоспособность кода
5. Markdown-оформление — валидность синтаксиса, консистентность стиля

Для каждого замечания:
1. Процитируй проблемный фрагмент в блоке `>`
2. Укажи серьёзность: critical / major / minor / suggestion
3. Объясни проблему
4. Предложи исправленный вариант

Формат ответа:
- Начни с краткого summary (3-5 предложений)
- Затем оценки по каждому критерию с обоснованием
- Затем список замечаний, сгруппированный по серьёзности
- Заверши вердиктом: готов к публикации / нужны правки / требует переработки
</instructions>

<examples>

<example>
<input>## Установка\nЗапустите команду для установки</input>
<review>
**Summary:** Секция установки неполная — отсутствует ключевая информация.

**Структура: 3/5** — заголовок на месте, но секция слишком короткая.

**Замечания:**
- [major] Цитата:
  > Запустите команду для установки
  Проблема: не указана сама команда установки.
  Исправление: `npm install package-name`
- [minor] Нет указания на prerequisites.
  Исправление: добавить секцию "Требования" с версией Node.js.

**Вердикт:** нужны правки
</review>
</example>

</examples>

<document>
{ВСТАВЬТЕ СОДЕРЖИМОЕ MARKDOWN-ФАЙЛА СЮДА}
</document>
```
