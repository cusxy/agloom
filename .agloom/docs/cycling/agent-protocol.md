# Протокол работы агентов

Runtime-протокол для агентов агентных циклов (spec-cycle, research-cycle и др.).
Протокол оркестрации (запуск, мониторинг, возобновление агентов):
[orchestrator-protocol.md](orchestrator-protocol.md).

## Принцип работы

Агент запускается оркестратором с **изолированным контекстом**.
Доступа к результатам предыдущих фаз нет — вся информация передаётся через входные параметры.

Агенты-исполнители при возврате от reviewer могут быть **возобновлены** (resume) —
предыдущий контекст сохраняется, отчёт reviewer передаётся как новое сообщение.
В этом случае достаточно адресовать замечания, не повторяя чтение файлов.

## Верификация DoR/DoD

Каждый агент содержит Definition of Ready и Definition of Done.

**Перед началом работы** — проверить все пункты DoR и отправить сообщение 1
(preconditions). Если хотя бы один пункт не пройден (`verdict: fail`) —
завершить работу.

При проверке DoR агенту ТРЕБУЕТСЯ оценить **доменную достаточность** входных
данных — содержат ли scope и context всё необходимое для выполнения его задачи.
Конкретные пункты доменной достаточности определяются в DoR каждого агента.

Если данных недостаточно — зафиксировать в comment соответствующего пункта DoR
**что именно отсутствует** и выставить `verdict: fail`. Если недостаточность
связана с качеством артефакта предыдущей фазы — указать `returnTo`
(см. [Сообщение 1](#сообщение-1--preconditions-перед-началом-работы)). Оркестратор определит маршрутизацию
(см. [Обработка DoR-ошибок агентов](orchestrator-protocol.md#обработка-dor-ошибок-агентов)).

Если context содержит указание `skip_clarification: true` — агент МОЖЕТ
пропустить проверку доменной достаточности и выбрать наиболее вероятную
интерпретацию самостоятельно, зафиксировав её в `choices` результата
с `confidence: low`.

**Перед завершением** — проверить все пункты DoD и включить результат в сообщение 2
(поле `postconditions`). Если хотя бы один пункт не пройден — продолжить работу
до выполнения всех пунктов.

## Вход

Prompt агента содержит два параметра в plain text формате:

```text
scope:
- <path-to-file>

context:
<свободный текст>
```

- **scope** — пути к файлам (относительные от корня проекта), по одному на строку.
- **context** — содержание зависит от типа перехода:
  - При создании: описание задачи, результаты уточнения требований
    (ответы пользователя, принятые решения), результаты предварительного
    исследования (если проводилось).
  - При внутрифазовом возврате от reviewer: отчёт reviewer с findings.
  - При возврате к ранней фазе: Phase Execution Summaries (choices
    агента с метками валидации, summaries промежуточных фаз), findings
    причины возврата.
  - При межфазовом переходе: краткое описание задачи, Phase Execution
    Summaries завершённых фаз.
  - Флаг `skip_clarification: true` (если пользователь запросил opt-out).

Требования к содержанию context при запуске агентов определены
в [Формирование context](orchestrator-protocol.md#формирование-context).

## Выход

Агенту ЗАПРЕЩАЕТСЯ выводить свободный текст, промежуточные размышления
или пояснения вне блока thinking, потому что это увеличивает время вывода
и расход output-токенов. Весь вывод агента — строго JSON.

Агенту СЛЕДУЕТ использовать extended thinking (thinking-блоки) для анализа
и reasoning перед формированием JSON output. Thinking-блоки не являются частью
вывода агента и не нарушают правило «весь вывод — строго JSON». Двухшаговый
подход (free-form reasoning в thinking, затем структурированный JSON) устраняет
деградацию reasoning, возникающую при строгом JSON-mode.

Агент отправляет ровно **два сообщения** за время работы:

1. **preconditions** — результат проверки DoR перед началом работы.
2. **result** — результат работы с артефактами, findings и проверкой DoD.

Порядок полей в обоих сообщениях следует принципу schema-guided reasoning:
сначала тип, затем факты и доказательства, verdict — последним. Это обеспечивает
формирование решения на основе собранных данных, а не подгонку данных
под заранее выбранный verdict.

### Формат пункта проверки

Каждый пункт DoR и DoD описывается единообразно. ТРЕБУЕТСЯ перечислять
все пункты — и пройденные, и непройденные:

```json
{
  "id": "dor-1",
  "comment": "комментарий агента",
  "verdict": "pass | fail",
  "returnTo": "agent-name | null"
}
```

- `id` — идентификатор пункта из определения агента (например, `dor-1`, `dod-3`).
- `comment` — конкретное найденное значение или причина fail (1–2 предложения).
- `verdict` — результат проверки данного пункта.
- `returnTo` — рекомендуемый агент для исправления при `verdict: fail` (`null`
  при pass или если проблему может разрешить оркестратор). Используется
  в preconditions для маршрутизации к агенту ранней фазы.

### Сообщение 1 — preconditions (перед началом работы)

```json
{
  "type": "preconditions",
  "preconditions": [
    { "id": "dor-1", "comment": "...", "verdict": "pass", "returnTo": null },
    { "id": "dor-2", "comment": "...", "verdict": "fail", "returnTo": "spec-writer" }
  ],
  "verdict": "pass | fail"
}
```

Если хотя бы один пункт имеет `verdict: fail` — общий `verdict: fail`.
Агенту ТРЕБУЕТСЯ завершить работу сразу после этого сообщения, без отправки
сообщения 2. Если пункт содержит `returnTo` — оркестратор МОЖЕТ использовать его
для маршрутизации (см. [Обработка DoR-ошибок агентов](orchestrator-protocol.md#обработка-dor-ошибок-агентов)).

### Сообщение 2 — result (после завершения работы)

```json
{
  "type": "result",
  "artifacts": ["<path>"],
  "choices": [],
  "findings": [],
  "postconditions": [
    { "id": "dod-1", "comment": "...", "verdict": "pass" },
    { "id": "dod-2", "comment": "...", "verdict": "fail" }
  ],
  "verdict": "pass | fail"
}
```

- `artifacts` — пути к созданным/изменённым файлам.
- `choices` — массив ключевых решений и предположений агента (пустой если
  нетривиальных решений не было). См. [Структура choice](#структура-choice).
- `findings` — массив замечаний (пустой при отсутствии). Каждый finding
  содержит `returnTo` — рекомендуемый агент для исправления.
- `postconditions` — результат проверки postconditions. Если хотя бы один пункт
  имеет `verdict: fail` — агенту ТРЕБУЕТСЯ продолжить работу до выполнения
  всех пунктов.
- `verdict` — `pass` если все пункты postconditions выполнены, `fail` если нет.
  Генерируется последним, на основе findings и postconditions.

## Структура finding

Каждый finding соответствует конкретному пункту валидации из определения агента.
ТРЕБУЕТСЯ перечислять все пункты — и пройденные, и непройденные. Это обеспечивает
явное обоснование по каждому критерию. Для замечаний, не привязанных к конкретному
пункту валидации, используется тип `general`.

```json
{
  "id": "D1",
  "file": "path/to/file:42",
  "description": "...",
  "severity": "high | medium | low",
  "verdict": "pass | fail",
  "returnTo": "agent-name"
}
```

- `id` — идентификатор пункта валидации из определения агента, или `general`.
- `file` — путь к файлу с номером строки (пустая строка при `verdict: pass`).
- `description` — обоснование: почему пункт пройден или в чём проблема (1–2 предложения).
- `severity` — оценка критичности (`null` при `verdict: pass`).
- `verdict` — результат проверки данного пункта. Генерируется последним.
- `returnTo` — рекомендуемый агент для исправления (`null` при pass).

## Структура choice

Choice фиксируется когда агент принимает нетривиальное решение: выбирает между
альтернативами, интерпретирует неоднозначное требование или делает предположение
при отсутствии данных.

```json
{
  "id": "C1",
  "context": "...",
  "analysis": "...",
  "choice": "...",
  "confidence": "high | medium | low"
}
```

- `id` — последовательный идентификатор (C1, C2, ...). При возобновлении
  агента (resume) нумерация продолжается с последнего использованного ID.
- `context` — какие данные есть или отсутствуют, какие варианты рассмотрены
  (1–2 предложения).
- `analysis` — ключевой tradeoff или причина неопределённости (1–2 предложения).
- `choice` — что выбрано или предположено.
- `confidence` — уверенность в выборе, генерируется последним на основе context
  и analysis. Значение по умолчанию — `medium`.
  - `high` — данные достаточны, варианты сравнены, альтернатив нет.
  - `medium` — данные неполны, но есть обоснование. Значение по умолчанию
    при любой неопределённости.
  - `low` — данных нет, выбрана наиболее вероятная интерпретация.

### Что фиксировать как choice

- Выбор между альтернативными подходами (архитектура, API-дизайн, структура данных).
- Интерпретацию неоднозначного требования.
- Предположение при отсутствии данных в scope, context или документации.
- Сознательное отклонение от стандартного паттерна.
