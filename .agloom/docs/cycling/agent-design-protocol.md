# Протокол создания и валидации агентов

Design-time протокол для создания, изменения и валидации определений агентов.

- Общие правила (RFC 2119, тон, стиль, правила написания): [cycle-design-protocol.md](cycle-design-protocol.md).
- Runtime-протокол (формат ввода/вывода, findings, DoR/DoD): [agent-protocol.md](agent-protocol.md).

## Структура определения агента

Каждый файл определения агента ДОЛЖЕН содержать секции, разделённые на две группы: **header** (контракт)
и **implementation** (детали).

Header — контракт агента: намерение, вход, выход, quality gates. Используется
оркестратором и при валидации связей между агентами. Implementation — внутренние
правила и процедуры, нужные только самому агенту.

### Header (контракт)

| Секция              | Обязательность | Описание                            |
| ------------------- | -------------- | ----------------------------------- |
| YAML front matter   | ТРЕБУЕТСЯ      | `name`, `description`, `model`      |
| Вводный абзац       | ТРЕБУЕТСЯ      | Намерение, зона ответственности     |
| Общие документы     | ТРЕБУЕТСЯ      | Ссылки на загружаемые документы     |
| Входные параметры   | ТРЕБУЕТСЯ      | Типы scope и context по переходам   |
| Артефакты генерации | ТРЕБУЕТСЯ      | Типы создаваемых/изменяемых файлов  |
| Definition of Ready | ТРЕБУЕТСЯ      | Preconditions запуска (чеклист)     |
| Definition of Done  | ТРЕБУЕТСЯ      | Postconditions завершения (чеклист) |
| returnTo            | ТРЕБУЕТСЯ      | Допустимые значения returnTo        |

DoR каждого агента ДОЛЖЕН включать пункт (или пункты) проверки **доменной
достаточности** context. Формулировка пунктов специфична для домена агента —
она описывает, какие именно данные агент ожидает в context для выполнения
своей задачи.

Для пунктов DoR, где критерий прохождения неочевиден, РЕКОМЕНДУЕТСЯ
включать pass/fail примеры по аналогии с критериями reviewer'ов.
Конкретные якоря повышают калибровку проверки и снижают количество
ложных fail. Добавлять примеры для всех пунктов не требуется —
только для тех, где формулировка допускает неоднозначную интерпретацию.

#### Секция «Входные параметры»

Описывает типы файлов в scope и содержимое context для каждого
перехода, в котором агент может быть запущен:

```markdown
## Входные параметры

- **Scope**: <типы файлов> — <пояснение>.
- **Context**:
  - От <источник> (<режим>): <что содержит>.
  - От <источник> (<режим>): <что содержит>.
```

#### Секция «Артефакты генерации»

Перечисляет типы файлов, которые агент создаёт или изменяет.
Конкретные файлы определяет агент в процессе работы.

### Implementation (детали)

| Секция             | Обязательность    | Описание                               |
| ------------------ | ----------------- | -------------------------------------- |
| Определение режима | Если применимо    | Логика выбора режима работы            |
| Правила            | Исполнители       | Правила и процедуры выполнения задачи  |
| Нештатные ситуации | Исполнители       | Типовые проблемы и их решения          |
| Завершение         | Исполнители       | Шаги валидации перед отправкой result  |
| Критерии проверки  | Reviewer'ы        | Критерии оценки артефактов             |
| Стратегия проверки | Reviewer'ы (рек.) | Порядок и приоритет проверки критериев |
| Формат вывода      | Reviewer'ы        | Маппинг критериев на JSON findings     |

Секции implementation разделены по ролям: исполнители используют «Правила» +
«Нештатные ситуации» + «Завершение», reviewer'ы — «Критерии проверки» +
«Формат вывода» (+ «Стратегия проверки» при наличии). Название секции «Правила»
МОЖЕТ быть доменно-специфичным (например, «Правила создания», «Правила генерации»).

Формат вывода **всех** агентов (исполнителей и reviewer'ов) определён
в [agent-protocol.md](agent-protocol.md#выход) — строго JSON, два сообщения
(preconditions + result). Секция «Завершение» описывает процедурные шаги
(форматирование, компиляция, тесты), выполняемые **перед** отправкой
result-сообщения. Секция «Формат вывода» описывает, как доменные критерии
reviewer'а маппятся на JSON findings.

#### Секция «Критерии проверки» (reviewer'ы)

Каждый критерий проверки ТРЕБУЕТСЯ описывать в структурированном формате:

```markdown
### <ID>. <Название>

<Описание: что проверяется, какие подпункты>

**Pass-пример:** <конкретный пример артефакта, который проходит данный критерий>

**Fail-пример:** <конкретный пример артефакта, который не проходит данный критерий>
```

Примеры pass/fail ТРЕБУЮТСЯ для каждого критерия, потому что они дают модели
конкретные якоря для калибровки решений и снижают количество false positives.
Примеры СЛЕДУЕТ создавать синтетически, приближая структуру и уровень
детализации к реальным артефактам. Использование реальных артефактов
ЗАПРЕЩАЕТСЯ, потому что конкретные примеры создают anchoring bias — модель
ищет совпадение с примером вместо анализа критерия.

### Порядок секций

Секции header ДОЛЖНЫ располагаться перед секциями implementation в файле
определения, потому что это обеспечивает читаемость контракта — оркестратор
и reviewer видят вход/выход/quality gates до деталей реализации.

## Валидация и оптимизация

Структурная валидация агентов (intra-agent + inter-agent) выполняется
через `/cycle-creator`. Запуск РЕКОМЕНДУЕТСЯ при изменении DoR/DoD,
секций «Вход» / «Артефакты» или `returnTo` любого агента.

Оптимизация определений агентов (DoR/DoD, правила, описания нештатных
ситуаций) выполняется через `/cycle-creator`.
