# Исследование: паттерны Agent SOP для агентов spec-cycle

Дата: 2026-03-14

## Контекст исследования

Проект использует цикл spec-driven development с 6 агентами (spec-writer, spec-reviewer, test-deriver,
test-reviewer, spec-implementer, impl-reviewer), описанными в `.agloom/agents/`. Агенты управляются
оркестратором ([SKILL.md](../skills/spec-cycle/SKILL.md)) и следуют общему протоколу
([agent-protocol.md](cycling/agent-protocol.md)).

AWS открыла фреймворк [Agent SOP](https://github.com/strands-agents/agent-sop) — набор markdown-шаблонов
для описания рабочих процессов AI-агентов. Amazon внутренне использует тысячи таких SOP в production.
Ключевая идея — использование ключевых слов RFC 2119 (MUST, SHOULD, MAY) для создания иерархии обязательств,
что повышает предсказуемость поведения агентов.

Цель исследования — определить, какие паттерны из Agent SOP применимы к агентам проекта, и сформировать
конкретный план изменений.

## Часть 1. Анализ паттернов Agent SOP

### 1.1. Иерархия обязательств (RFC 2119 в constraints)

**Паттерн.** Каждое правило в Agent SOP имеет явный уровень обязательности:

```markdown
**Constraints:**

- You MUST validate directory structure exists
- You SHOULD log all setup actions
- You MAY skip validation if --force flag is provided
```

Три уровня позволяют агенту приоритизировать требования. При длинных инструкциях LLM точнее следует
критичным требованиям и не застревает на опциональных.

**Текущее состояние в проекте.** Протокол (`agent-protocol.md`) определяет таблицу соответствий
RFC 2119, но агенты используют её только при написании спецификаций продукта. Собственные правила
агентов сформулированы без градации: «Реализуй только то, что следует из спецификации», «Копируй
паттерны из существующего кода» — всё воспринимается как одинаково обязательное.

**Вывод.** Применимо. Добавить RFC 2119 keywords к правилам агентов. Это особенно важно
для агентов с большим количеством правил (spec-writer, spec-implementer, impl-reviewer).

### 1.2. Обоснование запретов (MUST NOT + because)

**Паттерн.** Agent SOP требует указывать причину каждого запрета:

```markdown
- You MUST NOT delete files without confirmation because this could result in permanent data loss
```

Без обоснования:

```markdown
- You MUST NOT delete files
```

Исследования показывают, что LLM лучше следуют запретам с указанной причиной — голый запрет
конкурирует с обучающими данными модели, а обоснованный запрет усиливает compliance.

**Текущее состояние в проекте.** Часть запретов обоснована:

> Агент не правит спецификации и тесты — это входные данные, а не объекты редактирования.
> При обнаружении ошибки в спецификации или тесте — сообщить в отчёте, но не править.

Но многие запреты остаются без причины:

> Не вноси изменений сверх замечаний ревью.

**Вывод.** Применимо. Дополнить все запреты обоснованиями.

### 1.3. Секция Troubleshooting

**Паттерн.** Agent SOP включает типовые проблемы и их решения прямо в описание workflow:

```markdown
## Troubleshooting

### Build Issues

If builds fail during implementation:

- You SHOULD verify you're in the correct directory for the build system
- You SHOULD try clean builds before rebuilding
- You SHOULD check for missing dependencies
```

**Текущее состояние в проекте.** DoR/DoD покрывают предусловия и постусловия, но не покрывают
runtime-ситуации: «тесты падают по причине, не связанной с моим кодом», «спецификация содержит
противоречие, которое не заметил reviewer», «компиляция ломается из-за зависимости».

Агент spec-implementer частично описывает одну такую ситуацию:

> Если тесты падают: проанализируй причину: ошибка в реализации или в тесте.

Но это единичный случай, не систематический подход.

**Вывод.** Применимо. Добавить секции Troubleshooting в агенты, где runtime-ситуации наиболее
вероятны: spec-implementer (сборка, тесты), test-deriver (существующий код не компилируется,
тесты неожиданно проходят).

### 1.4. Явная параметризация

**Паттерн.** Agent SOP формализует входные параметры:

```markdown
## Parameters

- **task_description** (required): Description of the task
- **mode** (optional, default: "auto"): interactive | auto
```

**Текущее состояние в проекте.** Протокол определяет формат входа (scope + context), но параметры
описаны неформально. Агент сам интерпретирует, что содержит context.

**Вывод.** Неприменимо в чистом виде. Агенты запускаются оркестратором через Task tool,
параметры передаются в prompt. Формализация параметров в стиле SOP создала бы дублирование
с протоколом агентов. Текущий формат (scope + context) достаточен.

### 1.5. Режимы работы (interactive / auto)

**Паттерн.** Agent SOP определяет поведение для каждого шага в зависимости от режима:

- **interactive** — показать, спросить, подождать подтверждения.
- **auto** — выполнить, задокументировать решение, продолжить.

**Текущее состояние в проекте.** Разделение implicit: reviewer-агенты всегда «interactive»
(quality gate), исполнители — «auto». Режим зашит в роль агента, а не является параметром.

**Вывод.** Неприменимо. Текущее разделение по ролям (исполнитель/reviewer) точнее
отражает архитектуру цикла, чем параметрический режим.

### 1.6. Артефакты

**Паттерн.** Agent SOP явно перечисляет файлы, создаваемые на каждом шаге:

```markdown
## Artifacts

• {dir}/context.md
• {dir}/plan.md
• {dir}/progress.md
```

**Текущее состояние в проекте.** Артефакты описаны в выходном JSON (`artifacts` в протоколе),
но в описании агента нет перечня типов файлов, которые он создаёт. Агент сам определяет,
какие файлы создавать, и это правильно — оркестратор не должен вычислять конкретные файлы
за агента.

**Вывод.** Частично применимо. Добавить секцию «Артефакты» как **выходной контракт** агента —
перечень типов файлов, которые агент создаёт или изменяет. Секция описывает формат выхода
(аналог секции «Результат» в спецификации операции), но не диктует конкретные файлы.
Агент сам решает, какие именно файлы нужны в рамках задачи. Валидация результата — ответственность
reviewer-агента на следующем шаге цикла, не оркестратора.

### 1.7. Грамматическое лицо в инструкциях агентам

**Вопрос.** Проект требует третье лицо в спецификациях продукта (`agent-protocol.md` → «Тон и стиль»).
Оправдано ли распространение этого правила на инструкции самим агентам? Agent SOP использует
второе лицо: «You MUST validate», «You SHOULD log». Текущие описания агентов проекта уже используют
второе лицо: директивные инструкции агенту («…— spec-writer», «…не пишет тесты»).

**Два контекста — два ответа.**

#### Спецификации продукта → третье лицо (обосновано)

Третье лицо — стандарт requirements engineering (ISO/IEC/IEEE 29148, RFC-документы, Use Cases
по Cockburn). Устраняет неоднозначность адресата и делает спецификацию пригодной для механического
извлечения тестов. Пример:

- Верно: «Система нормализует email к нижнему регистру.»
- Неверно: «Нормализуй email к нижнему регистру.»

#### Инструкции агентам → второе лицо (эффективнее)

Прямого A/B-исследования «You MUST» vs «Агент должен» не опубликовано, но косвенные данные
сходятся в одном направлении:

1. **Instruction-tuning data.** Модели обучаются на данных RLHF/SFT, написанных преимущественно
   во втором лице. «You must» ближе к обучающему распределению, чем «The agent must».

2. **26 Principles (Bsharat et al., 2023).** Эмпирически показано, что фразы «Your task is»
   и «You MUST» повышают accuracy — до +57% на LLaMA, +67% на GPT-4 (в совокупности
   с другими принципами, не в изоляции).

3. **Industry practice.** Agent SOP (AWS), системные промпты OpenAI Codex, Cline, Claude Code —
   все используют второе лицо для инструкций агентам.

4. **Practitioner consensus.** «Use clear, commanding language», «Be Direct and Imperative» —
   рекомендации из руководств по промптингу.

5. **GPT Builder** автоматически генерирует инструкции в третьем лице («This GPT...»),
   но это единственный контрпример среди известных систем.

6. **Prompt framing research.** Ключевой фактор — ясность и специфичность формулировки,
   а не грамматическое лицо само по себе. Однако второе лицо обеспечивает бóльшую директивность
   при равной ясности.

**Вывод.** Правило третьего лица обосновано для спецификаций продукта (выход агента) и не обосновано
для инструкций агентам (описание агента). Это разные типы документов с разными адресатами:
спецификация описывает **что система делает**, инструкция описывает **что агент должен делать**.
Текущие описания агентов уже используют второе лицо — это соответствует industry practice
и не требует изменений. Правило в `agent-protocol.md` → «Тон и стиль» следует уточнить:
третье лицо применяется к **спецификациям продукта**, а не к описаниям агентов.

## Часть 2. План изменений

### Изменение 1. RFC 2119 keywords в правилах агентов

**Что.** Добавить уровни обязательности (ТРЕБУЕТСЯ, СЛЕДУЕТ, МОЖЕТ) к правилам в описаниях агентов.

**Где.** Все 6 агентов — секции «Правила», «Завершение», DoR, DoD.

**Пример (spec-implementer, «Правила»).**

До:

```markdown
- Реализуй только то, что следует из спецификации. Не добавляй функциональность, которой нет в документах.
- Копируй паттерны из существующего кода проекта, не изобретай новые подходы.
- Денежные суммы: DECIMAL в PostgreSQL, string в entity и DTO, decimal.js для арифметики.
```

После:

```markdown
- Тебе ТРЕБУЕТСЯ реализовать только то, что следует из спецификации.
  Добавление функциональности, которой нет в документах, ЗАПРЕЩАЕТСЯ,
  потому что это нарушает трассируемость цепочки spec → test → impl
  и обесценивает пройденное ревью.
- Тебе СЛЕДУЕТ копировать паттерны из существующего кода проекта,
  а не изобретать новые подходы.
- Денежные суммы ТРЕБУЕТСЯ хранить как DECIMAL в PostgreSQL, string
  в entity и DTO, и использовать decimal.js для арифметики.
```

### Изменение 2. Обоснование запретов

**Что.** Каждый запрет в агентах дополнить причиной (формат: «ЗАПРЕЩАЕТСЯ <действие>, потому что <причина>»).

**Где.** Все 6 агентов — любое правило с отрицанием.

**Текущие запреты без обоснования и предлагаемые дополнения:**

| Агент            | Запрет                                                   | Обоснование                                                                                                                                            |
| ---------------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| spec-writer      | «Не вноси изменений сверх замечаний ревью»               | потому что незатронутые секции уже прошли quality gate и их изменение потребует повторного ревью                                                       |
| spec-implementer | «Не добавляй функциональность, которой нет в документах» | потому что это нарушает трассируемость spec → test → impl и обесценивает пройденное ревью                                                              |
| test-deriver     | «Не правь спецификации»                                  | потому что агент фазы test ЗАПРЕЩАЕТСЯ редактировать артефакты фазы specify — при обнаружении ошибки требуется возврат к spec-writer                   |
| test-reviewer    | «Не правь файлы»                                         | потому что reviewer выявляет проблемы, но не вносит правки — разделение ответственности между reviewer и исполнителем обеспечивает независимость ревью |
| impl-reviewer    | «Не правь файлы»                                         | аналогично test-reviewer                                                                                                                               |

### Изменение 3. Секции Troubleshooting

**Что.** Добавить секцию «Нештатные ситуации» в агенты-исполнители.

**Где.** spec-implementer, test-deriver.

**Содержимое для spec-implementer:**

```markdown
## Нештатные ситуации

### Тесты падают из-за ошибки в тесте, а не в реализации

Если тест проверяет поведение, не соответствующее спецификации — зафиксировать
расхождение в findings (`returnTo: test-deriver`). Код тестов ЗАПРЕЩАЕТСЯ
редактировать, потому что это нарушает разделение фаз цикла.

### Компиляция ломается из-за несовместимости зависимостей

Если ошибка не связана с текущими изменениями — зафиксировать в findings
и завершить работу с verdict: fail. Не пытаться исправлять инфраструктурные
проблемы, потому что это выходит за scope задачи.

### Спецификация содержит противоречие

Если шаг поведения противоречит расширению или секции Результат — зафиксировать
в findings (`returnTo: spec-writer`). Не выбирать интерпретацию самостоятельно,
потому что это подменяет решение автора спецификации.
```

**Содержимое для test-deriver:**

```markdown
## Нештатные ситуации

### Тест неожиданно проходит

Проверить: (а) тестируемое поведение уже реализовано в коде, (б) тест тривиален
и проходит при любой реализации. В случае (а) — пояснить в сводке. В случае (б) —
переписать тест.

### Существующий код не компилируется

Если ошибка компиляции существовала до начала работы — зафиксировать в findings
и завершить работу с verdict: fail. Не исправлять чужой код, потому что это
выходит за scope фазы test.

### Спецификация содержит [NEEDS CLARIFICATION]

DoR ТРЕБУЕТСЯ отклонить запуск. Если маркер обнаружен после начала работы —
остановиться, зафиксировать в findings (`returnTo: spec-writer`).
```

### Изменение 4. Секции «Артефакты»

**Что.** Добавить секцию «Артефакты» как выходной контракт агента — перечень типов файлов,
которые агент создаёт или изменяет. Конкретные файлы определяет агент самостоятельно.
Оркестратор не вычисляет список и не валидирует его — это делает reviewer на следующем шаге.

**Где.** spec-writer, test-deriver, spec-implementer.

**Пример для spec-writer:**

```markdown
## Артефакты

- Файл спецификации (`docs/`): создание нового или обновление существующего.
```

**Пример для test-deriver:**

```markdown
## Артефакты

- Тестовые файлы (`*.spec.ts`): создание новых или обновление существующих.
  Размещение — colocation с тестируемым сервисом.
```

**Пример для spec-implementer:**

```markdown
## Артефакты

- Миграции (`apps/server/migrations/`): raw SQL, при изменении схемы БД.
- Entity-файлы: TypeORM-сущности, соответствующие схеме.
- DTO-файлы: валидация входных данных (class-validator).
- Сервисы: бизнес-логика.
- Контроллеры: эндпоинты, декораторы авторизации.
- NestJS-модуль: регистрация (imports, providers, exports, controllers).
- `app.module.ts`: подключение нового модуля, если создан.
```

### Изменение 5. Обновление agent-protocol.md

**Что.** Расширить секцию «Ключевые слова (RFC 2119)» — указать, что keywords применяются
не только в спецификациях продукта, но и в описаниях агентов для градации обязательности правил.

### Изменение 6. Уточнение правила третьего лица

**Что.** Уточнить в `agent-protocol.md` → «Тон и стиль», что правило третьего лица
распространяется на **спецификации продукта** (выход агента), а не на описания агентов.

**Где.** `.agloom/docs/cycling/agent-protocol.md`.

**До:**

```markdown
Спецификации пишутся в третьем лице. Обращения ко второму лицу (императив
«выполни», «проверь», «укажи») запрещаются.
```

**После:**

```markdown
Спецификации продукта (`type: spec`) пишутся в третьем лице. Обращения ко второму
лицу (императив «выполни», «проверь», «укажи») в спецификациях запрещаются,
потому что третье лицо устраняет неоднозначность адресата и делает спецификацию
пригодной для механического извлечения тестов.

Описания агентов (`.agloom/agents/`) используют второе лицо («Ты ТРЕБУЕТСЯ...»,
«Ты ЗАПРЕЩАЕТСЯ...»), потому что instruction-tuned модели оптимизированы следовать
директивным инструкциям во втором лице (см. .agloom/docs/agent-sop-patterns.md § 1.7).
```

## Часть 3. Неприменимые паттерны

| Паттерн SOP                    | Причина неприменимости                                                                      |
| ------------------------------ | ------------------------------------------------------------------------------------------- |
| Формат `.sop.md`               | Проект использует Claude Code agents (`.agloom/agents/`), формат уже определён              |
| Parameters                     | Агенты получают вход через протокол (scope + context), формализация дублировала бы протокол |
| Mode (interactive/auto)        | Разделение ролей (исполнитель/reviewer) заменяет параметрический режим                      |
| MCP-сервер                     | Проект работает в single-tool environment (Claude Code)                                     |
| Конвертеры (Cursor, Skills)    | Аналогично — нет multi-IDE requirement                                                      |
| Resumability через progress.md | Оркестратор использует resume через agent ID, артефакт прогресса избыточен                  |

## Заключение

| Решение                              | Выбор                                                                                 |
| ------------------------------------ | ------------------------------------------------------------------------------------- |
| RFC 2119 keywords в правилах агентов | Да — все 6 агентов                                                                    |
| Обоснование запретов                 | Да — все запреты в агентах                                                            |
| Секции Troubleshooting               | Да — spec-implementer, test-deriver                                                   |
| Секции «Артефакты»                   | Да — spec-writer, test-deriver, spec-implementer                                      |
| Обновление agent-protocol.md         | Да — расширение области применения RFC 2119                                           |
