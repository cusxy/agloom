# План перехода к уровню Validated

## Контекст

Система spec-cycle находится на уровне 2 (Structured): агенты формализованы,
контракты описаны, протокол един. Уровень 3 (Validated) требует автоматических
проверок, тестов и observability. Подробный анализ и обоснование —
[agent-as-program.md](agent-as-program.md).

## Принципы перехода

- **Инкрементальность.** Каждый шаг самодостаточен и приносит пользу без
  зависимости от последующих.
- **Валидируемость.** Каждый шаг имеет критерий приёмки.
- **Минимализм.** Реализуется минимум, необходимый для перехода на следующий уровень.

## Группировка фаз

Фазы разделены на две группы по логической зависимости:

| Группа                | Фазы | Цель                                       |
| --------------------- | ---- | ------------------------------------------ |
| Структурная валидация | 1-4  | Привести систему в консистентное состояние |
| Runtime валидация     | 5-7  | Инструментировать, проверить, измерить     |

Обоснование порядка: формат execution log (фаза 5) зависит от понимания
edge cases (фаза 4) и структуры системы (manifest, фаза 1). Smoke test (фаза 6)
зависит от execution log. Baseline metrics (фаза 7) требуют нескольких
прогонов с логированием. Структурная валидация (фазы 1-4) не зависит
от инструментирования и выполняется первой.

## Фазы

### Фаза 1. Определённость (Manifest)

**Цель.** Единый реестр всех компонентов системы с явными зависимостями.

#### Шаг 1.1. Manifest файл

Создать `.claude/skills/spec-cycle/manifest.md` со списком компонентов.

**Содержимое:** реестр компонентов (оркестратор, агенты, общие документы)
и граф переходов. Manifest — стабильное описание системы; аналитические
артефакты (цепность, типизация) не включаются.

**Критерий приёмки:**

- [ ] Manifest файл создан.
- [ ] Все агенты и документы перечислены с кратким описанием.
- [ ] Граф переходов зафиксирован.

#### Шаг 1.2. Валидация ссылок

Проверить что все пути в manifest, в секциях «Общие документы» агентов
и в `relates` front matter разрешаются в существующие файлы.

**Критерий приёмки:**

- [ ] Все ссылки из manifest проверены — ни одна не ведёт в никуда.
- [ ] Все `relates` в front matter проверены.
- [ ] При нахождении битых ссылок — исправлены.

### Фаза 2. Intra-agent lint (внутренний линтинг)

**Цель.** Автоматизируемый чеклист корректности отдельного определения агента.

#### Шаг 2.1. Формализация lint-правил

Определить правила проверки на основе мета-критериев из `dor-dod-criteria.md`
и паттернов из `agent-sop-patterns.md`.

**Структурные правила (проверяемые парсером):**

| #   | Правило                                                     | Серьёзность |
| --- | ----------------------------------------------------------- | ----------- |
| S1  | YAML front matter содержит `name`, `model`, `description`   | high        |
| S2  | Присутствуют обязательные секции: DoR, DoD                  | high        |
| S3  | Присутствует секция «Общие документы» со ссылками           | medium      |
| S4  | Присутствует секция «Артефакты» (для исполнителей)          | medium      |
| S5  | Присутствует секция «Нештатные ситуации» (для исполнителей) | medium      |
| S6  | DoR/DoD оформлены как чеклист (`- [ ]`)                     | low         |
| S7  | В конце файла указан `returnTo`                             | medium      |

**Семантические правила (проверяемые LLM или вручную):**

| #   | Правило                                                  | Серьёзность |
| --- | -------------------------------------------------------- | ----------- |
| M1  | Каждый ЗАПРЕЩАЕТСЯ имеет обоснование (`потому что`)      | high        |
| M2  | Пункты DoR/DoD бинарны (да/нет, без полутонов)           | high        |
| M3  | Пункты DoR/DoD атомарны (одно условие, нет «и»)          | medium      |
| M4  | Пункты DoR/DoD верифицируемы (есть артефакт или команда) | medium      |
| M5  | RFC 2119 keywords используются в правилах и запретах     | medium      |
| M6  | Инструкции написаны во втором лице (2-е лицо + RFC 2119) | low         |

**Критерий приёмки:**

- [ ] Lint-правила задокументированы в manifest или отдельном файле.
- [ ] Каждое правило имеет ID, описание и серьёзность.

#### Шаг 2.2. Аудит всех агентов по lint-правилам

Проверить все 6 агентов по lint-правилам. Зафиксировать нарушения, исправить.

**Критерий приёмки:**

- [ ] Все 6 агентов проверены по всем правилам S1-S7, M1-M6.
- [ ] Нарушения high severity — исправлены.
- [ ] Нарушения medium severity — исправлены или обоснованно отклонены.
- [ ] Результат аудита зафиксирован (таблица: агент x правило -> pass/fail).

### Фаза 3. Inter-agent lint (линтинг связей)

**Цель.** Валидация согласованности интерфейсов между агентами.

Реализуется командой `/validate-agents` (`.claude/skills/validate-agents/SKILL.md`),
которая выполняет три группы проверок: цепность DoD → DoR, совместимость
артефактов на стыках, валидность returnTo.

#### Шаг 3.1. Запуск валидации

Запустить `/validate-agents`. Зафиксировать отчёт.

#### Шаг 3.2. Устранение нарушений

По результатам отчёта:

- Разрывы цепности high severity — обновить DoR/DoD для устранения.
- Несовместимости артефактов — исправить секции «Вход» / «Артефакты».
- Невалидные returnTo — исправить в определениях агентов.

#### Шаг 3.3. Повторная валидация

Запустить `/validate-agents` повторно — убедиться, что нарушения high закрыты.

**Критерий приёмки:**

- [ ] `/validate-agents` запущен, отчёт зафиксирован.
- [ ] Разрывы цепности high severity — закрыты.
- [ ] returnTo валидны (указывают на существующих агентов раньше в графе).
- [ ] Артефакты совместимы на всех стыках.
- [ ] Повторный запуск `/validate-agents` подтверждает отсутствие high-нарушений.

### Фаза 4. Error Handling Coverage

**Цель.** Документировать поведение оркестратора при edge cases.

#### Шаг 4.1. Каталог edge cases

Идентифицировать и документировать все edge cases оркестратора:

| #   | Edge case                                   | Текущее поведение    | Ожидаемое поведение                       |
| --- | ------------------------------------------- | -------------------- | ----------------------------------------- |
| E1  | Агент не вернул JSON-блок                   | Не определено        | Treat as verdict: fail, повтор 1 раз      |
| E2  | Агент вернул невалидный JSON                | Не определено        | Treat as verdict: fail, повтор 1 раз      |
| E3  | `agent_id` невалиден при resume             | Не определено        | Создать нового агента, записать warning   |
| E4  | Файл из scope не существует                 | DoR агента отловит   | Оркестратор валидирует до запуска агента  |
| E5  | Context window exceeded (агент не завершил) | Не определено        | Создать нового агента с summary контекста |
| E6  | Все тесты проходят на фазе Test (нет red)   | spec-implementer DoR | Оркестратор проверяет до запуска          |
| E7  | Пользователь прервал цикл                   | Не определено        | Записать partial execution log            |

**Критерий приёмки:**

- [ ] Каталог edge cases создан.
- [ ] Для каждого edge case определено ожидаемое поведение.

#### Шаг 4.2. Обновление SKILL.md

Добавить секцию «Обработка нештатных ситуаций» с описанием поведения
при каждом edge case.

**Критерий приёмки:**

- [ ] SKILL.md содержит секцию с edge cases E1-E7.
- [ ] Каждый edge case описывает конкретное действие оркестратора.

### Фаза 5. Прозрачность (Execution Log)

**Цель.** Каждый запуск цикла оставляет структурированный след, пригодный
для post-mortem анализа.

#### Шаг 5.1. Формат execution log

Определить JSON-формат лога одного прогона цикла.

**Формат записи (один агент):**

```json
{
  "agent": "spec-writer",
  "phase": "specify",
  "mode": "new",
  "timestamp_start": "ISO 8601",
  "timestamp_end": "ISO 8601",
  "verdict": "pass",
  "findings_count": 0,
  "findings_high": 0,
  "artifacts": ["docs/backend/categories.md"],
  "return_to": null,
  "resumed_from": null
}
```

**Формат лога цикла:**

```json
{
  "cycle_id": "UUID",
  "timestamp_start": "ISO 8601",
  "timestamp_end": "ISO 8601",
  "scope": ["docs/backend/categories.md"],
  "status": "completed",
  "iterations": 8,
  "retries": 1,
  "agents": [
    /* массив записей агентов */
  ],
  "validation_pipeline": {
    "format": "pass",
    "build": "pass",
    "lint": "pass",
    "test": "pass"
  }
}
```

**Критерий приёмки:**

- [ ] Формат описан и добавлен в agent-protocol.md.

#### Шаг 5.2. Интеграция в SKILL.md

Оркестратор ведёт лог в процессе работы и выводит его в сводке.

**Изменения:**

- SKILL.md → секция «Цикл»: добавить инструкцию вести JSON-лог.
- SKILL.md → секция «Сводка»: добавить вывод лога.

**Критерий приёмки:**

- [ ] SKILL.md содержит инструкцию записывать JSON-лог.
- [ ] Секция «Сводка» включает вывод лога цикла.
- [ ] Один реальный прогон цикла — лог записан и корректен.

#### Шаг 5.3. Ретроспектива

Расширить секцию «Сводка» структурированной ретроспективой.

**Формат ретроспективы:**

```text
## Ретроспектива

### Метрики
- Агентов запущено: N
- Возвратов: M (фаза: причина)
- Валидационный пайплайн: pass/fail

### Что прошло гладко
- ...

### Что потребовало возвратов
- Фаза X: причина (finding type, severity)

### Реализованные сценарии
- ...
```

**Критерий приёмки:**

- [ ] SKILL.md → секция «Сводка» содержит шаблон ретроспективы.

### Детальная оценка

#### #14. Частичное выполнение цикла

**Суть.** Пользователь может запросить выполнение отдельных фаз: только написание
спецификации, только извлечение тестов, только ревью.

**Оценка.** Текущий SKILL.md описывает только полный цикл. Технически агенты
уже можно вызвать напрямую (через subagent_type), но SKILL.md не описывает
этот режим — пользователь не знает о возможности, и не определены DoR/DoD
для частичного запуска. Это критически важно для отладки системы: при обнаружении
проблемы в ревью нужно перезапустить одну фазу, а не весь цикл.

**Разбиение.** Не требуется — это одна задача.

**Открытый вопрос: DoR/DoD при частичном запуске.**

При частичном выполнении цикла возникает вопрос: применять ли DoR/DoD уровня
**скила** (SKILL.md) или достаточно DoR/DoD конкретных **агентов** запрашиваемых
фаз? Аргументы:

- DoR/DoD скила описывает полный цикл (все 3 reviewer'а прошли, status = implemented) —
  они неприменимы к частичному запуску.
- DoR/DoD агентов уже проверяют preconditions своей фазы (status: ready, файлы существуют).
- Однако скилу нужна минимальная валидация входных параметров (scope валиден,
  запрашиваемая фаза существует) и определение выхода (что возвращается
  при частичном выполнении).

**Решение:** При частичном запуске скилу ТРЕБУЕТСЯ определить собственные
компактные DoR/DoD для каждого режима (валидация параметров, формат вывода),
а DoR/DoD конкретных агентов применяются как есть.

**Реализация:**

- Добавить в SKILL.md секцию «Режимы запуска»: полный цикл, отдельная фаза,
  диапазон фаз (specify → test, test → implement).
- Для каждого режима определить: входные параметры, DoR скила (валидация
  параметров и предусловий), DoD скила (что считать успехом), формат вывода.
- Определить, когда частичный запуск допустим (артефакты предыдущих фаз
  существуют и актуальны).

**Когда:** до начала Level 3 (самостоятельная задача, не зависит от плана).

#### #15. Детерминация context

**Суть.** Поле context в промпте агента (свободный текст) семантически размыто.
Два разных context'а формально оба `string`, но содержат принципиально разную
информацию в зависимости от перехода.

**Оценка.** Валидное наблюдение. Из исследования ([agent-as-program.md](agent-as-program.md)):
контракт гарантирует форму, но не содержание. Это снижает предсказуемость
агентов и затрудняет верификацию. DSPy решает эту проблему через Signatures —
типизированные I/O контракты.

**Разбиение.** Да, на два шага:

**15a. Типизация context по переходам.** Для каждого перехода в графе определить,
что именно содержит context:

| Переход                          | Тип context                               |
| -------------------------------- | ----------------------------------------- |
| orchestrator → spec-writer (new) | Описание функциональности от пользователя |
| spec-reviewer → spec-writer      | Reviewer report (findings[])              |
| orchestrator → test-deriver      | (пустой — всё в scope)                    |
| test-reviewer → test-deriver     | Reviewer report (findings[])              |
| orchestrator → spec-implementer  | (пустой — всё в scope)                    |
| impl-reviewer → spec-implementer | Reviewer report (findings[])              |
| impl-reviewer → spec-writer      | Reviewer report (findings[], direction[]) |

Это формализация того, что уже de facto происходит, но не задокументировано.

**15b. Шаблоны содержимого context.** Для каждого типа context определить
минимальный набор полей (шаблон). Пример для reviewer report:

```text
context:
Отчёт <agent-name>.

findings:
1. [type] [severity] file:line — описание
...

summary: <текст>
returnTo: <agent-name>
```

**Зависимость:** #19a (header контракт). Типизация context возможна только
после формализации контрактов агентов (что агент принимает, что отдаёт).
Сначала — описать header каждого агента (входы, выходы, quality gates),
затем — определить что именно передаётся в context на каждом переходе.

**Когда:** Level 3, Фаза 3 (inter-agent lint, шаг 3.3 — типизация артефактов).
Выполняется после Фазы 1 (#19a). 15a — обязательно, 15b — рекомендуется.

#### #16. Параметр human-in-the-loop / auto

**Суть.** Передавать параметр, определяющий, может ли агент задавать вопросы
пользователю (AskUserQuestion) или работает автономно.

**Оценка.** Эта идея рассматривалась в [§ 1.5](agent-sop-patterns.md#15-режимы-работы-interactive--auto) и была
отклонена: разделение по ролям (исполнитель/reviewer) заменяет параметрический
режим. Однако есть валидный use case, не покрытый текущим решением: **отладка
самой системы**. При разработке/настройке агентов полезно видеть промежуточные
решения и подтверждать их.

Реализация требует:

- Параметр `mode: "auto" | "interactive"` в промпте агента.
- Изменение поведения агента: в interactive — запрашивать подтверждение перед
  записью файлов и на ключевых развилках.
- Передача параметра через оркестратор.

**Когда:** Level 4. Текущая система ещё не проходит достаточно прогонов, чтобы
оценить, где interactive mode действительно нужен. После сбора baseline metrics
(Фаза 7) станет ясно, на каких фазах чаще всего происходят возвраты — это
и есть кандидаты для interactive breakpoints.

#### #17. Транслятор код → спецификация

**Суть.** Reverse engineering: генерация спецификаций из существующего кода.
Аналог CodeSpeak bidirectional sync.

**Оценка.** Критически важная функциональность для adoption существующих проектов.
Без неё интеграция spec-cycle в проект с уже написанным кодом требует ручного
написания спецификаций для всего существующего кода — prohibitive cost.

Реализация требует **двух новых агентов**, образующих отдельную фазу:

- **spec-extractor** — исполнитель: анализирует код (entity, service, controller,
  migration) и генерирует спецификацию в формате spec-format.md. Знает все типы
  операций (service:endpoint, library:method, etc.).
- **extraction-reviewer** — reviewer: проверяет не только валидность спецификации
  (как spec-reviewer), но и **корректность переноса** — что поведение кода
  точно отражено в спецификации, без потерь и искажений.

Использование spec-reviewer напрямую недостаточно: он проверяет качество
спецификации как документа (формат, полнота, непротиворечивость), но не
верифицирует соответствие спецификации исходному коду.

Эта фаза (extract) становится **модулем** наравне с существующими (specify,
test, implement). Артефакты фазы extract (spec-файлы) переиспользуются
как вход для фаз test и implement. Получается модульная система, в которой
фазы как модули могут комбинироваться:

```text
Greenfield:  specify → test → implement
Adoption:    extract → test → implement
Update:      specify (fix) → test → implement
```

Каждый модуль имеет собственный интерфейс (header), понятную зону
ответственности и инкапсулированную логику. Это закладывает основу для
фреймворка (#21), но без преждевременного обобщения.

**Когда:** Level 4 (adoption). Предусловие: headers (#19a) формализованы,
чтобы новая фаза extract могла подключаться к графу через типизированные
интерфейсы.

#### #18. Spec stubs для существующего кода

**Суть.** Минимальные spec-файлы для модулей, которые реализованы, но не имеют
формальных спецификаций. Аналог `// @ts-ignore` или `any` в TypeScript.

**Оценка.** Прагматичный механизм adoption. Позволяет:

- Зафиксировать границы формализованной части системы.
- Постепенно заменять stubs на полные specs (техдолг).
- Агентам знать о существовании модулей без полной спецификации.

Однако текущий проект — **greenfield**: весь код пишется через spec-cycle,
спецификации создаются до имплементации. Stubs нужны при adoption существующих
проектов, где код уже написан без спецификаций. Реализация stubs без реального
use case приведёт к speculative design.

Реализация (при необходимости):

- Новый `status: stub` в YAML front matter.
- Минимальная структура: summary, description, maps_to, перечень операций
  (только заголовки, без Вход/Поведение/Расширения/Результат).
- spec-reviewer, test-deriver, spec-implementer пропускают stub-спецификации.
- Обновить CLAUDE.md → «Статусы» с описанием `stub`.

**Когда:** Level 4 (adoption). Реализовать совместно с #17 (транслятор
код → спецификация) — stubs как промежуточный формат при постепенной
формализации существующего кода.

#### #19. Header/implementation разделение агентов

**Суть.** Разделить определение агента на:

- **Header** (контракт): DoR, DoD, вход/выход, артефакты, returnTo — видим
  оркестратору и другим агентам.
- **Implementation** (детали): правила, troubleshooting, подготовка — нужны
  только самому агенту.

**Оценка.** Сильная идея с несколькими преимуществами:

- Снижает token consumption: оркестратор читает только headers.
- Делает контракты machine-parseable: header можно валидировать скриптом.
- Линтинг (Фаза 2-3) работает преимущественно с headers.
- Аналогия с header files из C/C++ точна.

**Разбиение.** Да:

**19a. Логическое разделение (виртуальный header).** Формализовать, какие секции
агента составляют «контракт» и документировать это в `agent-protocol.md`.
Не требует физического разделения файлов — только маркировка: «эти секции =
header, эти = implementation». Lint-правила (Фаза 2) проверяют header-секции.

Header отображает четыре аспекта контракта:

1. **Намерение** — что агент делает и зачем (аналог purpose/intent).
2. **Вход** — что агент принимает (типы scope, типы context).
3. **Выход** — что агент возвращает (типы артефактов, допустимые returnTo).
4. **Quality gates** — DoR/DoD для валидации и стыковки с другими агентами.

Секции контракта (header):

- YAML front matter: `name`, `model`, `description` (намерение)
- Вводный абзац агента (расширенное описание намерения и зоны ответственности)
- Вход: типы scope (spec files, test files, impl files), типы context
  по переходам (описание функциональности, reviewer report, пустой)
- Выход: типы артефактов (spec files, test files, impl files, отчёт),
  допустимые значения returnTo
- Definition of Ready (quality gate входа)
- Definition of Done (quality gate выхода)

Секции реализации (implementation):

- Определение режима
- Правила написания
- Нештатные ситуации
- Подготовка / Анализ
- Завершение

**19b. Физическое разделение файлов.** Вынести header в отдельный файл
(например, `spec-writer.header.md` и `spec-writer.md`). Оркестратор читает
только header; агент читает оба файла при запуске.

**Когда:** 19a — Level 3, Фаза 1-2 (agent-protocol + intra-agent lint). Логическое
разделение формализуется в `agent-protocol.md`, lint-правила проверяют header-секции.
19b — Level 4, когда token consumption станет измеримой проблемой (после
baseline metrics).

#### #20. Внешние скрипты для логирования (JSONL)

**Суть.** Вместо того чтобы LLM-агент конструировал JSON-строки, использовать
shell-скрипты для записи логов. Формат JSONL (одна JSON-строка на запись).

**Оценка.** Валидная оптимизация:

- LLM ненадёжен при генерации строго форматированного JSON.
- JSONL лучше одного JSON-файла: append-only, не ломается при прерывании,
  каждая строка — самодостаточная запись.
- Shell-скрипт (`scripts/log-agent.sh`) принимает параметры и записывает
  JSONL — детерминистично, не тратит токены.

Пример: `scripts/log-agent.sh --agent spec-writer --verdict pass --artifacts "docs/backend/x.md"`.

Ограничение: оркестратор (SKILL.md) работает как промпт для LLM, не как
программа. Вызов скрипта через Bash tool возможен, но увеличивает число
tool calls. Компромисс: скрипт для записи + LLM для интерпретации.

**Когда:** Level 4. На Level 3 execution log записывается оркестратором
в сводке (простейший формат, без внешних скриптов). При переходе к Level 4,
когда появятся baseline metrics и станет ясно, насколько надёжен LLM
при генерации JSON, принять решение о внедрении JSONL + скриптов.

#### #21. Фреймворк для project-specific workflows

**Суть.** Превратить spec-cycle в генерируемый/конфигурируемый фреймворк:
разные проекты определяют свои workflow (spec-driven, простой code review,
RAG pipeline и т.д.).

**Оценка.** Это **Level 4+** (Optimized → Platform) — кардинальная смена scope.
Текущая система — domain-specific инструмент для одного проекта. Фреймворк
требует:

- Декларативный формат описания графа (не процедурный SKILL.md).
- Pluggable agent types (пользователь определяет своих агентов).
- Конфигурируемые quality gates (не hardcoded DoR/DoD).
- Генерация SKILL.md из конфигурации.
- Документация, примеры, шаблоны.

Это полезная долгосрочная vision, но преждевременная оптимизация для текущего
состояния. Текущая система должна пройти Level 3 (валидирована) и Level 4
(оптимизирована по метрикам), прежде чем обобщать.

Однако некоторые решения Level 3 закладывают фундамент:

- Manifest (Фаза 1) = зачаток декларативного описания.
- Header/impl split (#19a) = зачаток pluggable agents.
- Типизация context (#15a) = зачаток typed graph edges.

**Когда:** post-Level 4. Не включать в текущий план. Держать как north star.

#### #22. Research файлы → база знаний агентов

**Суть.** Трансформировать `.claude/docs/` research файлы в промпты/знания,
которые агенты используют для повышения качества работы.

**Оценка.** Сейчас research файлы (`spec-driven-testing.md`, `agent-sop-patterns.md`,
`dor-dod-criteria.md`) — документация для человека. Агенты не читают их
систематически. Но они содержат ценные паттерны и решения:

- `spec-driven-testing.md` → алгоритм извлечения тестов (нужен test-deriver)
- `dor-dod-criteria.md` → мета-критерии DoR/DoD (нужен reviewer'ам)
- `agent-sop-patterns.md` → правила написания инструкций (нужен при создании
  новых агентов)

Два подхода:

- **Прямая ссылка**: добавить research файлы в секции «Общие документы»
  соответствующих агентов. Простейший подход, но увеличивает token consumption.
- **Экстракт**: извлечь ключевые правила/паттерны в компактные reference sheets
  и ссылаться на них. Аналог: «скомпилировать» research в «заголовки».

Рекомендуется второй подход, начиная с самого ценного:

- `spec-driven-testing.md` → test-deriver уже содержит алгоритм извлечения;
  дублирование не нужно. Но можно добавить ссылку в «Общие документы».
- `dor-dod-criteria.md` → полезен для reviewer'ов. Добавить ссылку.

**Когда:** Level 4. Сейчас research файлы — информация для принятия решений,
не для регулярного использования агентами. На Level 3 фокус — структурная
валидация и observability; интеграция knowledge base — оптимизация качества
работы агентов, что относится к Level 4.
