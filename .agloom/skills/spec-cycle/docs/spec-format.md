# Формат спецификации

Формат описания операций и правила написания спецификаций (`type: spec`).

Ключевые слова «ТРЕБУЕТСЯ», «ЗАПРЕЩАЕТСЯ», «ДОЛЖЕН», «НЕ ДОЛЖЕН», «СЛЕДУЕТ»,
«НЕ СЛЕДУЕТ», «МОЖЕТ» и «НЕОБЯЗАТЕЛЬНО» в этом документе толкуются
в соответствии с [RFC 2119](https://tools.ietf.org/html/rfc2119).

## Операция

Операция — единица поведения системы. Каждая операция ДОЛЖНА содержать
секции: заголовок с типом операции, Вход, Поведение, Расширения, Результат.

### Типы операций

| Тип                      | Описание                   | Файл               | Статус      |
| ------------------------ | -------------------------- | ------------------ | ----------- |
| `service:endpoint`       | HTTP endpoint              | `types/service.md` | описан      |
| `service:bootstrap`      | Инициализация модуля       | `types/service.md` | описан      |
| `service:shutdown`       | Graceful shutdown          | `types/service.md` | описан      |
| `service:event`          | Обработчик события         | `types/service.md` | планируется |
| `service:cron`           | Запланированная задача     | `types/service.md` | планируется |
| `library:initialization` | Создание экземпляра        | `types/library.md` | описан      |
| `library:method`         | Публичный метод            | `types/library.md` | описан      |
| `cli:command`            | CLI-команда                | `types/cli.md`     | описан      |
| `cli:procedure`          | Переиспользуемая процедура | `types/cli.md`     | описан      |
| `cli:command-ext`        | Расширение команды         | `types/cli.md`     | описан      |
| `web:action`             | Действие в UI              | —                  | планируется |
| `web:input`              | Ввод данных в UI           | —                  | планируется |

Пути к файлам указаны относительно этого документа. Агент загружает файл типа
по необходимости.

Формат секций Вход и Результат зависит от типа. Секции Поведение и Расширения —
общие для всех типов.

### Общие правила

#### Стандартная вставка RFC 2119

Каждая спецификация (`type: spec`) ДОЛЖНА содержать в начале документа
(после front matter) блок:

```text
Ключевые слова «ТРЕБУЕТСЯ», «ЗАПРЕЩАЕТСЯ», «ДОЛЖЕН», «НЕ ДОЛЖЕН», «СЛЕДУЕТ»,
«НЕ СЛЕДУЕТ», «МОЖЕТ» и «НЕОБЯЗАТЕЛЬНО» в этом документе толкуются
в соответствии с [RFC 2119](https://tools.ietf.org/html/rfc2119).
```

Таблица соответствий и правила использования описана в `agent-protocol.md`
в разделе «Ключевые слова».

#### Форматирование секций

Названия секций (Вход, Поведение, Расширения, Результат) ТРЕБУЕТСЯ оформлять
жирным текстом с двоеточием. Между названием секции и содержимым ТРЕБУЕТСЯ
пустая строка:

```text
**Поведение:**

1. Шаг.
2. Шаг.
```

#### Поведение

Каждый шаг ДОЛЖЕН описывать одно наблюдаемое действие. Формулировки,
содержащие «и», ТРЕБУЕТСЯ разделять на отдельные шаги. Побочные эффекты
(запись в БД, обращение к внешней системе) ТРЕБУЕТСЯ описывать явными шагами.

#### Расширения

Для каждого шага, который может завершиться неудачей, ТРЕБУЕТСЯ расширение
с результатом. При отсутствии расширений ТРЕБУЕТСЯ явно указать
«Нет расширений». Каждое расширение ДОЛЖНО ссылаться на номер шага
(2a, 3b и т.д.). Если несколько расширений намеренно неразличимы —
это ТРЕБУЕТСЯ указать явно.

#### Нотация обязательности

- `обязательно` — параметр ДОЛЖЕН быть передан.
- `опционально` — параметр МОЖЕТ отсутствовать. При наличии значения
  по умолчанию ТРЕБУЕТСЯ указать `default: <значение>`.

#### Вложенные структуры

Вложенные структуры ТРЕБУЕТСЯ описывать через отступ:

```text
- `items` (array, обязательно) — элементы для обновления.
  - `id` (UUID, обязательно) — идентификатор элемента.
  - `position` (integer, обязательно) — новая позиция.
```

#### Enum-значения

Enum-значения ТРЕБУЕТСЯ указывать в скобках после типа:

```text
- `type` (string: "income" | "expense" | "transfer", обязательно) — тип транзакции.
```

#### Маркеры неопределённости

`[NEEDS CLARIFICATION]` — маркер нерешённых вопросов.
Спецификация со `status: ready` НЕ ДОЛЖНА содержать такие маркеры.

## Качество требований (ISO/IEC/IEEE 29148)

Каждый пункт спецификации ДОЛЖЕН быть:

- **Verifiable** — возможно написать тест, проверяющий соответствие.
- **Complete** — описано поведение при всех условиях, включая ошибочные.
- **Unambiguous** — допускается только одна интерпретация.

## Источник истины

При противоречиях между источниками приоритет определяется от частного к общему:

1. Явное указание от пользователя.
2. Реализация (код).
3. Специализированная спецификация (`docs/backend/*.md`).
4. Общая спецификация (`docs/database/index.md`).

ЗАПРЕЩАЕТСЯ выдумывать бизнес-логику, которой нет в источниках.

## Тон и стиль

Спецификации продукта (`type: spec`) пишутся в третьем лице. Обращения
ко второму лицу (императив «выполни», «проверь», «укажи») ЗАПРЕЩАЮТСЯ,
потому что третье лицо устраняет неоднозначность адресата и делает
спецификацию пригодной для механического извлечения тестов.

Неверно:

> Не выдумывай бизнес-логику, которой нет в источниках.

Верно:

> ЗАПРЕЩАЕТСЯ выдумывать бизнес-логику, которой нет в источниках.
