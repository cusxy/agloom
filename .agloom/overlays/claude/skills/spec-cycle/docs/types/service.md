# Типы операций: service

Операции backend-сервиса (NestJS).

## service:endpoint

HTTP endpoint — обработка входящего HTTP-запроса.

### Шаблон

```text
### <Название операции>

`<HTTP-метод> <путь>` — <контекст доступа>.

**Вход:**

Path:

- `:param` (тип) — описание.

Query:

- `param` (тип, опционально, default: значение) — описание.

Body:

- `field` (тип, обязательно) — описание.

**Поведение:**

1. <Шаг — одно наблюдаемое действие>.
2. <Шаг>.
N. <Финальный шаг>.

**Расширения:**

2a. <Условие отклонения> → <HTTP-статус> <сообщение>.
3a. <Условие отклонения> → <результат>.

**Результат:**

<HTTP-статус>.

- `field` (тип) — описание.
```

### Вход

Параметры сгруппированы по источнику:

- **Path** — параметры из пути (`:id`, `:accountId`). Обязательность не указывается —
  path-параметры всегда обязательны.
- **Query** — параметры строки запроса. Указывать обязательность и значение
  по умолчанию.
- **Body** — поля тела запроса (JSON). Указывать обязательность.
- Группы без параметров опускаются. Если у операции нет входных параметров —
  указать "Нет входных параметров".

### Результат

HTTP-статус и список полей тела ответа с типами — в том же формате, что и Body
во Вход. Вложенные структуры и массивы — через отступ.

Если операция не возвращает тела — указать только статус (например,
`204 No Content.`).

### Контекст доступа

Строка после HTTP-метода и пути описывает требования к авторизации:

- `публичный` — эндпоинт без авторизации (`@Public()`).
- `авторизованный пользователь` — любой аутентифицированный пользователь.
- `scope: <значение>` — требуется API-токен с указанным scope (`@RequireScope`).
- `только сессия` — недоступен через API-токен (`@SessionOnly()`).

Допускается комбинация: `авторизованный пользователь, scope: finance:read`.

### Пример

```text
### Корректировка баланса

`POST /accounts/:id/adjust` — авторизованный пользователь, scope: finance:write.

**Вход:**

Path:

- `:id` (UUID) — идентификатор аккаунта.

Body:

- `target_balance` (string, обязательно) — целевой баланс.
- `description` (string, опционально) — описание корректировки.

**Поведение:**

1. Найти аккаунт по `id` и `user_id` текущего пользователя.
2. Валидировать точность `target_balance` по `Currency.decimal_places` валюты аккаунта.
3. Вычислить `delta = target_balance - account.balance`.
4. Создать транзакцию типа `adjustment` с `amount = delta`.
5. Обновить `account.balance = target_balance` в той же DB-транзакции.

**Расширения:**

1a. Аккаунт не найден или не принадлежит пользователю → 404 "Account not found".
2a. Точность `target_balance` превышает `decimal_places` → 422 "Invalid precision".
3a. `delta = 0` → 422 "Adjustment not needed".

**Результат:**

201 Created.

- `id` (UUID) — идентификатор транзакции.
- `type` (string) — "adjustment".
- `amount` (string) — сумма корректировки (знаковая).
- `description` (string | null) — описание.
- `created_at` (ISO 8601) — дата создания.
```

## service:bootstrap

Инициализация модуля — подготовка ресурсов при запуске приложения.
В NestJS реализуется через `onModuleInit()` или логику в `main.ts`.

### Шаблон

```text
### <Название>

`bootstrap: <модуль>`.

**Вход:**

- `PARAM` (тип, обязательно) — описание.

**Поведение:**

1. <Шаг инициализации>.
2. <Шаг>.

**Расширения:**

1a. <Условие> → <результат (завершить процесс / retry / fallback)>.

**Результат:**

<Модуль> готов к обработке запросов.
```

### Вход

Конфигурация модуля: переменные окружения, параметры `forRoot()`/`forRootAsync()`,
инжектируемые зависимости. Обязательность и типы — по общим правилам.

### Результат

Описание готовности модуля: какие ресурсы инициализированы, какие зависимости
доступны для инъекции.

### Расширения

Ошибки инициализации обычно фатальны — сервис не может работать без ключевого
ресурса. Типичные результаты расширений:

- Завершить процесс с ошибкой.
- Повторить попытку (retry с backoff).
- Использовать fallback (например, in-memory кеш вместо Redis).

### Пример

```text
### Подключение к базе данных

`bootstrap: DatabaseModule`.

**Вход:**

- `DB_HOST` (string, обязательно) — хост PostgreSQL.
- `DB_PORT` (number, опционально, default: 5432) — порт.
- `DB_NAME` (string, обязательно) — имя базы данных.
- `DB_USER` (string, обязательно) — пользователь.
- `DB_PASS` (string, обязательно) — пароль.

**Поведение:**

1. Создать пул соединений к PostgreSQL с указанными параметрами.
2. Проверить доступность базы данных (тестовый запрос).
3. Выполнить pending-миграции.

**Расширения:**

1a. Невозможно установить соединение → завершить процесс с ошибкой.
3a. Миграция завершилась ошибкой → откатить миграцию, завершить процесс с ошибкой.

**Результат:**

DatabaseModule готов: пул соединений активен, схема БД актуальна.
```

## service:shutdown

Graceful shutdown — освобождение ресурсов при остановке приложения.
В NestJS реализуется через `onModuleDestroy()` или `beforeApplicationShutdown()`.

### Шаблон

```text
### <Название>

`shutdown: <модуль>`.

**Поведение:**

1. <Шаг завершения>.
2. <Шаг>.

**Расширения:**

Нет расширений.

**Результат:**

<Ресурсы> освобождены.
```

### Вход

Операция shutdown обычно не принимает входных параметров — модуль использует
ресурсы, полученные при инициализации. Если параметры необходимы (таймаут
ожидания, флаг force) — описать по общим правилам.

### Результат

Описание освобождённых ресурсов: закрытые соединения, остановленные таймеры,
отменённые подписки.

### Пример

```text
### Остановка базы данных

`shutdown: DatabaseModule`.

**Поведение:**

1. Дождаться завершения активных запросов (таймаут 30с).
2. Закрыть пул соединений к PostgreSQL.

**Расширения:**

1a. Таймаут ожидания превышен → принудительно закрыть соединения.

**Результат:**

Пул соединений к PostgreSQL закрыт.
```
