# Исследование: спецификации как источник тестовых сценариев

Дата: 2026-03-14

## Контекст исследования

Проект использует Test Driven Development (TDD) для верификации поведения системы. Тесты должны проверять реальное
поведение с минимальным использованием моков (классическая школа TDD), а тестовые сценарии — выводиться из спецификаций,
а не придумываться ad hoc.

Текущие спецификации (`docs/backend/*.md`) описывают поведение системы в произвольной форме: шаги алгоритма без явного
указания ошибочных сценариев, неявные трансформации входных данных, неуказанная транзакционность. Из такого описания
невозможно систематически извлечь полный набор тестовых сценариев — часть поведения выводится только из чтения кода.

Цель исследования — определить подход к написанию спецификаций, который:

1. Обеспечивает систематическое извлечение тестовых сценариев.
2. Соответствует критериям качества требований ISO/IEC/IEEE 29148:2018.
3. Не создаёт избыточных накладных расходов для небольшой команды.

## Часть 1. Написание спецификаций

### Критерии качества требований (ISO/IEC/IEEE 29148:2018)

Стандарт определяет характеристики хорошего требования. Для контекста проекта выделены три критичные характеристики,
непосредственно влияющие на возможность извлечения тестов:

| Характеристика  | Определение                                              | Типичное нарушение в текущих спецификациях              |
| --------------- | -------------------------------------------------------- | ------------------------------------------------------- |
| **Verifiable**  | Можно спроектировать тест, проверяющий соответствие      | "Ищет User по email" — нет критерия проверки            |
| **Complete**    | Описывает поведение при всех условиях, включая ошибочные | Ошибочные сценарии не описаны                           |
| **Unambiguous** | Допускает только одну интерпретацию                      | "Создаёт User и AuthProvider" — транзакционность неясна |

Дополнительные характеристики (consistent, traceable, necessary) важны, но не являются блокирующими для извлечения тестов.

Характеристики feasible и free of implementation неприменимы: реализуемость оценивается разработчиком самостоятельно,
а детали реализации (bcrypt, JWT) являются частью контракта backend-спецификации.

### Рассмотренные форматы спецификаций

#### 1. Use Cases (Alistair Cockburn)

Полный формат включает: актор, область действия, уровень, заинтересованные стороны, предусловия, постусловия, основной
сценарий, расширения (extensions), вариации.

**Плюсы:**

- Расширения (extensions) — механизм, заставляющий для каждого шага явно ответить на вопрос "что если не удалось?".
  Обеспечивает полноту ошибочных сценариев.
- Тесты выводятся механически: основной сценарий → happy path, каждое расширение → отдельный тест.
- Пропуск расширения для шага — осознанное решение ("отклонения невозможны"), а не случайность.

**Минусы:**

- Полный формат (актор, область действия, уровень, заинтересованные стороны) избыточен для команды, где один человек
  выполняет роли аналитика, разработчика и тестировщика.
- Высокие накладные расходы на поддержание полного формата при частых изменениях.

#### 2. Gherkin / BDD (Given-When-Then)

Формат из Behavior-Driven Development, используемый в Cucumber, SpecFlow и аналогах.

```gherkin
Сценарий: Успешный вход по email/паролю
  Допустим пользователь зарегистрирован с email "user@example.com"
  Когда он входит с email "User@Example.COM" и верным паролем
  Тогда система возвращает пару токенов сессии
```

**Плюсы:**

- Сценарии читаемы как документация.
- Каждый сценарий непосредственно является тестом (исполняемые спецификации).

**Минусы:**

- Описывает каждый сценарий отдельно (плоский список), а не основной поток + расширения. Отсутствует структура
  для систематической проверки полноты — нет привязки ошибочного сценария к конкретному шагу.
- Стирает границу между спецификацией и тестом, создавая два артефакта, описывающих одно и то же.
- Требует дополнительного инструментального стека поверх Jest.

#### 3. EARS (Easy Approach to Requirements Syntax)

Шаблоны для формулировки требований, разработанные в Rolls-Royce:

```text
Когда <пользователь передаёт email и пароль>, система должна
  <нормализовать email и аутентифицировать пользователя>.

Если <пользователь не найден по email>, система должна
  <вернуть 401 "Invalid credentials">.
```

**Плюсы:**

- Каждое предложение по шаблону — одно проверяемое требование.
- Простой формат, низкий порог входа.

**Минусы:**

- Плохо передаёт последовательность шагов — требования атомарны, но не связаны в сценарий.
- Не имеет механизма для систематической проверки полноты (нет привязки ошибки к шагу).

### Выбранный подход

Полноценные Use Cases, Gherkin и EARS не подходят как самостоятельные форматы. Выбран подход: **дополнение текущего
формата спецификаций расширениями (extensions) из Use Cases**.

Текущий формат (пошаговое описание поведения в markdown) сохраняется и дополняется:

- **Расширениями (extensions)** из Use Cases — для каждого шага, который может завершиться неудачей, явно описан
  результат отклонения.
- **Структурированными секциями Вход и Результат** — для явного описания входных параметров и формата ответа.

Итоговый формат операции содержит 4 обязательные секции: **Вход**, **Поведение**, **Расширения**, **Результат**.

#### Обоснование

1. **Низкая стоимость внедрения.** Не требует переписывания спецификаций — дополнение структурированными секциями.
2. **Инкрементальность.** Секции добавляются по мере написания тестов для конкретного модуля.
3. **Систематическая полнота.** Механизм расширений привязывает каждый ошибочный сценарий к конкретному шагу. Отсутствие
   расширения у шага — осознанное решение. Явные секции Вход и Результат исключают неявные предположения о параметрах
   и формате ответа.
4. **Совместимость.** Формат остаётся markdown, структура `docs/` не меняется, front matter не меняется.

### Правила написания требований

Каждое требование (пункт поведения) должно удовлетворять следующим критериям:

1. **Одно наблюдаемое поведение** (atomic). Если в формулировке есть "и" — разделить на два пункта.
2. **Проверяемость** (verifiable). Для пункта можно написать тест, который проверяет соответствие. Если нельзя —
   формулировка неполная или двусмысленная.
3. **Полнота ошибочных сценариев** (complete). Для каждого шага, который может завершиться неудачей, существует расширение
   с указанием результата.
4. **Явные трансформации** (unambiguous). Неочевидные преобразования входных данных (нормализация, хеширование,
   транзакционность) указаны явно.
5. **Отсутствие избыточности** (not over-specified). Детали, не влияющие на наблюдаемое поведение (внутренние имена
   переменных, порядок SQL-запросов внутри транзакции), не входят в спецификацию.

#### Чеклист для ревью требования

При написании или ревью каждого пункта спецификации:

- [ ] Можно ли написать тест? Если нет — формулировка неполная или двусмысленная.
- [ ] Описан ли результат при неудаче? Если шаг может не удаться — добавить расширение.
- [ ] Одно ли поведение описано? Если "и" в формулировке — разделить.
- [ ] Нет ли неявных предположений? Нормализация, транзакционность, побочные эффекты — указать явно.
- [ ] Не избыточно ли? Если убрать пункт, потеряется ли информация, нужная для написания теста?

### Формат описания операции

```markdown
### <Название операции>

`<HTTP-метод> <путь>` — <контекст доступа>.

Вход:

- `field` (тип, обязательность) — описание.

Поведение:

1. <Шаг — одно наблюдаемое действие>.
2. <Шаг>.
   N. <Финальный шаг>.

Расширения:
2a. <Условие отклонения> → <HTTP-статус> <сообщение>.
3a. <Условие отклонения> → <результат>.
3b. <Другое условие для того же шага> → <результат>.

Результат:
<HTTP-статус>. <Описание тела ответа: поля, типы, формат>.
```

Правила секций:

- **Вход** — все принимаемые параметры с типами и ограничениями (обязательность, формат, допустимые значения).
- **Поведение** — каждый шаг описывает одно наблюдаемое действие. Побочные эффекты (запись в БД, обращение к внешней
  системе) — явные шаги.
- **Расширения** — для каждого шага, который может завершиться неудачей — расширение с результатом. Если расширений
  нет — указать «Нет расширений» явно. Опциональные пояснения к группам расширений (неразличимость ошибок и т.д.)
  следуют после списка расширений.
- **Результат** — HTTP-статус и формат тела ответа при успехе (поля, типы, структура).

### Пример: текущая vs улучшенная спецификация

Текущая:

```markdown
### Вход

`POST /auth/login` — принимает `{ email, password }`.

1. Ищет User по email.
2. Ищет AuthProvider с `provider = "password"` для найденного пользователя.
3. Проверяет `bcrypt(password) == password_hash`.
4. Создаёт Session, генерирует пару токенов.
5. Возвращает токены через httpOnly-cookie.
```

Проблемы: входные параметры не типизированы, нормализация email не указана, ошибочные сценарии
отсутствуют, неразличимость ошибок не зафиксирована, формат ответа не описан.

Улучшенная:

```markdown
### Вход

`POST /auth/login` — публичный эндпоинт.

Вход:

- `email` (string, обязательный) — email пользователя.
- `password` (string, обязательный) — пароль.

Поведение:

1. Email нормализуется к нижнему регистру.
2. Ищет User по нормализованному email.
3. Ищет AuthProvider с `provider = "password"` для найденного пользователя.
4. Проверяет пароль через bcrypt.
5. Создаёт Session, генерирует пару токенов.
6. Устанавливает токены в httpOnly-cookie (`access_token`, `refresh_token`).

Расширения:
2a. Пользователь не найден → 401 "Invalid credentials".
3a. Password-провайдер отсутствует → 401 "Invalid credentials".
4a. Пароль неверный → 401 "Invalid credentials".

Ошибки 2a, 3a, 4a намеренно неразличимы (защита от user enumeration).

Результат: 200. Тело: `{ accessToken: string, refreshToken: string }`. Токены также
устанавливаются в httpOnly-cookie.
```

## Часть 2. Извлечение тестовых сценариев из спецификации

### Философия тестирования

Проект следует классической (Detroit) школе TDD:

- **Реальные объекты** — предпочитаются везде, где возможно. Моки используются только для неуправляемых внешних
  зависимостей (external HTTP API), которые не контролируются разработчиком.
- **Поведение, а не реализация** — тест проверяет наблюдаемый результат (возвращаемое значение, состояние в БД, HTTP-ответ),
  а не порядок вызовов или внутреннюю структуру.
- **Устойчивость к рефакторингу** — рефакторинг без изменения поведения не должен ломать тесты. Если ломает — тест
  проверяет детали реализации и должен быть переписан.

Источники: Kent Beck — _TDD: By Example_, Vladimir Khorikov — _Unit Testing: Principles, Practices, and Patterns_.

### Классификация зависимостей (по Khorikov)

| Тип зависимости | Определение                     | Примеры в проекте               | Стратегия в тестах                   |
| --------------- | ------------------------------- | ------------------------------- | ------------------------------------ |
| **Managed**     | Контролируется разработчиком    | PostgreSQL, TypeORM-репозитории | Реальная (testcontainers или аналог) |
| **Unmanaged**   | Не контролируется разработчиком | CurrencyBeacon API, CoinAPI     | Мок или стаб                         |
| **Внутренняя**  | Другой сервис внутри приложения | SessionService, TokenService    | Реальная (если поднята БД)           |

bcrypt — реальный. Детерминистичен для проверки (`compare` всегда возвращает корректный результат для пары
пароль/хеш), мокание удаляет проверку того, что хеширование работает.

### Алгоритм извлечения тестовых сценариев

Для каждой операции в спецификации:

**Шаг 1. Happy path.** Основной сценарий (все шаги выполнены успешно) → один тест.

**Шаг 2. Расширения.** Каждое расширение (Na) → один тест. Тест проверяет:

- Условие отклонения выполняется.
- Система возвращает указанный результат (HTTP-статус, сообщение).
- Побочные эффекты не произошли (если применимо — например, User не создан при откате транзакции).

**Шаг 3. Неочевидные поведенческие аспекты.** Для каждого шага, содержащего трансформацию (нормализация, хеширование,
транзакционность) → отдельный тест, проверяющий трансформацию.

**Шаг 4. Кросс-расширения.** Если несколько расширений намеренно неразличимы (как ошибки 2a/3a/4a в примере входа) →
один тест, проверяющий одинаковость ошибок.

### Пример: извлечение тестов для операции "Вход"

Из улучшенной спецификации:

```text
Спецификация                    → Тестовый сценарий
────────────────────────────────────────────────────────────────────────────────
Шаги 1-6 (happy path)          → аутентифицирует пользователя с корректными
                                  данными и возвращает токены
Шаг 1 (нормализация)           → нормализует email к нижнему регистру
Расширение 2a                   → отклоняет вход с несуществующим email
Расширение 3a                   → отклоняет вход если у пользователя нет
                                  password-провайдера
Расширение 4a                   → отклоняет вход с неверным паролем
Примечание к 2a/3a/4a           → возвращает одинаковую ошибку для всех случаев
                                  неудачного входа
```

Результат в Jest:

```typescript
describe('AuthService', () => {
  describe('login — вход по email/паролю', () => {
    it('аутентифицирует пользователя с корректными данными и возвращает токены');
    it('нормализует email к нижнему регистру');
    it('отклоняет вход с несуществующим email');
    it('отклоняет вход если у пользователя нет password-провайдера');
    it('отклоняет вход с неверным паролем');
    it('возвращает одинаковую ошибку для всех случаев неудачного входа');
  });
});
```

### Чего не должно быть в тестах

1. **Проверка порядка вызовов.** "Сначала вызвался `findOne`, потом `save`" — деталь реализации. Если результат
   правильный, порядок не важен.
2. **Проверка прокидывания параметров.** Если параметр передаётся без трансформации в другой сервис — это проверка того,
   что TypeScript передаёт аргументы функций. Поведение принимающего сервиса тестируется в его собственных тестах.
3. **Проверка типов возврата.** Структура `SessionTokens` гарантируется TypeScript на этапе компиляции. Тестировать
   наличие полей `accessToken` и `refreshToken` — тестировать компилятор.
4. **Тесты ради code coverage.** Если тест не проверяет требование из спецификации — он не нужен.

### Структура тестовых файлов

Тестовые файлы зеркалят структуру спецификаций:

```text
docs/backend/auth.md → "Регистрация"        → auth.service.spec.ts → describe('register')
docs/backend/auth.md → "Вход"               → auth.service.spec.ts → describe('login')
docs/backend/auth.md → "Сессии"             → session.service.spec.ts
docs/backend/auth.md → "API-токены"         → api-token.service.spec.ts
```

Traceability обеспечивается структурным соответствием: секция спецификации → `describe`-блок теста. Формальная
матрица трассировки (requirements traceability matrix) не требуется.

## Заключение

| Решение                              | Выбор                                                       |
| ------------------------------------ | ----------------------------------------------------------- |
| Формат спецификаций                  | Markdown с 4 секциями (Вход/Поведение/Расширения/Результат) |
| Школа TDD                            | Классическая (Detroit): реальные объекты, минимум моков     |
| Стратегия для managed-зависимостей   | Реальная БД (testcontainers)                                |
| Стратегия для unmanaged-зависимостей | Моки/стабы                                                  |
| Извлечение тестов                    | Механическое: happy path + расширения + трансформации       |
| Структура тестов                     | Зеркалит структуру спецификаций                             |
