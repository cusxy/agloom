# Исследование: критерии качества инструкций для AI coding-агентов

Дата: 2026-03-23

## Контекст исследования

### Проблема

AI coding-агенты (Claude Code, Cursor, GitHub Copilot, Windsurf и другие) используют файлы
инструкций уровня проекта (AGENTS.md, CLAUDE.md, `.cursorrules` и аналоги) для адаптации
поведения к конкретной кодовой базе. Эти файлы содержат конвенции, архитектурные решения,
команды сборки и ограничения, которые агент не может вывести из кода самостоятельно.

Качество таких файлов напрямую влияет на результат работы агента, однако устоявшихся критериев
качества не существует. Эмпирические данные (ETH Zurich, 2026) показывают, что некачественные
инструкции не просто бесполезны — они ухудшают результат по сравнению с отсутствием инструкций.

### Мотивация

Проект Acorn Budgeting активно использует файлы инструкций: `CLAUDE.md` для общего контекста,
`.claude/agents/` для определения агентов spec-cycle, `.claude/skills/` для скиллов. Понимание
критериев качества позволит:

- оценить текущее состояние собственных инструкций;
- сформулировать чеклист для написания и ревью инструкций;
- избежать эмпирически подтверждённых антипаттернов.

### Цель

Провести аудит ландшафта файлов инструкций для AI coding-агентов: форматы провайдеров,
эмпирические данные о влиянии на качество, критерии качественного файла инструкций,
рекомендуемая структура и антипаттерны.

### Границы

- Файлы инструкций уровня проекта (project-level), а не системные промпты или пользовательские
  настройки.
- Coding-агенты, а не general-purpose LLM.
- Фокус на практических рекомендациях, а не на теории промпт-инжиниринга.

## Критерии оценки (мета-критерии аудита)

Мета-критерии определены до анализа данных для защиты от anchoring bias.

| #   | Критерий           | Определение                                                            |
| --- | ------------------ | ---------------------------------------------------------------------- |
| C1  | Релевантность      | Каждая инструкция добавляет информацию, недоступную агенту из кода     |
| C2  | Лаконичность       | Файл укладывается в оптимальные размерные рамки без потери содержания  |
| C3  | Точность           | Инструкции конкретны и однозначны, содержат примеры при необходимости  |
| C4  | Структурность      | Файл организован с помощью заголовков, иерархии и логического порядка  |
| C5  | Сопровождаемость   | Инструкции легко обновлять при эволюции проекта                        |
| C6  | Непротиворечивость | Инструкции не конфликтуют между собой и с другими источниками          |
| C7  | Верифицируемость   | Соблюдение инструкций можно проверить (тестами, линтером, ревью)       |
| C8  | Портативность      | Инструкции работают через границы инструментов (при использовании > 1) |

## Ландшафт провайдеров

### Обзор форматов

| Провайдер        | Файл инструкций                      | Формат        | Иерархия | Glob-скоупинг |
| ---------------- | ------------------------------------ | ------------- | -------- | ------------- |
| Claude Code      | `CLAUDE.md`                          | Markdown      | Да       | Нет           |
| Cursor           | `.cursor/rules/*.mdc`                | MDC (MD+YAML) | Да       | Да            |
| GitHub Copilot   | `.github/copilot-instructions.md`    | Markdown      | Да       | Да            |
| Windsurf         | `.windsurf/rules/*.md`               | Markdown      | Да       | Да            |
| Cline            | `.clinerules/*.md`                   | MD+YAML       | Да       | Да            |
| Roo Code         | `.roo/rules/*.md`                    | Markdown      | Да       | Да            |
| Aider            | `CONVENTIONS.md` + `.aider.conf.yml` | Markdown+YAML | Нет      | Нет           |
| AGENTS.md (стд.) | `AGENTS.md`                          | Markdown      | Да       | Нет           |

### Claude Code — CLAUDE.md

Файл `CLAUDE.md` загружается в начале каждой сессии Claude Code и является основным механизмом
передачи проектного контекста. Поддерживается иерархия: `~/.claude/CLAUDE.md` (глобальный),
корень проекта, родительские и дочерние директории. Импорт дополнительных файлов — через
синтаксис `@path/to/file`.

**Официальные рекомендации Anthropic:**

- Держать файл коротким и читаемым для человека.
- Включать только то, что не может быть выведено из кода: bash-команды, стиль кода,
  конвенции workflow.
- Для каждой строки задавать вопрос: «Приведёт ли удаление этой строки к ошибкам Claude?»
  Если нет — удалить.
- Для критичных правил использовать эмфазу: «IMPORTANT», «YOU MUST».
- Хранить в git; итеративно улучшать при каждой ошибке агента
  («compounding engineering»).
- Специализированные инструкции выносить в skills (`.claude/skills/`), которые загружаются
  по запросу и не раздувают контекст каждой сессии.

**Плюсы:**

- Глубокая интеграция с Claude Code: иерархия файлов, `@`-импорты, skills, hooks,
  subagents.
- Поддержка progressive disclosure: CLAUDE.md → skills → agents.
- Механизм hooks для детерминированных действий (в отличие от advisory-инструкций).

**Минусы:**

- Привязка к экосистеме Claude Code; другие инструменты игнорируют файл.
- Отсутствие glob-скоупинга (в отличие от Cursor и Copilot).
- Нет формальной валидации формата — ошибки обнаруживаются только по поведению агента.

### Cursor — .cursor/rules/\*.mdc

Cursor перешёл от legacy-файла `.cursorrules` к модульной системе `.mdc` (Markdown Component)
с YAML frontmatter. Каждый файл содержит `description`, `globs` и `alwaysApply`.

**Плюсы:**

- Автоматическая активация правил по glob-паттернам (файл `.mdc` с `globs: ["*.py"]`
  применяется только при работе с Python-файлами).
- Модульность снижает token overhead: нерелевантные правила не загружаются.
- Крупнейшая коллекция community-правил (awesome-cursorrules).

**Минусы:**

- Проприетарный формат `.mdc`, не поддерживаемый другими инструментами.
- Deprecated legacy-формат создаёт путаницу при миграции.
- Отсутствие иерархии директорий (в отличие от CLAUDE.md и AGENTS.md).

### GitHub Copilot — copilot-instructions.md

GitHub Copilot использует `.github/copilot-instructions.md` для repository-wide инструкций
и `.instructions.md` с YAML frontmatter (`applyTo`) для path-specific инструкций.

**Плюсы:**

- Нативная интеграция с GitHub-экосистемой (PR, issues, code review).
- Поддержка path-specific инструкций с glob-скоупингом.
- Иерархия приоритетов: personal → repository → organization.

**Минусы:**

- Рекомендуется формат коротких самодостаточных утверждений; сложные многоуровневые
  инструкции не поддерживаются нативно.
- Ограниченная поддержка за пределами VS Code и GitHub.

### Windsurf — .windsurf/rules/\*.md

Windsurf (ранее Codeium, ныне Cognition AI) поддерживает как legacy `.windsurfrules`,
так и модульные правила в `.windsurf/rules/` с GUI-обёрткой.

**Плюсы:**

- Каскадная AI-система (Cascade) с пониманием всей кодовой базы.
- Поддержка glob-скоупинга и условной активации.
- Каталог примеров правил от команды Windsurf.

**Минусы:**

- Исторические проблемы с надёжностью обработки правил (GitHub issue #157).
- Частая смена форматов и владельцев (Codeium → Cognition).
- Меньшая экосистема по сравнению с Cursor и Claude Code.

### Cline / Roo Code — .clinerules / .roo/rules/

Cline и его форк Roo Code используют директории `.clinerules/` и `.roo/rules/`
соответственно. Поддерживается YAML frontmatter с условием `paths` для условной активации.

**Плюсы:**

- Режим-специфичные правила (`.roo/rules-{mode-slug}/`).
- Условная активация по паттернам файлов.
- Обратная совместимость между Cline и Roo Code.

**Минусы:**

- Фрагментация форматов при миграции между Cline и Roo Code.
- Меньшая зрелость документации по сравнению с крупными провайдерами.

### Aider — CONVENTIONS.md

Aider загружает `CONVENTIONS.md` как read-only файл через `--read` или `.aider.conf.yml`.
Файл передаётся LLM как контекст и кешируется при включённом prompt caching.

**Плюсы:**

- Простота: стандартный Markdown без метаданных.
- Поддержка prompt caching для снижения стоимости.
- Интеграция в CLI-пайплайны (`--message`, `--file`, `--read`).

**Минусы:**

- Нет условной активации или glob-скоупинга.
- Плоская структура: один файл без иерархии.
- Нет механизма progressive disclosure.

### AGENTS.md — открытый стандарт

AGENTS.md — открытый формат под управлением Agentic AI Foundation (Linux Foundation).
Используется в 60 000+ open-source репозиториях. Поддерживается 25+ инструментами,
включая Cursor, Copilot, Windsurf, Cline, Aider, Gemini CLI и другие. Claude Code
не поддерживает AGENTS.md нативно, но может быть настроен через `@`-импорт в CLAUDE.md.

**Плюсы:**

- Кросс-инструментальная совместимость: одни инструкции для всех агентов.
- Иерархия директорий (аналогично `.gitignore`).
- Активная стандартизация под Linux Foundation.
- Единый источник истины для команд с несколькими AI-инструментами.

**Минусы:**

- Стандартный Markdown без glob-скоупинга (в отличие от Cursor и Copilot).
- Отсутствие механизма progressive disclosure (skills, hooks).
- Потенциальный overhead: файл загружается в каждый запрос целиком.

## Эмпирические данные

### Исследование ETH Zurich (arXiv:2602.11988, февраль 2026)

Gloaguen et al. создали AGENTbench — 138 задач из реальных pull requests в 12 Python-
репозиториях — и протестировали 4 агента (Claude Code Sonnet 4.5, Codex GPT-5.2,
Codex GPT-5.1 Mini, Qwen Code) в трёх условиях: без файла контекста, с LLM-генерированным
файлом, с файлом, написанным разработчиком.

**Ключевые результаты:**

| Условие                 | Успешность задач | Стоимость inference |
| ----------------------- | ---------------- | ------------------- |
| Без файла контекста     | Baseline         | Baseline            |
| LLM-генерированный файл | −3%              | +20%                |
| Файл от разработчика    | +4%              | +19%                |

**Выводы исследования:**

- LLM-генерированные файлы ухудшают результат: избыточные требования и дублирование
  информации отвлекают агента.
- Файлы от разработчиков дают маргинальное улучшение (+4%), но увеличивают стоимость.
- Обзоры архитектуры и листинги директорий не ускоряют навигацию: агенты эффективно
  обнаруживают структуру кода самостоятельно.
- Агенты «слишком послушны»: они следуют инструкциям даже когда те избыточны, что
  приводит к лишним шагам и проверкам.

### Исследование ICSE JAWs (arXiv:2601.20404, 2026)

Lulla et al. провели парный эксперимент на 124 pull requests, измеряя эффективность
(wall-clock time, потребление токенов), а не корректность.

**Ключевые результаты:**

| Метрика                    | Изменение с AGENTS.md |
| -------------------------- | --------------------- |
| Медианное время (сек.)     | 98.57 → 70.34 (−29%)  |
| Потребление output-токенов | −17%                  |

**Важное ограничение:** исследование измеряло эффективность, а не корректность. Агент,
завершающий задачу быстрее, но с ошибкой, не улучшает результат.

### Исследование Instruction Gap (arXiv:2601.03269, 2025)

Исследование показало, что compliance LLM с инструкциями снижается по мере роста длины
и сложности инструкций. Основные причины:

- **Ограничения внимания:** модели теряют ранние инструкции при длинном контексте.
- **Конкуренция с обучающими данными:** при конфликте явных инструкций с паттернами
  обучения модели часто возвращаются к learned behavior.
- **Эффект lost-in-the-middle:** информация в середине длинного контекста обрабатывается
  менее эффективно, чем в начале или конце.

### Данные «26 Principles» (Bsharat et al., 2023)

Эмпирическое исследование показало, что фразы «Your task is» и «You MUST» повышают
accuracy до +57% на LLaMA и +67% на GPT-4 (в совокупности с другими принципами,
не в изоляции). Второе лицо и директивный тон ближе к instruction-tuning данным,
на которых обучались модели.

### Данные контекстного окна (Anthropic, community, 2025–2026)

- Контекстное окно Claude Code — 200K токенов.
- ~80% контекста потребляется чтением файлов и результатами инструментов.
- При заполнении 70% контекста — потеря точности; при 85% — рост галлюцинаций;
  при 90%+ — эрратичное поведение.
- Skills-архитектура с on-demand загрузкой позволяет восстановить до 15K токенов
  на сессию (82% improvement vs загрузка всего в CLAUDE.md).

## Синтез: критерии качества

### C1. Релевантность: включать только недоступную из кода информацию

Это наиболее важный критерий, подтверждённый эмпирически (ETH Zurich): избыточная
информация ухудшает результат.

**Фильтрующий вопрос:** «Может ли агент обнаружить это самостоятельно, читая код?»
Если да — не включать.

| Включать                                             | Исключать                                              |
| ---------------------------------------------------- | ------------------------------------------------------ |
| Нестандартные команды сборки/тестирования            | Описание структуры директорий                          |
| Конвенции, отличающиеся от defaults языка/фреймворка | Стандартные конвенции, которые агент уже знает         |
| Архитектурные решения, неочевидные из кода           | Подробная документация API (ссылка вместо копирования) |
| Deprecated-код, используемый в production            | Информация, часто меняющаяся                           |
| Готчи и нелогичные аспекты проекта                   | Очевидные практики («пишите чистый код»)               |
| Переменные окружения и настройки dev-среды           | Пофайловое описание кодовой базы                       |

### C2. Лаконичность: жёсткий бюджет размера

Эмпирические данные определяют три порога:

| Диапазон      | Характеристика                                  | Источник                          |
| ------------- | ----------------------------------------------- | --------------------------------- |
| < 60 строк    | Оптимальный для профессиональных команд         | Addy Osmani, GitHub blog          |
| 60–200 строк  | Рекомендуемый для большинства проектов          | Anthropic, community consensus    |
| 200–500 строк | Верхняя граница; требует модульной структуры    | Claude Code docs                  |
| > 500 строк   | Зона деградации: правила теряются, compliance ↓ | ETH Zurich, Instruction Gap paper |

**Практическое правило:** каждая строка в корневом файле инструкций загружается в каждый
запрос. Файл в 500 строк — это ~4000 токенов из 200K бюджета контекстного окна (2%),
но эффект непропорционально велик из-за instruction dilution.

### C3. Точность: конкретные формулировки с примерами

Абстрактные формулировки («пишите хороший код», «следуйте best practices») не изменяют
поведение модели и расходуют token budget (D-тир по классификации
`ai-markdown-review-prompts.md`).

**Неэффективно:**

```text
Следуйте хорошим практикам тестирования.
```

**Эффективно:**

```text
Тесты: React Testing Library + Vitest. Один тест-файл на компонент.
Формат: `ComponentName.test.tsx`. Минимум моков — реальные объекты.
```

Один код-сниппет, демонстрирующий ожидаемый стиль, эффективнее трёх абзацев описания
(GitHub blog: «Code examples over explanations»).

### C4. Структурность: логическая организация с иерархией

Рекомендуемый порядок секций (по приоритету для агента):

1. **Команды** — bash-команды для сборки, тестирования, линтинга. Размещаются первыми,
   потому что агент обращается к ним чаще всего.
2. **Архитектура** — технологический стек (с версиями), ключевые паттерны.
3. **Конвенции кода** — стиль, нейминг, структура файлов. С примерами.
4. **Тестирование** — фреймворк, подход, команды запуска.
5. **Git workflow** — ветвление, коммит-сообщения, PR-конвенции.
6. **Границы** — что агенту запрещено делать (safety constraints).

Для проектов с объёмными инструкциями — модульная структура с progressive disclosure:

```text
CLAUDE.md                          # Корневой: < 200 строк
├── .claude/skills/api/SKILL.md    # API-конвенции (on-demand)
├── .claude/skills/db/SKILL.md     # Миграции и TypeORM (on-demand)
└── .claude/agents/                # Агенты (isolated context)
```

### C5. Сопровождаемость: устойчивость к изменениям кода

Устаревшие инструкции хуже отсутствующих: агент уверенно следует неверной информации.

**Рекомендации:**

- Описывать возможности, а не пути файлов: «модуль авторизации использует кастомный
  middleware» вместо `src/auth/handlers.ts` — путь может измениться.
- Хранить инструкции в git и ревьюить при изменениях.
- Периодически аудитировать (рекомендация: ежеквартально).
- Итеративное улучшение: при каждой повторяющейся ошибке агента — добавить правило;
  при каждом правиле, которое агент не нарушает — удалить.

### C6. Непротиворечивость: единый источник истины

При использовании нескольких AI-инструментов (Cursor + Claude Code) возникает риск
дрейфа инструкций. Рекомендуемый подход — один source of truth (AGENTS.md или CLAUDE.md)
с ссылками из tool-specific файлов.

Внутри одного файла — не допускать конфликтующих инструкций. Приоритет правил
при иерархии: ближайший к редактируемому файлу файл имеет наивысший приоритет.

### C7. Верифицируемость: проверяемые инструкции

Инструкции, compliance с которыми можно проверить, более эффективны:

- «Запускать `pnpm run lint` после изменений» — верифицируемо (hook или тест).
- «Код должен быть элегантным» — не верифицируемо.

Детерминированные действия лучше оформлять как hooks, а не advisory-инструкции.
Hooks гарантируют выполнение; инструкции — нет.

### C8. Портативность: кросс-инструментальная совместимость

Для проектов с одним AI-инструментом — портативность несущественна. Для мульти-
инструментальных команд — AGENTS.md как единый файл с ссылками из CLAUDE.md,
`.cursorrules` и copilot-instructions.md.

## Стиль написания инструкций

### Второе лицо + директивный тон

Эмпирические данные (Bsharat et al., Agent SOP, industry practice) сходятся:
instruction-tuned модели лучше следуют инструкциям во втором лице с директивным тоном.
Подробный анализ — в [§ 1.7](agent-sop-patterns.md#17-грамматическое-лицо-в-инструкциях-агентам).

```text
# Эффективно
You MUST run tests after code changes.
ЗАПРЕЩАЕТСЯ коммитить напрямую в main.

# Менее эффективно
Tests should ideally be run after code changes.
Желательно не коммитить в main.
```

### Иерархия обязательств (RFC 2119)

Градация MUST / SHOULD / MAY позволяет агенту приоритизировать при длинных инструкциях.
При конфликте между правилами агент выбирает MUST над SHOULD. Без градации все правила
воспринимаются одинаково, и при ограниченном внимании менее важные правила конкурируют
с критичными.

### Обоснование запретов

Запреты с указанием причины имеют более высокий compliance, чем голые запреты
(Agent SOP, [§ 1.2](agent-sop-patterns.md#12-обоснование-запретов-must-not--because)). Голый запрет конкурирует
с обучающими данными модели; обоснованный запрет усиливает его.

```text
# Эффективно
ЗАПРЕЩАЕТСЯ удалять файлы миграций, потому что это необратимо
разрушит схему production-БД.

# Менее эффективно
Не удаляйте файлы миграций.
```

### Позитивные vs негативные формулировки

Позитивные формулировки (что делать) эффективнее негативных (что не делать), но
границы и safety constraints требуют явных запретов. Рекомендуемая трёхуровневая
структура:

- ✅ **Always do** — обязательные действия.
- ⚠️ **Ask first** — действия, требующие подтверждения.
- 🚫 **Never do** — абсолютные запреты с обоснованием.

## Антипаттерны

### AP1. Автогенерация через /init без редактирования

LLM-генерированные файлы ухудшают результат на 3% (ETH Zurich). Автогенерация дублирует
информацию, доступную агенту из кода, и добавляет шум. Решение: `/init` как стартовая
точка, затем ручная фильтрация по критерию C1 (релевантность).

### AP2. Монолитный файл > 500 строк

Длинные инструкции приводят к instruction dilution: критичные правила теряются среди
нерелевантных. Исследование Instruction Gap (arXiv:2601.03269) подтверждает: compliance
снижается с ростом длины. Решение: модульная структура с progressive disclosure.

### AP3. Описание структуры директорий

Обзоры кодовой базы и листинги файлов не ускоряют навигацию агента (ETH Zurich).
Агенты эффективно обнаруживают структуру самостоятельно. Дополнительно, файловые пути
быстро устаревают при рефакторинге. Решение: описывать возможности, а не структуру.

### AP4. Дублирование документации

Копирование API-документации, README или changelog в файл инструкций. Контент устаревает,
токены расходуются. Решение: ссылки (`@path/to/file`) вместо копирования.

### AP5. Расплывчатые persona-инструкции

Обобщённая persona-инструкция «полезный помощник по программированию» — D-тир, не несущая информации.
Решение: конкретная роль с ограничениями: «Тест-инженер для React, следует примерам,
не модифицирует source code».

### AP6. Устаревшие инструкции

Немaintained файл инструкций хуже отсутствующего: агент уверенно следует устаревшей
информации. Решение: хранить в git, ревьюить при изменениях, аудитировать ежеквартально.

### AP7. Отсутствие границ

Файл без секции «что запрещено» позволяет агенту принимать рискованные решения
(коммиты в main, удаление файлов, модификация production-конфигов). Решение:
явная секция границ с обоснованием каждого запрета.

### AP8. Одинаковые инструкции для разных контекстов

Загрузка правил миграций базы данных при работе с CSS-файлами. Нерелевантные
инструкции потребляют токены и создают шум. Решение: glob-скоупинг (Cursor, Copilot)
или skills (Claude Code).

## Рекомендуемый шаблон файла инструкций

```markdown
# Project Name

## Команды

- Build: `pnpm run build`
- Test: `pnpm run test`
- Lint: `pnpm run lint`
- Format: `pnpm run fmt`

## Стек

TypeScript, Node.js, NestJS, TypeORM, PostgreSQL 17.
React (frontend, планируется). Docker Compose для deployment.

## Конвенции

- ES modules (import/export), не CommonJS.
- Денежные суммы: DECIMAL в PostgreSQL, строки в DTO, decimal.js для арифметики.
- Commit messages: Conventional Commits.
- Тесты: Detroit TDD, реальная БД (testcontainers), минимум моков.

## Тестирование

- Фреймворк: Jest.
- Запуск одного теста: `pnpm --filter @acorn/server run test -- --testPathPattern=<pattern>`
- После изменений кода: запустить `pnpm run build && pnpm run lint && pnpm run test`.

## Границы

- 🚫 ЗАПРЕЩАЕТСЯ коммитить напрямую в main.
- 🚫 ЗАПРЕЩАЕТСЯ удалять файлы миграций, потому что это разрушит production-схему.
- 🚫 ЗАПРЕЩАЕТСЯ использовать parseFloat/Number для денежных сумм, потому что
  это приводит к ошибкам округления.
- ⚠️ Новые зависимости — только после согласования.
```

## Заключение

### Ключевые выводы

1. **Качество > количество.** Эмпирические данные (ETH Zurich) подтверждают: избыточные
   инструкции ухудшают результат. Оптимальный файл инструкций содержит 60–200 строк
   только недоступной из кода информации.

2. **Не генерировать, а писать.** LLM-генерированные файлы снижают успешность на 3%
   и увеличивают стоимость на 20%. Файлы от разработчиков дают +4% успешности.
   Рекомендация ETH Zurich: «ограничить инструкции non-inferable details».

3. **Progressive disclosure.** Корневой файл — минимальный; специализированные инструкции —
   в skills, agents или path-specific файлах. Это снижает token overhead и instruction
   dilution.

4. **Стиль имеет значение.** Директивный тон (второе лицо + MUST/SHOULD/MAY), обоснование
   запретов и конкретные примеры повышают compliance. Абстрактные формулировки («будь
   внимательным») не влияют на поведение.

5. **Стандартизация идёт.** AGENTS.md (Linux Foundation) — emerging standard с поддержкой
   25+ инструментов. Для мульти-инструментальных команд целесообразно использовать его
   как единый source of truth.

6. **Верификация критична.** Детерминированные действия (линтинг, тесты) эффективнее
   оформлять как hooks, а не advisory-инструкции. Это устраняет зависимость от compliance
   модели.

### Рекомендации для проекта Acorn Budgeting

Текущий `CLAUDE.md` проекта следует оценить по критериям C1–C8, с особым вниманием
к C1 (релевантность) и C2 (лаконичность). Модульная архитектура (CLAUDE.md → skills →
agents) уже соответствует принципу progressive disclosure. Рекомендуемые действия:

- Аудит CLAUDE.md по фильтрующему вопросу: «Может ли агент обнаружить это из кода?»
- Перенос специализированных инструкций в skills (если не перенесены).
- Добавление hooks для детерминированных проверок (линтинг, форматирование).
- Формализация границ (секция «что запрещено» с обоснованиями).
