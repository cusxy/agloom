# Протокол оркестрации

Общий протокол для skill-оркестраторов агентных циклов. Определяет инвариантные
механизмы запуска, мониторинга, возобновления агентов и обработки результатов.

## Принцип работы

Оркестратор работает **inline** в основном контексте. Его задача — управлять
последовательностью фаз, передавать данные между агентами и принимать решения
о возвратах.

Оркестратору ЗАПРЕЩАЕТСЯ вносить изменения в файлы проекта напрямую, потому что
любые изменения в файлы проекта вносятся исключительно субагентами — оркестратор
управляет процессом, но не является исполнителем.

Каждую фазу ТРЕБУЕТСЯ выполнять **отдельным агентом** с изолированным контекстом.
Формат входа/выхода агентов описан в [agent-protocol.md](agent-protocol.md).

## Структура цикла

Цикл состоит из одной или нескольких **фаз**. Каждая фаза — пара
«исполнитель → reviewer». Переход к следующей фазе ТРЕБУЕТСЯ выполнять
только при `verdict: pass` от reviewer.

```text
executor₁ → reviewer₁ → executor₂ → reviewer₂ → ... → executorₙ → reviewerₙ
     ↑            |           ↑            |                 ↑            |
     └────────────┘           └────────────┘                 └────────────┘
     (при замечаниях)         (при замечаниях)               (при замечаниях)
```

### Возврат к ранним фазам

В многофазных циклах любой reviewer МОЖЕТ рекомендовать возврат к **любому**
более раннему агенту через поле `returnTo`. При возврате ТРЕБУЕТСЯ повторить
**всю цепочку** от точки возврата до текущего шага, потому что артефакты
промежуточных фаз могут стать невалидными после изменений на ранней фазе.

Агентам ЗАПРЕЩАЕТСЯ редактировать артефакты ранних фаз, потому что разделение
фаз обеспечивает независимость ревью на каждом этапе. При обнаружении ошибки
в артефакте ранней фазы — возврат к соответствующему агенту.

`returnTo` — рекомендация агента. Оркестратор МОЖЕТ следовать ей или принять
собственное решение, опираясь на критичность findings.

## Адаптация к сложности задачи

Оркестратору СЛЕДУЕТ оценивать сложность задачи перед запуском агентов
и адаптировать стратегию выполнения. Это МОЖЕТ включать:

- **Выбор модели для агента**: параметр `model` в Agent tool.
  - По умолчанию — `sonnet`.
  - Задачи, требующие глубокого reasoning (ревью, архитектурные решения) —
    `opus`.
  - Примитивные задачи, сводящиеся к прямому следованию инструкциям
    (форматирование, переименование) — `haiku`.
- **Пропуск фаз**: если задача тривиальна и фазы определены как необязательные
  в сценарии конкретного skill, оркестратор МОЖЕТ пропустить промежуточные фазы.

Конкретные правила адаптации определяются в сценарии каждого skill.

## Запуск агентов

Агентов ТРЕБУЕТСЯ запускать через **Agent tool**.

### Параметры запуска

```text
Agent tool:
  subagent_type:        <agent-name>
  name:                 <уникальное имя для адресации через SendMessage>
  prompt:               <scope и context в формате agent-protocol.md>
  mode:                 "bypassPermissions"
  run_in_background:    true
  description:          <краткое описание задачи, 3–5 слов>
```

Параметр `name` ТРЕБУЕТСЯ задавать — он используется для возобновления агента
через `SendMessage`. Параметр `description` СЛЕДУЕТ использовать для
идентификации агента в уведомлении (например, `"spec-writer: create spec"`).

### Ожидание результата

После запуска агента с `run_in_background: true` система автоматически уведомит
о завершении. ЗАПРЕЩАЕТСЯ опрашивать статус агента, потому что уведомление
о завершении доставляется автоматически. Время ожидания СЛЕДУЕТ использовать
для взаимодействия с пользователем.

### Парсинг результата

Ответ агента — строго JSON. Формат сообщений подробно описан в разделе [Выход](agent-protocol.md#выход).

## Возобновление агента (resume)

При переходах **внутри одной фазы** СЛЕДУЕТ возобновлять предыдущий экземпляр
агента через `SendMessage(to: <name>)`. Агент продолжает с полным сохранением
контекста предыдущей работы — не тратит токены на повторное чтение файлов.

Внутрифазовые переходы — это оба направления между исполнителем и reviewer:

- reviewer → исполнитель (возврат на доработку после `verdict: fail`).
- исполнитель → reviewer (повторная верификация после исправлений).

**Когда использовать SendMessage (resume):**

- Любой переход внутри одной фазы (reviewer ↔ исполнитель).

**Когда создавать нового агента:**

- Межфазовые переходы (другой агент, другой контекст).
- Возврат к ранней фазе из поздней — файлы могли измениться между фазами,
  агент увидит устаревшие версии в транскрипте.

## Определение scope

1. Если пользователь указал файлы — ТРЕБУЕТСЯ использовать их как scope.
2. Если пользователь описал задачу — ТРЕБУЕТСЯ определить целевые файлы (существующие или путь
   для новых) и использовать как scope. Описание задачи ТРЕБУЕТСЯ передавать в context.
   Правила определения путей определены в сценарии конкретного skill.
3. Между фазами: `artifacts` предыдущего агента ТРЕБУЕТСЯ использовать как
   `scope` следующего.

## Формирование context

При запуске агента оркестратору ТРЕБУЕТСЯ сформировать context, содержащий
все данные, необходимые агенту для выполнения работы. Агент работает
в изолированном контексте и не имеет доступа к истории взаимодействия
оркестратора с пользователем.

### Обязательное содержание context

При первом запуске агента (создание) context ТРЕБУЕТСЯ включать:

- Описание задачи пользователя.
- Результаты уточнения требований: ответы пользователя на вопросы
  и принятые решения (из pre-cycle clarification).
- Результаты предварительного исследования — если оркестратор проводил
  исследование кодовой базы, документации или внешних источников.
- Флаг `skip_clarification: true` — если пользователь запросил opt-out.

При межфазовом переходе в context ТРЕБУЕТСЯ включать:

- Краткое описание задачи (агент не видит предыдущие фазы).
- Phase Execution Summaries всех завершённых фаз
  (см. [Phase Execution Summary](#phase-execution-summary-pes)).

При возврате к ранней фазе в context ТРЕБУЕТСЯ включать:

- Краткое описание задачи.
- Phase Execution Summary фазы, к которой происходит возврат (choices агента,
  включая метки валидации пользователем, и findings summary).
- Phase Execution Summaries всех фаз, выполненных после точки возврата,
  чтобы агент понимал что произошло после его работы.
- Findings, послужившие причиной возврата (только fail-items).

При внутрифазовом возврате от reviewer context формируется из findings
reviewer-агента (см. [Интерпретация результата](#интерпретация-результата)).

## Уточнение требований (pre-cycle clarification)

Перед запуском первого агента оркестратору ТРЕБУЕТСЯ провести двухраундовую
процедуру уточнения требований. Цель — сократить дельту понимания между
пользователем и агентами до начала работы.

### Процедура

**Раунд 1 — первичный анализ:**

1. Проанализировать задачу пользователя на полноту, непротиворечивость и однозначность.
2. Определить необходимость предварительного исследования:
   - Кодовая база и документация проекта.
   - Внешние источники: документация API, библиотек, фреймворков —
     если у оркестратора недостаточно актуальных данных по теме задачи.
   - Сравнительный анализ подходов к реализации — если задача допускает
     несколько архитектурных решений.
3. При необходимости — провести исследование до формулирования вопросов,
   чтобы вопросы были предметными, а не общими.
4. Сформулировать уточняющие вопросы в структурированном формате.
5. Задать вопросы пользователю и получить ответы.

**Раунд 2 — реанализ (double-check):**

1. Проанализировать ответы пользователя совместно с исходной задачей.
2. Проверить: не противоречат ли ответы исходному запросу, не вводят ли
   новые неоднозначности, достаточно ли данных для начала работы.
3. Если выявлены вопросы второго слоя — задать их пользователю.
4. Если новых вопросов нет — сообщить пользователю и запросить подтверждение
   к старту.

Третьего раунда нет. Оставшиеся неоднозначности обрабатываются агентами
через `choices` с `confidence: low` или `medium`
(см. [Структура choice](agent-protocol.md#структура-choice)).

### Формат вопросов

Оркестратору СЛЕДУЕТ задавать вопросы в структурированном виде:

```text
**Q1. <Тема>**: <Вопрос>
Контекст: <почему этот вопрос важен>
Варианты: <если применимо, перечислить варианты с оценкой>
```

### Opt-out

Если пользователь явно указал пропустить уточнение (например,
«без дополнительных вопросов»), оркестратор МОЖЕТ пропустить оба раунда
и приступить к запуску агентов.

При opt-out оркестратору ТРЕБУЕТСЯ передать указание `skip_clarification: true`
в context каждого субагента, чтобы агенты пропустили проверку неоднозначностей
в DoR (см. [Верификация DoR/DoD](agent-protocol.md#верификация-dordod)).

## Валидация на границах фаз (human-in-the-loop)

Оркестратор использует модель **selective HITL** — глубина вовлечения
пользователя определяется уровнем confidence в choices агентов. Принцип:
минимальное вмешательство при высокой уверенности, обязательное — при
неуверенности.

### Когда запрашивать валидацию

- **Forward transition** (фаза N → фаза N+1):
  - Если все choices имеют `confidence: high` — валидация НЕ ТРЕБУЕТСЯ.
    Оркестратор информирует пользователя о принятых решениях и переходит
    к следующей фазе без блокировки.
  - Если есть choices с `confidence: low` или `medium` — ТРЕБУЕТСЯ
    запросить валидацию. Оркестратор представляет пользователю: артефакты
    фазы, choices (группированные по confidence), краткую сводку результата.
  - Если choices отсутствуют и задача тривиальна — валидация НЕ ТРЕБУЕТСЯ.
  - Если choices отсутствуют, но задача нетривиальна — оркестратору СЛЕДУЕТ
    передать reviewer указание проверить артефакт на имплицитные решения,
    которые executor не зафиксировал как choices.
- **Return** (reviewer fail → executor fix): валидация НЕ ТРЕБУЕТСЯ, если
  executor не добавил новых choices с `confidence: low` или `medium`.
  Если добавил — ТРЕБУЕТСЯ запросить валидацию.
- **Конец цикла**: ТРЕБУЕТСЯ запросить валидацию всегда. Пользователь
  подтверждает завершение или указывает, что требуется доработка.

### Формат валидации

Оркестратору СЛЕДУЕТ представлять пользователю структурированную сводку:

```text
Фаза <N> завершена: <название фазы>

Артефакты: <список файлов>
Verdict reviewer: <pass/fail>

Решения, требующие валидации:
- [low] <choice> — <context>
- [medium] <choice> — <context>

Принятые решения (для ознакомления):
- [high] <choice>

Подтверждаете переход к следующей фазе?
```

При пропуске HITL (all-high) оркестратору СЛЕДУЕТ вывести краткую сводку
без блокировки:

```text
Фаза <N> завершена: <название фазы>

Артефакты: <список файлов>
Принятые решения: <перечень high-confidence choices>

Переход к следующей фазе.
```

При отказе пользователя — оркестратор уточняет замечания и возвращает
к соответствующему агенту.

### Механизм валидации choices

Каждый choice имеет идентификатор (`id`), назначенный агентом. Оркестратор
использует эти идентификаторы при представлении choices пользователю.

Пользователь МОЖЕТ:

- Подтвердить все choices («да, продолжаем»).
- Отклонить конкретные choices по ID («C2 неверно, нужно X»).
- Скорректировать choice («C3 — почти, но с уточнением Y»).

При подтверждении оркестратор добавляет метку `ПОДТВЕРЖДЕНО` в PES.

### Opt-out

Если пользователь явно указал пропустить валидацию, оркестратор МОЖЕТ
пропустить human-in-the-loop на forward transitions. Валидацию в конце цикла
ТРЕБУЕТСЯ запрашивать даже при opt-out.

## Phase Execution Summary (PES)

После прохождения фазы (reviewer `verdict: pass`) оркестратору ТРЕБУЕТСЯ
построить Phase Execution Summary из результатов агентов фазы.

PES является **единственным механизмом передачи контекста между фазами**
(context budget). Агент следующей фазы получает PES, а не полный транскрипт
предыдущих агентов. Это обеспечивает контролируемый объём контекста
без необходимости ручного управления: каждая фаза сжимает свои результаты
в типизированную сводку, которая содержит всё необходимое для продолжения
работы.

### Содержание PES

```text
## Phase Summary: <название фазы>

Artifacts: <список файлов>
Choices:
- [high] <choice> — <context краткий>
- [medium] <choice> — <context краткий> → ПОДТВЕРЖДЕНО
Findings summary:
- <что проверено и пройдено: краткая сводка>
- <что потребовало доработки: суть замечания и как исправлено>
```

- `choices` — из result исполнителя фазы. Каждый choice включает confidence.
- Метка `ПОДТВЕРЖДЕНО` — добавляется после валидации пользователем
  на human-in-the-loop. Подтверждённые choices НЕ ДОЛЖНЫ пересматриваться
  при возврате к агенту.
- `findings summary` — краткая сводка результатов ревью: какие критерии
  проверены, какие замечания были и как они разрешены. При межфазовом
  переходе информация о пройденных findings доступна агенту следующей фазы.

### Правила хранения

- PES строится один раз при завершении фазы.
- При возврате к фазе и повторном прохождении — оркестратор строит новый PES
  из комбинации старого PES и нового output агента. Подтверждённые choices,
  которые новый агент не изменил, сохраняют метку `ПОДТВЕРЖДЕНО`. Новые
  или изменённые choices требуют повторной валидации. Findings summary
  обновляется с учётом новых итераций ревью.
- Оркестратор хранит PES в своём контексте (inline, не в файлах).

## Интерпретация результата

- `verdict: pass` → построить PES, переход к следующей фазе (или завершение цикла).
- `verdict: fail` → оценить findings. Каждый finding содержит `returnTo` —
  рекомендуемый агент для исправления. Оркестратору ТРЕБУЕТСЯ определить точку
  возврата на основе `returnTo` из findings, опираясь на критичность замечаний.

При внутрифазовом возврате ТРЕБУЕТСЯ передать `findings` из result
reviewer-агента как `context`. При межфазовом возврате — формировать
обогащённый context (см. [Формирование context](#формирование-context)).

## Обработка DoR-ошибок агентов

Если агент вернул `verdict: fail` в preconditions, оркестратору ТРЕБУЕТСЯ
проанализировать каждый непройденный пункт DoR: его `comment` и `returnTo`.

### Маршрутизация по returnTo

Если пункт DoR содержит `returnTo` — проблема в артефакте предыдущей фазы,
а не в context от оркестратора. Оркестратору ТРЕБУЕТСЯ:

1. Передать comment как context агенту из `returnTo`.
2. После исправления — повторить всю цепочку от точки возврата до текущего
   агента (аналогично межфазовому возврату от reviewer).

### Самостоятельное разрешение

Если `returnTo` не указан (`null`), оркестратор МОЖЕТ разрешить DoR-ошибку
без обращения к пользователю если:

- Агенту не хватает файла, который оркестратор может найти в проекте.
- Агенту не хватает контекста, который оркестратор уже получил от пользователя
  во время pre-cycle clarification, но не включил в context.
- Агенту нужны результаты исследования, которое оркестратор может провести
  самостоятельно (чтение кода, документации).

В этом случае оркестратор дополняет context и перезапускает агента.

### Эскалация к пользователю

Оркестратору ТРЕБУЕТСЯ обратиться к пользователю если:

- `returnTo` не указан и оркестратор не может разрешить проблему самостоятельно.
- Агент запросил данные, которых нет в проекте и которые может предоставить
  только пользователь.

## Обработка ошибок

- Если reviewer возвращает `verdict: fail` 3 раза подряд на одной фазе —
  ТРЕБУЕТСЯ остановиться и сообщить пользователю о зацикливании с деталями findings.
- Если `artifacts` исполнителя пуст — ТРЕБУЕТСЯ завершить с ошибкой (агент не создал артефакты).
- Если `artifacts` содержит несколько файлов — ТРЕБУЕТСЯ передать все файлы в scope reviewer.

## Сводка

После завершения цикла ТРЕБУЕТСЯ вывести сводку результатов. Содержание сводки
определяется сценарием конкретного skill.
